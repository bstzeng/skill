# 原生透明圖片生成

以原生 alpha 生成素材。在原始檔案通過 alpha 檢查之前，把看得見的棋盤格、寫著「透明」的提示詞，以及成功的工具呼叫都視為未驗證。

## 嚴守邊界

- 只有在新生成的素材、且交付物必須包含原生透明度時，才使用本技能。
- 除非使用者明確要求編修，否則把提供的圖片視為身分、主體、構圖或媒材的參考。
- 不要呼叫去背、分割、色鍵擷取、遮罩或本機 alpha 合成來搶救不透明的輸出。
- 不要把渲染出來的棋盤格稱為「透明」。RGB 的棋盤格是失敗的素材。
- 如果使用者其實是想從既有的不透明圖片移除背景，就導向去背工作流程，並揭露那是編修，而不是原生生成。

## 保守地生成

1. 保留使用者對主體、身分、風格、構圖與文字的限制。
2. 加上一個簡潔的輸出要求：回傳 PNG 或 WebP，主體以外的區域是帶有真正 alpha 通道的真實像素透明。
3. 使用只能下提示詞的內建圖片工具時，一次只發出一個原生 alpha 的交付物。除非目前的工具明確提供每次請求的背景控制，且已驗證並行時的原生 alpha 行為，否則不要平行處理。
4. 當使用者明確選擇提供輸出控制的 API 途徑時，要求 `background: "transparent"` 與 `output_format: "png"` 或 `"webp"`。
5. 保留原本回傳的位元組。驗證不得重寫、最佳化、合成、縮放或以其他方式改變交付物。

準備提示詞、重試失敗的輸出、生成多個素材或回報限制時，閱讀 [references/prompting-and-retry.md](references/prompting-and-retry.md)。

只有在以下條件都成立時，檔案才通過技術關卡：

- 解碼後的像素包含 alpha 通道；
- 至少有一個像素完全透明，且至少有一個可見；
- 當素材應該是獨立去背的時候，要求的留白角落是透明的；以及
- 驗證器在原始輸出上成功結束。

然後在對比強烈的檢視背景上檢查實際的邊緣。Alpha 中繼資料無法證明細毛是乾淨的，也無法證明圖片沒有大片半透明的霧感。即使中繼資料關卡通過，也要拒絕可見的棋盤格、邊緣光暈、彩色霧氣、非預期的陰影、被裁掉的髮絲或缺少的細節。

## 重試，但不假裝成功

- 遇到 RGB 或不透明的輸出時，保留所有主體不變條件，只重試原生 alpha 的輸出指示。
- 除非使用者要求更多，否則每個不同的素材最多總共嘗試生成三次。
- 每次嘗試後都要驗證。不要把失敗的圖片編修到符合要求。
- 如果所有嘗試都失敗，停下來並回報原始的模式與驗證失敗。只有在可用且獲得授權時，才提供明確的 API 途徑；絕不默默更換模型或使用去背。

## 回報證據

對每一個被接受的素材，回報：

- 已知的生成途徑與模型；
- 原始檔案路徑、格式、尺寸、模式與 SHA-256；
- alpha 極值、完全透明像素數、角落 alpha 值，以及驗證器的判定；
- 邊緣目視品管的結果；以及
- 確切的最終提示詞，或加到使用者提示詞中的原生 alpha 子句。

把 `generated`（已生成）、`alpha-validated`（已驗證 alpha）、`edge-inspected`（已檢查邊緣）、`user-accepted`（使用者已接受）與 `published`（已發布）保持為各自獨立的狀態。
