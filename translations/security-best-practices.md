# 資安最佳實踐

## 概述

本技能說明如何辨識目前脈絡所使用的語言與框架，然後從本技能的 references 目錄載入該語言和/或框架的資安最佳實踐資訊。

這些資訊（如果有的話）可以用來撰寫新的、預設安全的程式碼，或被動地偵測既有程式碼中的重大問題，或（在使用者要求時）提供漏洞報告並建議修正。

## 工作流程

本技能的第一步，是辨識你被要求使用、或已存在於你所處理專案範圍中的「所有」語言與「所有」框架。聚焦在主要的核心框架。你通常會想要同時辨識前端與後端的語言與框架。

然後檢查本技能的 references 目錄，看是否有與該語言和/或框架相關的文件。務必閱讀與特定框架或語言相關的「所有」參考檔。檔名格式為 `<language>-<framework>-<stack>-security.md`。你也應該檢查是否有一份與框架無關的 `<language>-general-<stack>-security.md`。

如果你處理的是包含前端與後端的網頁應用程式，務必同時檢查前端「與」後端的參考文件！

如果你被要求製作一個包含前端與後端的網頁應用程式，但沒有指定前端框架，也要查看 `javascript-general-web-frontend-security.md`。了解如何同時保護前端與後端是很重要的。

如果技能的 references 目錄中沒有相關資訊，就想一想你對該語言、框架以及其所有知名資安最佳實踐的了解。如果不確定，你可以試著上網搜尋資安最佳實踐的文件。

接下來它可以以幾種方式運作。

1. 主要模式是從此刻起，就用這些資訊撰寫預設安全的程式碼。這在開始新專案或撰寫新程式碼時很有用。

2. 次要模式是在專案中工作、為使用者撰寫程式碼時，被動地偵測漏洞。違反資安指引的嚴重或非常重要的漏洞或重大問題，可以被標記出來並告知使用者。這個被動模式應聚焦在影響最大的漏洞與安全的預設值。

3. 使用者可以要求一份資安報告，或要求改善程式碼庫的安全性。這種情況下，應產出一份完整的報告，描述專案沒有遵循資安最佳實踐指引的每一處。報告應排定優先順序，並有清楚的嚴重度與急迫性章節。然後提議開始處理這些問題的修正。見下方的「修正」。

## 工作流程決策樹

- 如果語言/框架不清楚，就檢查 repo 來確定，並列出你的證據。
- 如果 `references/` 中有相符的指引，只載入相關的檔案並遵循其指示。
- 如果沒有相符的指引，就想想你是否知道所選語言和/或框架的任何知名資安最佳實踐；但如果被要求產生報告，要讓使用者知道沒有具體的指引可用（你仍然可以產生報告，或偵測確定的嚴重漏洞）

# 覆寫

雖然這些參考包含了語言與框架的資安最佳實踐，但客戶可能有需要略過或覆寫這些實踐的情況。留意專案文件與提示檔中可能要求你覆寫某些最佳實踐的具體規則與指示。覆寫某項最佳實踐時，你「可以」向使用者回報，但不要和他們爭執。如果某項資安最佳實踐因為專案特定的原因需要被略過/忽略，你也可以建議在專案中加入關於這點的文件，讓人清楚為什麼沒有遵循該最佳實踐，並在未來沿用這個略過。

# 報告格式

產出報告時，你應該把報告寫成 `security_best_practices_report.md` 這個 Markdown 檔，或使用者提供的其他位置。你可以詢問使用者想把報告寫到哪裡。

報告的開頭應該有一段簡短的主管摘要。

報告應依漏洞的嚴重度，清楚劃分成多個章節。報告應聚焦在最嚴重的發現，因為這些對使用者的影響最大。所有發現都應標上數字 ID，方便引用。

對於嚴重的發現，附上一句影響說明。

報告寫好之後，也直接向使用者回報，不過可以比較精簡。如果使用者想更了解任何發現，你可以提議解釋任何發現或資安最佳實踐指引背後的原因。

重要：在報告中引用程式碼時，務必找出並附上你所引用程式碼的行號。

寫完報告檔之後，向使用者摘要發現。

也要告訴使用者最終報告寫在哪裡

# 修正

如果你產出了報告，讓使用者閱讀報告，並詢問是否開始進行修正。

如果你被動地發現了嚴重的問題，就通知使用者，並詢問他們是否要你修正這項發現。

產出修正時，一次專注修正一項發現。修正應附上簡潔清楚的註解，說明新程式碼是依據哪項具體的資安最佳實踐，也許再加上一句不這樣做為什麼危險的簡短理由。

一律考慮你想做的變更是否會影響使用者程式碼的功能。考慮這些變更是否可能讓專案目前的運作方式出現退化。不安全的程式碼常常因為其他原因而被依賴（這也是為什麼不安全的程式碼會存在那麼久）。避免弄壞使用者的專案，因為這可能讓他們以後不想再套用資安修正。寫一個深思熟慮、充分參考專案其他部分的修正，好過一個倉促的變更。

一律遵循使用者已設定的任何一般變更或 commit 流程。如果要做 git commit，提供清楚的 commit 訊息，說明這是為了符合資安最佳實踐。盡量避免把多個不相關的發現綁在同一個 commit 中。

一律遵循使用者已設定的任何一般測試流程（如果有的話），以確認你的變更沒有引入退化。考慮這些變更可能帶來的二階影響，如果有的話，在做之前先告知使用者。

# 一般資安建議

以下是幾項適用於幾乎任何語言或框架的安全程式設計建議。

### 避免用遞增 ID 作為資源的公開 ID

為某個將會暴露在網際網路上的資源指派 ID 時，避免使用小的自動遞增 ID。改用較長、隨機的 UUID4 或隨機 hex 字串。這能防止使用者得知資源的數量，以及猜出資源 ID。

### 關於 TLS 的注意事項

雖然 TLS 對正式部署很重要，但大多數開發工作都會在關閉 TLS 的情況下進行，或由某個範圍外的 TLS 代理提供。因此，要非常小心不要把缺少 TLS 回報為資安問題。也要非常小心「secure」cookie 的使用。只有在應用程式實際會透過 TLS 提供時才應該設定它們。如果在非 TLS 的應用程式上設定它們（例如部署在本機開發或測試時），會讓應用程式壞掉。你可以提供一個環境變數或其他旗標來覆寫 secure 的設定，讓它在部署到 TLS 正式環境之前保持關閉。此外，避免建議 HSTS。在沒有完全了解其持久影響的情況下使用它是危險的（可能造成重大中斷與使用者被鎖在外面），而且對 codex 所審查的專案範圍而言，一般不建議使用。
