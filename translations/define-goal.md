# 定義目標

## 概述

把使用者的意圖塑造成一個代理能誠實追求的目的。優先使用可衡量的結果、明確的證據與有界的範圍，而不是活動的描述。

本技能只涵蓋目標的定義與 goal 工具的建立。不要從本技能建立中間的規劃產出物、持久快照、帳本、決策紀錄或接續檔。

## 工作流程

1. 確認真的需要定義目標。
   - 當使用者要求 `$define-goal`、要求建立或設定目標、要求使用 goal 工具，或想要協助把一個意圖變成清楚的目的時，使用本技能。
   - 如果使用者只是要求一般的實作工作，就直接做，而不是強迫建立目標。

2. 用具體的話重述可能的目標。
   一個可用的目標會指名：
   - 將會成立的具體結果
   - 涉及的主要產出物、系統、repo、環境或使用者可見的行為
   - 如何驗證完成
   - 什麼在範圍內
   - 在模稜兩可會造成影響時，什麼在範圍外
   - 何時該停下來詢問使用者，而不是一直硬幹

3. 在領域允許時讓它量化。
   優先使用代表真正成功的數字，而不是裝飾性的精確：
   - 通過/失敗的驗證器：確切的測試、檢查、CI 作業、評估、指令或驗收條件
   - 品質門檻：延遲、錯誤率、成本、準確率、召回率、精確率、覆蓋率、不穩定率、bundle 大小、記憶體、可用時間、完成率或人工審查標準
   - 產出物限制：檔案路徑、受影響的模組、允許的指令、輸出格式、目標環境、截止日期或最大影響範圍
   - 證據數量：重現的失敗次數、成功的重跑次數、審查過的範例、遷移的紀錄、處理過的留言或驗證過的案例

4. 在設定之前修補薄弱的目標。
   - 當本地脈絡讓改寫是安全的時，把模糊的目標改寫成可衡量的目的。
   - 當缺少的細節會改變預期結果或驗證方式時，問一個簡潔的釐清問題。
   - 拒絕純粹的活動型目標，例如「取得進展」「繼續調查」「把事情變好」或「處理 X」，除非它們被磨利成一個可驗證的結果。

5. 建立目標之前，先檢查目前的目標狀態。
   - 呼叫 `get_goal`。
   - 如果沒有進行中的目標，且這個目的符合品質標準，就呼叫 `create_goal`。
   - 如果有一個仍符合使用者意圖的進行中目標，就繼續使用它，而不是建立重複的目標。
   - 如果有一個與新請求衝突的進行中目標，就詢問要完成目前的目標、在完成時把它標記為完成，還是開啟另一個以目標為依據的執行緒。

6. 只有在通過品質標準之後才建立目標。
   - 使用單一、簡潔的目的字串。
   - 在目的本身中包含驗證證據。
   - 當範圍邊界會限制工作時，把它們包含進去。
   - 只有在使用者明確要求時，才包含 token 預算。
   - 除非使用者明確要求以目標為依據的工作，否則不要為一般的多步驟任務呼叫 `create_goal`。

## 目標品質標準

在 `create_goal` 之前，目的應該回答：

- 完成時，什麼具體的事情會成立？
- 什麼證據能證明它？
- 什麼量化或二元的門檻定義了成功？
- 哪些範圍邊界很重要？
- 什麼情況應該讓代理停下來詢問？

好的：

> 以最小、安全的伺服器端變更，把文件記載的慢速路徑上的結帳 API p95 延遲降到 250 ms 以下，然後以 `npm run test:checkout` 以及既有的本機延遲基準測試驗證，連續 3 次執行的 p95 都低於 250 ms。

好的：

> 解決 PR 123 上要求修改程式碼的開啟中審查留言，只更新受影響的驗證檔案與測試，並以針對性的驗證測試指令，加上 `gh pr view 123` 顯示沒有未解決的要求修改討論串來驗證。

薄弱的：

> 讓結帳變快。

薄弱的：

> 繼續調查 PR 的留言。

## 量化的經驗法則

- 對於 bug，把成功定義為先重現、再修正，並在可能時有一個先失敗後通過的驗證器。
- 對於測試，指名確切的指令以及必要的通過條件。
- 對於效能，指名指標、目標門檻、量測方法與執行次數。
- 對於品質工作，定義一個可觀察的驗收標準，例如審查過的範例、lint/typecheck/test 通過，或使用者核准的產出物。
- 對於研究，定義研究必須促成的決策、範圍內的來源或系統，以及證據標準。
- 對於維運，定義健康狀態、監控時間窗、失敗門檻，以及回復或升級處理的觸發條件。

## 釐清問題

只有在一個合理的改寫可能會導致追求錯誤的結果時才詢問。讓問題保持簡短，並圍繞著缺少的驗證器或範圍邊界。

有用的問題形式：

- 「這裡應該用什麼指標定義成功：延遲、成本、準確率，還是使用者可見的行為？」
- 「我應該在哪個環境驗證：本機、staging，還是正式環境？」
- 「在我把這個目標標記為完成之前，你最低想要看到什麼證據？」

如果使用者無法提供指標，就提出最誠實、可用的二元驗證器，並請他們確認。
