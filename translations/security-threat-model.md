# 原始碼 Repo 威脅建模

交付一份可執行、AppSec 等級、專屬於該 repo 或專案路徑的威脅模型，而不是通用檢查清單。每一項架構主張都要錨定在 repo 中的證據上，並明確寫出假設。優先考量真實的攻擊者目標與具體影響，而非通用檢查清單。

## 快速開始

1) 收集（或推斷）輸入：
- Repo 根目錄路徑與任何範圍內的路徑。
- 預期用途、部署模型、網際網路暴露程度，以及驗證預期（如果已知）。
- 任何既有的 repo 摘要或架構規格。
- 使用 `references/prompt-template.md` 中的提示詞產生 repo 摘要。
- 遵循 `references/prompt-template.md` 中規定的輸出契約。可能的話逐字使用。

## 工作流程

### 1) 界定範圍並萃取系統模型
- 從 repo 摘要中辨識主要元件、資料儲存與外部整合。
- 辨識系統如何執行（伺服器、CLI、函式庫、worker）及其進入點。
- 把執行期行為與 CI/建置/開發工具，以及測試/範例區分開來。
- 把範圍內的位置對應到這些元件，並明確排除範圍外的項目。
- 沒有證據就不要宣稱存在某些元件、流程或控制措施。

### 2) 推導邊界、資產與進入點
- 把信任邊界列舉為元件之間具體的邊，並註明協定、驗證、加密、驗證輸入與速率限制。
- 列出驅動風險的資產（資料、憑證、模型、設定、運算資源、稽核日誌）。
- 辨識進入點（端點、上傳介面、解析器/解碼器、工作觸發器、管理工具、日誌/錯誤接收端）。

### 3) 校準資產與攻擊者能力
- 列出驅動風險的資產（憑證、個資、完整性關鍵狀態、可用性關鍵元件、建置產出物）。
- 根據暴露程度與預期用途，描述真實的攻擊者能力。
- 明確註明攻擊者「不具備」的能力，避免誇大嚴重性。


### 4) 把威脅列舉為濫用路徑
- 優先考慮能對應到資產與邊界的攻擊者目標（資料外洩、權限提升、完整性破壞、阻斷服務）。
- 為每個威脅分類，並連結到受影響的資產。
- 威脅數量保持少而精。

### 5) 以明確的可能性與影響推理排定優先順序
- 使用定性的可能性與影響（低/中/高），並附上簡短理由。
- 用「可能性 × 影響」設定整體優先順序（嚴重/高/中/低），並依既有控制措施調整。
- 說明哪些假設最影響排序。

### 6) 與使用者確認服務脈絡與假設
- 摘要會實質影響威脅排序或範圍的關鍵假設，然後請使用者確認或更正。
- 提出 1–3 個針對性問題來補足缺少的脈絡（服務負責人與環境、規模/使用者、部署模型、身分驗證/授權、網際網路暴露、資料敏感度、多租戶）。
- 在產出最終報告之前暫停，等待使用者回饋。
- 如果使用者拒絕或無法回答，說明哪些假設仍然存在，以及它們如何影響優先順序。

### 7) 建議緩解措施與聚焦路徑
- 區分既有的緩解措施（附證據）與建議的緩解措施。
- 把緩解措施連結到具體位置（元件、邊界或進入點）與控制類型（授權檢查、輸入驗證、schema 強制、沙箱、速率限制、機密隔離、稽核日誌）。
- 優先提供具體的實作提示，而非通用建議（例如「在 gateway 對上傳內容強制 schema」而非「驗證輸入」）。
- 建議要基於已確認的使用者脈絡；如果假設仍未解決，就把建議標示為有條件的。

### 8) 定稿前進行品質檢查
- 確認所有發現的進入點都已涵蓋。
- 確認每個信任邊界都在威脅中有所呈現。
- 確認執行期與 CI/開發已區分。
- 確認使用者的釐清（或明確的未回應）已反映在內。
- 確認假設與待解問題都已明確寫出。
- 確認報告格式與提示詞模板 `references/prompt-template.md` 中定義的必要輸出格式高度一致。
- 把最終 Markdown 寫入名為 `<repo-or-dir-name>-threat-model.md` 的檔案（使用 repo 根目錄的基本名稱，若被要求建模子路徑則使用範圍內目錄的名稱）。


## 風險優先順序指引（舉例說明，非窮舉）
- 高：驗證前的遠端程式碼執行（RCE）、驗證繞過、跨租戶存取、敏感資料外洩、金鑰或 token 竊取、模型或設定完整性遭破壞、沙箱逃逸。
- 中：針對關鍵元件的定向 DoS、部分資料暴露、具可衡量影響的速率限制繞過、影響偵測能力的日誌/指標汙染。
- 低：低敏感度資訊洩漏、容易緩解的雜訊型 DoS、需要不太可能成立之前提條件的問題。
