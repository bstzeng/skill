# 測試驅動開發（Test-Driven Development）

TDD 就是「紅 → 綠」循環。本技能是一份參考，讓這個循環產出值得保留的測試：什麼是好測試、測試該放在哪裡、有哪些反模式，以及循環的規則。每一節在每個循環都適用：在循環之前與進行中就要參考，而不是事後才看。

探索程式碼庫時，先讀 `GLOSSARY.md`（如果有），讓測試名稱與介面用語符合專案的領域語言，並尊重你所修改區域的 ADR。

## 什麼是好測試

測試透過公開介面驗證行為，而非實作細節。程式碼可以整個改掉，測試不應該跟著改。好的測試讀起來像規格：「使用者可以用有效的購物車結帳」清楚說明了存在什麼能力，而且它能撐過重構，因為它不在乎內部結構。

範例請見 [tests.md](tests.md)，mock 的指引請見 [mocking.md](mocking.md)。

## 接縫（Seams）：測試放在哪裡

**接縫**是你進行測試的公開邊界：在這個介面上你可以觀察行為，而不必伸手到內部。測試存在於接縫上，永遠不針對內部實作。

**只在事先約定好的接縫上測試。** 在寫任何測試之前，先寫下要測試的接縫並與使用者確認。未確認的接縫上不寫任何測試。你不可能測試所有東西，所以事先約定接縫，是讓測試心力落在關鍵路徑與複雜邏輯上、而不是每個邊角案例的方法。

詢問：「公開介面是什麼？我們應該測試哪些接縫？」為每個提議的接縫附上一行說明：它能抓到什麼、會漏掉什麼。

當介面本身的形狀還有疑問時（模組有多深、接縫該放哪、介面該暴露什麼），用「codebase-design」呼叫 Skill 工具取得相關詞彙。它是模組、介面、深度、接縫、轉接器、槓桿與區域性等術語的共同來源，是一份查閱用的參考，而不是要執行的一個 session。

## 反模式

- **與實作耦合**：mock 內部協作者、測試私有方法，或透過旁路驗證（直接查資料庫而不是使用介面）。徵兆：重構時測試壞了，但行為根本沒變。
- **同義反覆（Tautological）**：斷言用和程式碼一樣的方式重新計算預期值（`expect(add(a, b)).toBe(a + b)`、用同樣方式手動推導的快照、斷言常數等於它自己），所以它注定通過，永遠不可能和程式碼意見不同。預期值必須來自獨立的真實來源：已知正確的字面值、手算範例、規格。
- **水平切片**：先寫完所有測試，再寫完所有實作。大量預寫的測試驗證的是「想像中」的行為：你測試的是東西的「形狀」而非使用者可見的行為，測試對真正的變化變得不敏感，而且你在理解實作之前就已鎖死測試結構。改用**垂直切片**：一個測試 → 一段實作 → 重複，每個測試都是一顆**曳光彈**，回應上一個循環教會你的事。

## 循環規則

- **先紅後綠。** 先寫會失敗的測試，然後只寫剛好讓它通過的程式碼。不要預想未來的測試或加入臆測性的功能。
- **一次一個切片。** 每個循環一個接縫、一個測試、一個最小實作。
- **重構不屬於這個循環。** 它屬於審查階段（見 `code-review` 技能），而不是紅 → 綠的實作循環。
