# 診斷 Bug

一套處理困難 bug 的紀律。只有在有明確理由時才略過某些階段。

探索程式碼庫時，閱讀 `GLOSSARY.md`（如果有）以對相關模組建立清楚的心智模型，並檢查你所碰觸區域的 ADR。

## 遮蔽

本技能會讓你展示指令、輸出與擷取的產出物。**先遮蔽每一個機密**：在其位置寫上 `<REDACTED>`。以環境變數建立循環，讓憑證留在環境中，而不是出現在你展示的內容裡。擷取的產出物會帶有驗證標頭：只引用帶有訊號的那幾行。

如果遮蔽後的輸出不足以診斷 bug，就說明並詢問使用者。

## 第一階段：建立回饋循環

**這就是這項技能本身。** 其他一切都是機械性的。如果你對這個 bug 有一個**緊湊**的通過/失敗訊號（一個會因*這個* bug 變紅的訊號），你就會找到原因；二分搜尋、假設驗證與插樁全都只是在消耗它。如果你沒有，盯著程式碼看再久也救不了你。

在這裡投入不成比例的心力。**要積極。要有創意。拒絕放棄。**

### 建立方式，大致依此順序

1. **失敗的測試**，放在任何能觸及 bug 的接縫上：單元、整合、e2e。
2. 對執行中的開發伺服器使用 **Curl / HTTP 腳本**。
3. 用固定輸入進行 **CLI 呼叫**，將 stdout 與已知正確的快照做 diff。
4. **無頭瀏覽器腳本**（Playwright / Puppeteer），驅動 UI 並對 DOM/console/網路做斷言。
5. **重播擷取的追蹤。** 把真實的網路請求 / 承載 / 事件日誌存到磁碟；在隔離狀態下讓它重新走過該程式路徑。
6. **拋棄式測試框架。** 啟動系統的最小子集（一個服務、mock 掉的相依），用單一函式呼叫觸發 bug 的程式路徑。
7. **屬性 / 模糊測試循環。** 如果 bug 是「有時輸出錯誤」，就跑 1000 個隨機輸入並尋找失敗模式。
8. **二分搜尋框架。** 如果 bug 出現在兩個已知狀態之間（commit、資料集、版本），就把「在狀態 X 啟動、檢查、重複」自動化，讓你可以 `git bisect run`。
9. **差異比對循環。** 讓同一個輸入分別通過舊版與新版（或兩種設定），並 diff 輸出。
10. **真人參與（HITL）的 bash 腳本。** 最後手段。如果必須由人點擊，就用 `scripts/hitl-loop.template.sh` 來驅動*他們*，讓循環仍然有結構。擷取的輸出會回饋給你。

建對回饋循環，bug 就已修好 90%。

### 讓循環更緊湊

把循環當成一個產品。一旦你有了*某個*循環，就**收緊**它：

- 能讓它更快嗎？（快取設定、略過無關的初始化、縮小測試範圍。）
- 能讓訊號更銳利嗎？（對特定症狀做斷言，而不是「沒有崩潰」。）
- 能讓它更具決定性嗎？（固定時間、設定亂數種子、隔離檔案系統、凍結網路。）

30 秒又不穩定的循環只比沒有循環好一點點；2 秒且具決定性的循環才叫緊湊，是除錯的超能力。

### 非決定性的 bug

目標不是乾淨的重現，而是**更高的重現率**。把觸發條件循環 100 次、平行化、加壓、縮小時間窗口、注入 sleep。50% 機率出現的 bug 可以除錯；1% 的不行，所以要持續提高重現率直到可以除錯為止。

### 當你真的無法建立循環時

停下來並明確說明。列出你嘗試過的方法。請使用者提供：(a) 能重現它的任何環境的存取權，(b) 遮蔽過的擷取產出物（HAR 檔、日誌傾印、core dump、附時間戳記的螢幕錄影），或 (c) 加入暫時性正式環境插樁的許可。**不要**在沒有循環的情況下就開始提出假設。

### 完成條件：一個會變紅的緊湊循環

當循環**緊湊**且**能變紅**時，第一階段就完成了：你能說出**一個指令**（腳本路徑、測試呼叫、curl），而且你**已經至少執行過一次**（展示呼叫與其輸出，需遮蔽），並且它：

- [ ] **能變紅**：它驅動實際的 bug 程式路徑，並對**使用者所描述的確切症狀**做斷言，因此能在這個 bug 上變紅、修好後變綠。不是「執行時沒出錯」；它必須能*抓到這個特定的 bug*。
- [ ] **具決定性**：每次執行判定都相同（不穩定的 bug：依上述，有固定且高的重現率）。
- [ ] **快速**：幾秒，而不是幾分鐘。
- [ ] **代理可執行**：你可以在無人看管下執行它；真人參與只能透過 `scripts/hitl-loop.template.sh`。

如果你發現自己在這個指令存在之前就在讀程式碼建立理論，**停下來：直接跳到假設，正是本技能要防止的失敗。** 沒有能變紅的指令，就沒有第二階段。

## 第二階段：重現＋最小化

執行循環。看著它在 bug 出現時變紅。

確認：

- [ ] 循環產生的是**使用者**描述的失敗模式，而不是恰好在附近的另一個失敗。錯的 bug = 錯的修正。
- [ ] 失敗在多次執行中都可重現（或者，對於非決定性的 bug，重現率高到足以進行除錯）。
- [ ] 你已擷取確切的症狀（錯誤訊息、錯誤輸出、緩慢的時間），讓後續階段能驗證修正確實解決了它。

### 最小化

一旦變紅，就把重現縮小到**仍會變紅的最小情境**。**一次一個**地刪減輸入、呼叫者、設定、資料與步驟，每次刪減後都重新執行循環，只保留對失敗具關鍵作用的部分。

為什麼要這麼做：最小重現能縮小第三階段的假設空間（剩下更少可疑的活動部件），並成為第五階段乾淨的回歸測試。

當**每個剩下的元素都具關鍵作用**時就完成了：移除其中任何一個都會讓循環變綠。

在完成重現**與**最小化之前不要繼續。

## 第三階段：提出假設

在驗證任何假設之前，先產生 **3–5 個排序過的假設**。只產生單一假設會讓你錨定在第一個看似合理的想法上。

每個假設都必須**可證偽**：說明它所做的預測。

> 格式：「如果 <X> 是原因，那麼 <改變 Y> 會讓 bug 消失 / <改變 Z> 會讓它更嚴重。」

如果你說不出預測，那個假設只是一種感覺：捨棄或把它磨利。

**在驗證之前，把排序清單給使用者看。** 他們常有能立刻重新排序的領域知識（「我們剛部署了跟 #3 有關的變更」），或知道哪些假設已經被排除了。便宜的檢查點，省下大量時間。不要因此卡住；如果使用者不在，就照你的排序繼續。

## 第四階段：插樁

每個探針都必須對應到第三階段的一個特定預測。**一次只改變一個變數。**

工具偏好：

1. 若環境支援，使用**除錯器 / REPL 檢查**。一個中斷點勝過十行日誌。
2. 在能區分假設的邊界上放置**針對性日誌**。
3. 絕不「什麼都記錄然後 grep」。

**為每一行除錯日誌加上標籤**，使用唯一的前綴，例如 `[DEBUG-a4f2]`。最後清理時只需一次 grep。沒加標籤的日誌會殘留；加了標籤的會被清掉。

**效能分支。** 對於效能退化，日誌通常是錯的工具。改為：建立基準量測（計時框架、`performance.now()`、profiler、查詢計畫），然後二分搜尋。先量測，後修正。

## 第五階段：修正＋回歸測試

**在修正之前**先寫回歸測試，但前提是有一個**正確的接縫**可以放它。

正確的接縫是指測試能演練在呼叫點上實際發生的**真實 bug 模式**。如果唯一可用的接縫太淺（bug 需要多個呼叫者時卻只有單一呼叫者的測試、無法複製觸發 bug 之呼叫鏈的單元測試），在那裡寫回歸測試只會帶來虛假的信心。

**如果沒有正確的接縫，這本身就是一項發現。** 記下它。程式碼庫的架構正在阻止這個 bug 被鎖住。為下一階段標記這一點。

如果有正確的接縫：

1. 把最小化的重現轉成該接縫上一個失敗的測試。
2. 看著它失敗。如果你是透過修改程式碼或測試資料來強制它變紅，先與原始副本做 `diff`，證明修改確實生效，再相信它。
3. 套用修正。
4. 看著它通過。
5. 對原始（未最小化的）情境重新執行第一階段的回饋循環。

## 第六階段：清理

宣告完成前必須：

- [ ] 原始重現不再重現（重新執行第一階段的循環）
- [ ] 回歸測試通過（或已記錄缺少接縫的情況）
- [ ] 所有 `[DEBUG-...]` 插樁都已移除（`grep` 該前綴）
- [ ] 拋棄式原型已刪除（或移到明確標示的除錯位置）
- [ ] 最終證實正確的假設已寫在 commit / PR 訊息中，讓下一個除錯者學到經驗
