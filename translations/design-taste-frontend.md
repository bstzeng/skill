# tasteskill v2

由模型建構的頁面，通常看起來像模型見過的所有頁面的平均值：一個置中的標題壓在三行文字上、上面一個小標籤、一排圖示卡片、柔和的漸層、幾條細線和一行等寬字的說明。裡面沒有任何錯，也沒有任何東西是經過決定的。

本技能以四種方式用「決定」取代這些預設值：

1. **由腳本發牌，你從中挑選。** 被要求發明一種外觀時，模型每次都會挑該類別的預設。`scripts/draw.mjs` 從二十個經過研究的方向中發出三個；你挑選那個能承載主題概念的，然後腳本再從一個提煉自 247 個真實網站的資料庫中，發出它的字體系統、配色、主視覺與區塊構圖。
2. **概念來自主題本身。** 在這項研究中，區分最佳網站與平庸網站的，是取自事物本身的概念，而不是樣式。
3. **一套沒有裝飾的設計規範（house style）**，由 `scripts/inspect.mjs` 在真實瀏覽器中量測，讓規則是被檢查的，而不是靠期望的。
4. **你要看你做出來的東西。** 三種寬度的截圖、一份評審量表、修正、再看一次。

測試中學到的一個警告。拿掉裝飾只是工作的一半；一個失去了標籤、細線與卡片、卻沒有在原處得到任何東西的頁面，讀起來會很單薄，而盲測評審理所當然地會偏好一個有破綻但更豐富的頁面，而不是一個沒有破綻但空洞的頁面。另一半是實質內容：更大的字體、整片的色塊、這個主題世界的真實圖片（找來的或畫出來的），以及每個區塊都承載完整的內容。本技能就是為了給你這些而打造的；不要拿它去換克制。

在下面的指令中，`<skill>` 是本技能的資料夾。從專案根目錄執行它們，讓工作檔案落在那裡的 `.taste-skill/`。腳本需要 Node 22+ 以及已安裝的 Chrome、Edge 或 Chromium，且不會安裝任何東西。`assets.mjs` 還需要網路連線；它不使用任何 API 金鑰。

## 頁面還是 App 畫面

先決定這是兩種工作中的哪一種。

- **頁面**是被閱讀與捲動的：landing page、行銷或產品網站、作品集、活動、餐廳、單頁網站。它遵循下方的**流程**。
- **App 畫面**是在其中工作的：儀表板、管理或分析檢視、設定、帳務、要處理的收件匣或佇列、錢包、帶篩選的清單、編輯器或建構器。它遵循 **`references/app-screens.md`**：它自己的流程、它自己的發牌（`draw.mjs --app`）、它自己的規範（安靜的邊框、小標籤與重複的面板在那裡是正常的；漸層、光暈、有色方塊中的圖示、彩虹圖表與捏造的虛榮數字則不是）以及 `inspect.mjs --app`。開始前完整讀完那份檔案；下方的頁面流程不適用。

## 流程

依序執行。步驟 1–5 只需幾分鐘，卻決定了頁面好不好。

### 1. 閱讀需求與專案

找出什麼是真實的：主題、受眾、頁面必須讓人做的那一件事、技術棧、任何既有的品牌（色彩、字型、Logo），以及最重要的——**真正存在哪些影像**：專案自己的照片或產品照、可以展示的真實介面、你可以呼叫的圖片生成工具，或什麼都沒有。不要圍繞著你沒有的圖片做規劃。沒有自己的東西，很少等於什麼都沒有：主題所在的城市、街道、材質與歷史，都在開放的檔案庫與博物館中，只要註明出處就能免費使用（步驟 6，`scripts/assets.mjs`）。

如果請求很模糊，就自己決定，並用一行說明你的理解，而不是發問。只有在缺少的事實阻礙工作時才問（例如沒有產品名稱）。

然後在你的筆記中**盤點主題**：八到十二件屬於這位客戶、而不屬於任何競爭對手的東西。尋找它的名字以及名字的意義；它的地址、門牌號碼、街道與街區，以及那個地方的樣子（它的磁磚、招牌、油漆色彩、店面上的字體、它的光線、它的天氣）；需求中的數字（座位數、房間數、到海邊的分鐘數、價格、年份）；它所處的限制（每月只做一批、冬季休息、預約制）；它的材質與色彩；它的儀式與時刻（五點點燃的烤爐、七點的渡輪）；它的世界中的印刷品（時刻表、標籤、票券、招牌）。這份清單就是步驟 4 中概念的來源。在盲測中，每份需求的勝出頁面，都是由這樣一份清單上的某個項目打造而成的（客戶的名字及其意義、它所在的街道、讓它之所以成為它的那一個限制），而落敗的頁面則是有好的構圖、卻只有類別層級的概念。這份清單也是你的圖片搜尋：上面的每個地點、材質與印刷品，都是步驟 6 的一個查詢。

### 2. 寫出論點

在任何設計之前，把頁面列成主張與其證據，每個區塊一行，就像 `references/copy.md` §1 所示。主張決定存在哪些區塊、以及它們的順序。刪掉任何沒有主張的區塊。這就是你避開「主視覺、Logo 牆、三個功能、推薦語、定價、行動呼籲」這種罐頭順序的方法。

### 3. 抽出方向

這會發出三個方向，並印出每個的簡短摘要。拿每一個對照你的盤點：哪一種構圖方式能承載只有這位客戶才有的東西？選那一個，而不是最熟悉的那個，並在筆記中寫一行說明原因。在測試中，一個不適合主題的隨機方向，是弱頁面最常見的原因。然後發出完整的方向表：

{{CODE:3}}

- `--sector`：`node <skill>/scripts/draw.mjs --list sectors`。挑最接近的。
- `--sections`：取自 `--list roles` 的角色（features、showcase、how-it-works、testimonial、proof、stats、pricing、faq、cta、footer、intro、about、work、gallery、list、contact）。主視覺是隱含的。
- `--tone`（選填）：quiet、bold、warm、technical、playful、luxury、editorial。只有在需求明確要求某種調性時才傳入。
- `--have`：真正存在的素材，以逗號分隔：`photography`（專案自己拍攝的地點、人物或作品照片）、`product-photo`（特定產品的照片，或能產生它們的圖片工具）、`product-ui`（真實截圖）、`illustration`、`video`。如果都沒有就省略：發牌時會避開依賴它們的構圖，而方向表會說明如何誠實地填滿圖片欄位（軟體展示用 HTML 建構的自家介面；沒有照片的產品就畫出來，並放在其世界的真實圖片之中，絕不偽造產品照）。你將在開放館藏中找到的圖片不是專案自己的；不要把它們放進 `--have`。
- `--keep palette,type`：當品牌已經固定了色彩或字體時。發牌就只會發出構圖，由你把品牌的值對應到各角色。

指令會印出一張**方向表**。它就是這次建構的美術指導：

- **採用它。** 不要把它和你本來就會做的版面混在一起。如果它感覺陌生，很好：熟悉的版面正是本技能存在要防止的東西。
- 只有在你能說出理由時才重抽某一格（`--redraw hero | type | palette | photos | scenes | section:<role> | direction`）：它與明確的品牌限制相牴觸、需要一個不存在的素材，或是一個無法容納真實內容的區塊（下一點）。絕不為了得到更舒服的東西而重抽。在報告中記錄每一次重抽。
- 當發出的區塊無法容納真實內容時（它比較三種方案，但只有一個價格；它需要五則引言，但一則都沒有），不要扭曲內容去配合它。用 `--alternatives <role>` 列出其他選項，挑一個假設與內容相符的，並用 `--redraw section:<role>=<id>` 採用它。
- **拿配色對照主題。** 發出的配色既是一組色彩，也是一組比例（一個底色、一個墨色、一個強調色、色塊）。如果它的色彩與主題自身的材質相衝突（泥煤威士忌配糖果粉彩、山屋配霓虹），就重抽一次配色；如果主題有自己毫無疑問的色彩（它的材質、它街道的油漆、它窗外的風景），就保留發出的比例，改從主題取色，並在報告中說明。
- 隨時可用 `node <skill>/scripts/draw.mjs --show` 重新印出。在長時間的 session 中，每建構一個區塊前都重讀一次。

### 4. 找出概念

方向是一種構圖方式。概念則是讓頁面屬於這個主題、而不屬於其他任何主題的東西。在筆記中寫下這句話，在兩個空格都由主題本身填滿之前不要開始建構：

> 在這個頁面上，**[屬於這個主題的某樣東西]** 變成了 **[這個方向所要求的手法]**。

找第一個空格的地方：

- **它的產出。** 這個東西產出什麼？把真實的產出當成材料放到頁面上。（一台會印詩的相機，把它的文案做成紙條呈現。）
- **它的物件或形狀。** 它實際上長什麼樣子，剖面、剪影是什麼樣？放大它、裁切它，讓它成為框架或唯一的母題。
- **它的名字。** 字母能裝進一張照片、堆疊成一面牆、分到兩個角落嗎？
- **它的地點。** 有沒有某個景致會讓人想身在那裡？
- **它的儀式。** 有沒有一段頁面在捲動時可以演出的順序？
- **它的人造物。** 它的世界中已經存在什麼印刷品：票券、菜單、標籤、收據、邀請函、資料夾、手冊？
- **它的反面。** 哪個其他類別擁有這個類別所缺少的感覺？

從你的盤點（步驟 1）而不是從類別填第一個空格。**競爭者測試：** 把最接近的真實競爭者放進這句話（隔兩條街的麵包店、另一家橡木家具製造商、同一座山上的另一間山屋）。如果句子仍然成立，這個概念就屬於類別：一條麵包屬於每一家麵包店；這家店名所取自那條街上的七扇門，則只屬於這一家。「乾淨又現代」不是概念。研究評審團評分最低的網站，正是那些概念被記錄為「除了標準公式之外什麼都沒有」的網站。

**一個活的東西。** 給頁面一個訪客可以操作、或每次造訪都不同的東西，並由概念打造：選一種木材，看椅子用它做出來的樣子；輸入你的名字，看它用鑄字廠的字母刻出來；設定貸款，讀出真實的每月金額；看看山屋的爐子現在有沒有點著、離最後一班渡輪還有多久；選一個尺寸，看它放在房間裡的樣子。在盲測中，每個勝出的頁面都有一個，而評審第一個提到的就是它。規則：它使用主題的真實內容、能用拇指在手機上操作、在沒有腳本時有平實的備案、絕不妨礙閱讀，而且它是一件事，不是一座遊樂場。它在步驟 6 作為頁面的一部分建構，而不是在步驟 9 作為動態效果加上去。

**場景也承載概念。** 方向表上的捲動場景，是等待主題的手法。在建構之前，從你的盤點決定每個場景要呈現什麼：穿越飛行經過的是這間工作室自己的片頭卡，路線是這批貨物真正走的那條路，展開到全螢幕的那張圖片是客人將醒來的房間。填滿了任何人都能用的圖片的場景，就只是螢幕保護程式。

### 5. 寫出文字

在寫標記之前，依照 `references/copy.md`，把整個頁面寫成一份文案稿（純文字）：

- **每個標題在每種寬度下都不超過兩行。** 在確定一個句子之前，先做 copy.md §2 中的計算：以有自信的大小來說，大約 32 個字元在任何地方都是安全的。研究的藝廊主視覺，中位數是 5 個英文單字、32 個字元。
- 一句輔助句，直接放在標題下方（距離 32–48px）並與它一起顯示，絕不擺在第一屏的底部或被動畫延遲顯示。當標題是一個名字或一種修辭時，這句話要平實地說明這個東西是什麼。一個主要動作，以它的作用命名，在第一屏上作為真正的按鈕。
- **第一屏以大字回答訪客的第一個問題。** 對於活動：它是什麼、何時何地（日期屬於標題或第二大的字級，絕不只出現在小字中）。對於產品：它是什麼、多少錢或能做什麼。對於個人：是誰、做什麼。訪客為之而來的每個區塊（陣容、菜單、房間、價格）都有自己的標題，以及在導覽中自己的位置。
- **寫出完整的內容。** 需求要求的每個區塊都要完整傳達其資訊：附價格的完整菜單、每個房間各自的細節、每位講者與每場演講、價格以及它包含什麼、每個真實問題的答案。單薄的區塊，是乾淨的頁面輸給較繁複頁面最常見的原因。
- 在需求留有空白之處，預期要放範例細節（菜名、房型名稱與價格、專案標題），讓設計以完整的密度呈現；在報告中列出它們，請客戶確認。證據絕不捏造：沒有客戶、引言、評論、媒體報導、Logo 或營業統計。

### 6. 靜態地建構

建構頁面時，在腦中把動態效果關掉；需要動畫才看起來完成的頁面，並沒有完成。工作順序：

1. **Token。** 把方向表中的色彩與字體角色設為 CSS 自訂屬性。下游的一切都只引用 token。`<skill>/assets/base.css` 是一個你可以從它開始的中性基礎（重設、token 名稱、流體字級、網格、焦點與選取樣式、動態輔助工具）；它本身沒有任何外觀。
2. **主視覺，完全照藍圖描述**，在桌面與手機寬度下都要。在其他任何東西存在之前，先讓大的東西夠大、小的東西夠小。
3. **每個區塊都依其藍圖**，搭配這個專案的內容。保留幾何結構，更換主題。相鄰的區塊不得共用版面。**把概念帶進每一個區塊**，包括定價、FAQ 與頁尾：研究中最常見的失敗，即使在好網站中也一樣，是有辨識度的第一屏之後接著罐頭區塊。
4. **影像**，依此偏好順序：
   1. 專案自己的；
   2. 生成的，如果你有圖片工具；
   3. **開放館藏中主題世界的真實圖片**，只要存在誠實的那種。用 `node <skill>/scripts/assets.mjs "<query>"` 搜尋（Openverse、Wikimedia Commons、芝加哥藝術博物館與大都會博物館；預設只用允許商業使用的授權）。搜尋你的盤點，而不是類別：老明信片中它的街道、街區的古地圖、它材質的特寫、版畫中的它的行業、同類的博物館藏品、植物圖版、星圖。大尺寸且有意圖地使用它們：一張檔案照片作為主視覺、一幅版畫放大成頁面的母題、真實的街道地圖作為聯絡區塊。選擇之前先看過每一張；`--get <ref>` 會把它下載到 `assets/` 並記錄其來源與授權，`--credits` 會印出頁尾用的出處行。找來的圖片呈現的是客戶周圍的世界，絕不被呈現為客戶自己的產品、房間、菜餚、人物或團隊；
   4. **以程式碼從主題本身畫出來**，用於不存在誠實圖片的東西（它的物件、它的磁磚、它的窗戶、它產品的介面，以配色的真實色彩做成一致的扁平圖形語言）；
   5. 方向表上發出的照片，只用在誠實的通用圖片合適之處（海邊小屋用大海），絕不作為主題的替身；
   6. 只用字體與色彩。

   當專案有自己的流程或產品的影片或真實圖片時，第一屏要大尺寸地展示它（大約螢幕的 40% 或更多）。絕不在頁面上寫一句話說明圖片從哪裡來或它們不是什麼（「這些都不是我們的酒吧」）：圖說說明圖片是什麼，出處行小小地放在頁尾。作品集中為需求而虛構的作品，每件都畫成該作品完成後的一張靜態畫面（帶有自己字體的片頭卡、片尾影格、海報），帶有真實的細節，絕不畫成客戶產品的圖示。

   **底線（檢查器會檢查）：** 頁面上至少四張真實圖片，通常六到十二張（照片、檔案影像、地圖、版畫、影片、點陣藝術作品；對於軟體，其裁切後的介面片段也算）。SVG 繪圖不計入底線：畫出不存在圖片的東西，但仍要帶有真實圖片。只要存在誠實的片段，就加入一個動態畫面：用 `assets.mjs --video "<query>"` 搜尋，並作為帶封面影格的靜音循環使用。模型會略過圖片與影片，因為找它們是件工作；沒有它們，頁面就會失敗。

   `references/imagery.md` 涵蓋搜尋、授權與出處、影片、繪圖、裁切與處理。
5. **活的東西**，來自步驟 4，建構在它能證明主張的區塊中（通常是主視覺或預訂），使用真實內容、拇指大小的手機版本與平實的備案。
6. **捲動場景**，當方向表發出它們時（第 9 節），每個都搭配它所承載的區塊：頁面的重大時刻、穿越作品飛行的攝影機、展開到全螢幕的圖片、在捲動下扭曲的文字。從 `<skill>/assets/scenes/` 複製共用的舞台與場景的檔案，用這個專案自己的圖片與文字填滿場景，並設定頁面的 token 讓它採用頁面的外觀。場景是構圖：它決定頁面多長、每一屏呈現什麼，所以現在就建構，並在每一輪檢視中都看到它，而不是在最後才加上去。`references/scenes.md` 說明如何把場景放到頁面上、填滿它、調整它與檢查它；`assets/scenes/demo/<id>.html` 是每一個場景的可運作範例。
7. **飽滿度。** 把每一個桌面螢幕當成一張海報來看：一個主導的東西，以及它所承載的內容。大部分是空白底色的螢幕，是建構不足的區塊，而不是留白；每頁一處刻意的留白是上限，而有兩個或以上近乎空白之螢幕的頁面，檢查器會判定失敗。內文使用完整的墨色、16px 或更大；灰色用於次要的註記。
8. **框架。** 頁面在每種寬度下都有一組相等的外邊距，每個區塊都使用頁面所設定的寬度：當文字位於左半邊時，右半邊要放它的圖片、第二欄、清單或圖表，絕不是空無一物。不對稱存在於網格之內，絕不在框架上：只有當遠端有東西將它收合時，才放置空白。頁面上沒有任何一段高於約半個螢幕的範圍是完全空的；桌面上區塊間距為 120–240px。訪客為之而來的每個區塊，都以一個為它命名的標題開場，而第一屏以 `h1` 承載頁面的標題。這些是讀者在頁面看起來不對時最先指出的東西（「沒有清楚的標題」「莫名其妙的空白」「全部都被擠到一邊」），而檢查器會量測每一項。
9. **狀態與語意。** 真正的連結與按鈕、可見的焦點、替代文字、本身就是一種構圖的手機版面。每個控制項，包括活的東西，都能只用鍵盤依閱讀順序操作，並有無障礙名稱：它可見的標籤，或在只顯示圖示時使用 `aria-label`。

當你需要某個決定背後的細節時，閱讀 `references/type.md`、`references/colour.md` 與 `references/layout.md`；下方的法則是簡短版。

### 7. 關卡

{{CODE:4}}

`scenes.mjs` 會在桌面與手機上，以及減少動態的頁面中，為每個捲動場景在其停留的 0、10 … 100% 處拍照；當方向表上有場景時，`inspect.mjs` 也會拍下整段捲動（`desktop-film-NN.jpg`）。一個從未啟動、或在桌面上靜止不動的場景，判定為 `FAIL`。

`lint.mjs` 掃描原始碼中被禁止的模式與罐頭用語。`inspect.mjs` 在真實瀏覽器中以 1440、768 與 390 像素開啟頁面並量測它（標題行數、字級大小、實際載入的字型、色彩、線條、陰影、漸層、對比、溢出，以及框架：相等的邊距、擠在一邊的區塊、空白段落、標題、沒有標題的區塊、貼著螢幕邊緣的文字），並把截圖存到 `.taste-skill/inspect/`。修正每一個 `FAIL`。把每個 `WARN` 都視為錯誤，除非你能用一句話向設計師辯護它。重新執行直到沒有 `FAIL` 為止。不要和量測工具爭論，也不要把東西藏起來不讓它看到。檢查器透過一個拋棄式本機伺服器提供本機檔案；如果頁面也必須能直接從檔案系統開啟，在完成之前以那種方式開啟一次 `index.html`。

檢查訪客實際收到的東西。如果有建置步驟，最後一道關卡要在正式建置上執行（`vite build && vite preview`、`next build && next start`，或建置後的 `index.html`），而不只是在開發伺服器上：壓縮器與打包器會改變交付的內容（曾有一個拿掉了開發伺服器上有顯示的 `backdrop-filter`）。當檢查器看的是開發伺服器時，它會發出警告。

### 8. 看

通過關卡代表沒有量測到被禁止的東西。這並不代表頁面是好的。開啟檢查器列出的截圖（每一種視窗大小，用你的圖片檢視器或 Read 工具），並以 `references/critique.md` 評論它們：十四輪檢視、以 Awwwards 加權的分數、上限。依其格式寫下評論，修正前三大問題，再次執行檢查器，再看一次。最多三輪。

只根據圖片判斷。如果問題在截圖中看得到，它就是真的，不管程式碼怎麼說。

### 9. 動起來

現在建構動態層。它是必要的，而且不只是一個淡入：檢查器會計算頁面在載入與捲動時真正移動的元素數量，少於八個就判定失敗（少於十六個會警告）。任何捲動場景都已經建構好了（步驟 6）；在它們周圍，動態層有四個部分：

1. **招牌動作**，方向表上有指名：一個，做好（發出的場景可以就是它）。
2. **每個區塊各部分的進場：** 標題、然後文字、然後圖片，間隔 60–90ms 錯開，以不透明度上升 16–32px，在區塊進入時觸發一次。不是整塊一個淡入，也絕不能在腳本失敗時讓內容保持隱藏。
3. **每個控制項的回饋：** 按鈕、連結、卡片與活的東西上的按下、懸停與焦點。
4. **一個動態畫面：** 一段找來的片段作為靜音循環、照片上緩慢的縮放或漂移，或主視覺圖片上與捲動連動的移動。

只用 transform 與 opacity；每個動作都有 `prefers-reduced-motion` 備案，保留內容、拿掉位移。改變整個螢幕色彩或版面的動作（依章節變色、釘選的故事）是構圖的一部分，所以在步驟 6 建構它，讓每一輪檢視都看得到。`references/motion.md` 有 token 與經過測試的做法。然後再執行一次檢查器，並檢查每張截圖中是否有內容沒有出現。

### 10. 報告

在以下所有條件都成立之前不要報告；每一項都曾在一次結果很糟的測試執行中被略過：

- `inspect.mjs` 在頁面的最終版本上，於 1440、768 與 390 都顯示 **0 FAIL**。
- 你在最後一次修改之後，開啟了它列出的每一張截圖，而不只是第一屏。
- 有捲動場景時：`scenes.mjs` 在最終頁面上執行且沒有問題，而你讀了每一張表（桌面、手機、減少動態）。
- 一個陌生人看第一屏五秒鐘，就能說出這是什麼、該做什麼。
- 每個區塊都有標題；兩側邊距相符；頁面上沒有任何一段是空的。
- 你最後一輪的評論已依 `references/critique.md` §4 的形式寫下。

簡短地告訴使用者：發出的方向（名稱與種子）以及任何重抽與其原因；概念句與活的東西；你最後一輪評論的最終分數，以及仍有不足之處；每一張找來的圖片與片段，附其標題、創作者、授權與來源頁面（`assets.mjs --credits` 會印出清單），以及其出處在頁面上的位置；哪些內附照片與哪些繪圖是用來代替攝影的（以便替換）；以及任何上線前必須替換的範例內容。不要宣稱你沒有執行過的檢查。

## 設計規範（House rules）

無論方向為何，這些在每次建構中都成立。`inspect.mjs` 會量測它們。

| 規則 | 改為 |
| --- | --- |
| **標題：在每種寬度下都不超過兩行。** 每個 `h1`–`h6`，以及第一屏的主要文字（不論其標籤為何）。 | 刪字。然後加寬行長。最後才調大小。 |
| **第一屏要有清楚的標題**，放在頁面唯一的 `h1` 中，且每個區塊都有標題。 | 說明這是什麼：名稱加上它做什麼、產品加上它的用途、活動加上日期與地點。 |
| **外邊距相等；沒有擠在一邊的區塊**而另一半螢幕是空的。 | 用遠端的某樣東西收合每一處空白：區塊的圖片、第二欄、清單、圖表。 |
| **沒有空白段落**高於約半個螢幕。 | 正常的區塊間距。刻意的留白是一張擺放好的圖片或一片色塊，每頁一次。 |
| **陳述是段落。** 以大字排版的引言句或引文，標記為 `<p>` 或 `<blockquote>`，維持陳述的大小（桌面 36px 以下、手機 24px），長度約 25 個英文單字、三行。 | 比那更大就是標題，適用兩行規則。在盲測中，評審把一個跨四行的 42px 句子讀成四行的標題。 |
| **沒有眉標。** 標題上方沒有小標籤、主標題上方沒有膠囊徽章、沒有「New ·」小標。 | 把資訊放進標題或第一句，或者拿掉它。 |
| **真正的程式碼區塊以外不用等寬字。** | 內文字體。數字需要對齊處用表格數字。 |
| **沒有索引編號。** 沒有 01 / 02 / 03、沒有 (001)、沒有「步驟 2」。 | 以位置、大小或文字呈現順序。如果順序重要，用真正的 `<ol>`。 |
| **沒有細線。** 沒有髮絲般的分隔線、沒有 1px 外框盒、沒有網格線、十字準線或裁切標記。 | 空間。背景色調的一階變化。尺度的改變。一個實心的形狀。 |
| **沒有漸層。** 背景不用、按鈕不用、文字也不用。 | 平塗色彩，或真實的照片。照片上文字下方的中性遮罩是唯一例外。 |
| **靜止的東西沒有陰影。** 沒有光暈。 | 表面之間的一階色調差。只有真正浮起的東西才有陰影：選單、對話框。 |
| **沒有 AI 助理配色。** 沒有淡黃奶油底配陶土色或鏽色；沒有紫羅蘭或靛藍。 | 發出的配色。 |
| **沒有微小的大寫字距加寬標籤。** | 以可讀的大小、句首大寫書寫。 |
| **沒有頂部帶圖示的功能卡片，沒有一排相同的卡片。** | 發出的區塊藍圖。 |
| **沒有玻璃擬態。** 沒有背景模糊面板、沒有浮動膠囊導覽。 | 一條平實的列：字標、幾個連結、一個動作。 |
| **沒有 emoji、沒有漸層色團、沒有裝飾性形狀、沒有灰色長條的假儀表板。** | 一張真實的圖片、一個真實的介面片段，或者什麼都沒有。 |
| **標題中沒有特別樣式的強調字**（斜體、襯線、上色、底線）。 | 一種字體、一種顏色。由文字本身承載強調。 |
| **最多兩種字體，**通常一種。 | 發出的字體系統。 |

有三處保有它們自己的慣例，檢查器不會干涉：`<pre>`/`<code>` 中的真正程式碼（等寬字在那裡是正確的）、真正的表格與表單欄位（它們可以有線條），以及根元素帶有 `data-ui` 屬性的真實介面片段（產品自己的邊框與選單；見 `references/imagery.md` §7）。

老實說，為什麼是這些。有些是研究量測到的：在 247 個網站中，評審團評分 7.5 以上的網站使用圖示功能卡片的比例是 1%，而 6.5 以下的網站是 28%；膠囊徽章 14% 對 34%；漸層 22% 對 52%；陰影 24% 對 48%；微小字距大寫 16% 對 57%。另一些則是作者的品味，與目前的藝廊流行相反：等寬字標籤、索引編號與髮絲網格，在得獎網站上其實比在弱網站上*更*常見，這正是生成器模仿它們的原因，也是它們現在讀起來像戲服的原因。它們在這裡一律禁止，沒有例外。`references/tells.md` 保有附日期的登記清單。

拿掉裝飾會留下空間。絕不要用另一種裝飾填滿它。用尺度（讓主要的東西更大）、用完整的內容、用為這個主題製作的圖片，或用一片平塗色彩填滿它。每頁最多刻意留白一次。

## 工藝法則

簡短版。數字除非標示為設計規範，否則都來自研究。

**字體**
- 兩到三種大小承擔可見的工作：一個非常大、一個小，中間什麼都沒有。研究網站的標題與內文比例中位數為 4.3；最好的遠遠超過（最大字級：頂尖網站中位數 8.4vw，弱網站 5.0vw）。
- 展示字體：字距 -0.02 到 -0.05em，行高 0.85–1.05。內文：16–20px，行高 1.45–1.6，每行 45–75 個字元。
- 一頁五種大小是上限。一個字體家族是常態（研究網站的三分之一）；兩個是上限。
- 預設靠左對齊。最多一處置中。

**空間**
- 一套網格、一組緊湊的邊距（16–32px），處處使用；大的東西延伸到邊緣。整個頁面上的文字區塊共用兩到三條左緣。
- 不對稱在網格之內，絕不在框架上：兩側外邊距相等，偏離中心的標題由網格遠端的某樣東西回應。
- 區塊之間的間距明顯大於區塊內部的任何間距：桌面 120–240px（研究的中位數約 240）。
- 每個區塊的構圖都與相鄰區塊不同；沒有一個是卡片網格。

**色彩**
- 一個底色、一個墨色、一個強調色。強調色出現在動作上，或許再加一樣東西。
- 內文使用完整的墨色。以淡灰排版的頁面讀起來像未完成。
- 表面以小小的一階色調區隔，絕不用線條或陰影。
- 一個區塊可以改變整片底色。沒有東西會漸變成任何東西。

**影像**
- 一張主導的圖片勝過六張小圖。在評分最高的網站中，主視覺媒體有 68% 的時間覆蓋第一屏至少一半。
- 相同的裁切比例、相同的處理、直角，除非方向另有指示（73% 的研究網站讓媒體保持直角）。
- 沒有圖片勝過占位圖、圖示或抽象形狀。用心以其色彩為這個主題畫出的圖片，比兩者都好。找來並註明出處的它的世界的真實圖片，又更好。
- 每一張找來的圖片都下載進專案、在頁面上註明出處，並列在報告中。沒有一張被呈現為客戶自己的。
- 絕不讓任何東西疊在標題或陳述上方（檢查器會判定失敗）。

**元件**
- 按鈕：扁平、單一填色，要嘛直角、要嘛全圓，一次決定（頂尖網站：52% 直角、23% 膠囊；9–16px 的「柔和」圓角是弱網站的預設）。大多數強而有力的主視覺完全沒有按鈕，或只有一個。
- 導覽：字標、三到五個平實的連結、一個動作。沒有導覽列外框。
- 控制項以它的形式、標籤與位置說明如何使用它。當它似乎需要一句話說明如何操作時，重新設計控制項，而不是加上那句話。欄位接受什麼則是另一回事。先在能做到的地方移除限制：日期選擇器，或能接受任何常見格式的解析器。仍然存在的限制，例如密碼規則或檔案類型與大小，要在欄位旁保持可見，並以 `aria-describedby` 與其連結。
- 頁尾是經過設計的收尾，而不是網站地圖：在大多數強網站上，名稱會以全寬回歸。

## 特殊情況

**既有的品牌或設計系統。** 傳入 `--keep palette,type`，把品牌的色彩與字體對應到各角色，只從發牌中取用構圖。設計規範仍然適用；如果品牌本身要求某個被禁止的手法（它的 Logo 放在漸層中、它的強調色是紫羅蘭），就保留品牌素材，在報告中說明，並只針對那條規則對檢查器傳入 `--allow <rule>`。

**既有頁面或 App 畫面的重新設計、改造風格或審查。**

1. **記錄改造前。** 照原樣執行專案，並把它檢查到它自己的資料夾（`inspect.mjs <url> --out .taste-skill/before`，App 畫面加上 `--app`），並 lint 其原始碼。閱讀程式碼：框架、樣式方法（Tailwind v3 或 v4、CSS modules、styled-components、純 CSS）、元件，以及必須保留的東西：路由、表單、資料、行為、品牌自己的素材。
2. **審查到此為止。** 以 `references/critique.md` 評論改造前的截圖，搭配檢查器的量測列出發現，並指出最能改善頁面的三項變更。
3. **保留技術棧、內容與有效的部分。** 不遷移框架或樣式函式庫；加入任何東西之前先檢查相依檔。改造風格會保留版面，並從發出的方向取用字體、色彩與元件（品牌固定的部分用 `--keep`）；重新設計則發出完整的方向，並在既有元件內依其藍圖重建區塊。無論哪種，都用頁面的真實內容從流程的步驟 2 開始。
4. **工作順序，以最小風險換取最大效果：** 字體（字型與尺度）、色彩（一個底色、一個墨色、一個強調色）、框架（邊距、區塊節奏、第一屏的標題與每個區塊的標題）、狀態（懸停、焦點、載入、空白、錯誤），然後把罐頭元件（圖示卡片、膠囊徽章、漸層色團、卡片網格）替換成發出的藍圖。
5. **證明它。** 再次檢查到 `.taste-skill/after`，在每種寬度下比較前後，點過先前可運作的每個連結、表單與選單，並把前後的量測並排報告。

**一個元件或單一區塊，而不是整頁。** 除非沒有方向可以遵循，否則略過發牌。配合周圍的設計，套用設計規範與法則，並仍然檢查結果。

**沒有結帳、沒有表單後端。** 當需求指名了真實目的地時，主要按鈕就導向它。否則它會開啟一封帶有寫好主旨與內文的電子郵件（填入訪客選擇的 `mailto:`），或者，對於商店，它指向 `#checkout`，並在報告中說明上線前必須接上。絕不偽造付款表單。

**沒有 Chrome 或 Node 22。** 執行 `lint.mjs`（Node 18+），用你手邊的任何瀏覽器工具截圖，並評論那些截圖。在報告中說明檢查器無法執行。

**沒有網路。** 如果 `assets.mjs` 連不到任何來源，就畫出圖片，並在報告中說明無法搜尋開放館藏。
