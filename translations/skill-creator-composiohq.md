# 技能建立器

本技能提供建立有效技能的指引。

## 關於技能

技能是模組化、自足的套件，透過提供專門的知識、工作流程與工具來擴充 Claude 的能力。把它們想成特定領域或任務的「新手上路指南」——它們把 Claude 從通用代理，轉變成具備程序性知識的專門代理，而這些知識是任何模型都無法完全擁有的。

### 技能提供什麼

1. 專門的工作流程 —— 特定領域的多步驟程序
2. 工具整合 —— 處理特定檔案格式或 API 的指示
3. 領域專業 —— 公司專屬的知識、結構、商業邏輯
4. 內附資源 —— 用於複雜與重複任務的腳本、參考資料與素材

每個技能都由一個必要的 SKILL.md 檔案與選用的內附資源組成：

#### SKILL.md（必要）

**中繼資料品質：** YAML frontmatter 中的 `name` 與 `description` 決定 Claude 何時會使用這個技能。具體說明技能做什麼、何時使用。使用第三人稱（例如「當……時應使用本技能」，而不是「當……時使用這個技能」）。

#### 內附資源（選用）

##### 腳本（`scripts/`）

用於需要確定性可靠度或會被一再重寫之任務的可執行程式碼（Python/Bash 等）。

- **何時納入**：當同樣的程式碼一再被重寫，或需要確定性的可靠度時
- **範例**：用於 PDF 旋轉任務的 `scripts/rotate_pdf.py`
- **好處**：節省 token、具確定性，可以在不載入上下文的情況下執行
- **注意**：Claude 仍可能需要讀取腳本以進行修補或針對環境的調整

##### 參考資料（`references/`）

需要時才載入上下文、用來引導 Claude 流程與思考的文件與參考資料。

- **何時納入**：Claude 工作時應該參考的文件
- **範例**：財務結構的 `references/finance.md`、公司 NDA 範本的 `references/mnda.md`、公司政策的 `references/policies.md`、API 規格的 `references/api_docs.md`
- **使用情境**：資料庫結構、API 文件、領域知識、公司政策、詳細的工作流程指南
- **好處**：讓 SKILL.md 保持精簡，只在 Claude 判斷需要時才載入
- **最佳實務**：如果檔案很大（>1 萬字），在 SKILL.md 中附上 grep 搜尋模式
- **避免重複**：資訊應該只存在於 SKILL.md 或參考檔案其中之一，不要兩者都有。除非真的是技能的核心，否則詳細資訊偏好放在參考檔案——這讓 SKILL.md 保持精簡，同時讓資訊容易被找到而不占用上下文視窗。SKILL.md 只保留必要的程序性指示與工作流程指引；把詳細的參考資料、結構與範例移到參考檔案。

##### 素材（`assets/`）

不打算載入上下文、而是在 Claude 產出的輸出中使用的檔案。

- **何時納入**：當技能需要會在最終輸出中使用的檔案時
- **範例**：品牌素材 `assets/logo.png`、PowerPoint 範本 `assets/slides.pptx`、HTML/React 樣板 `assets/frontend-template/`、字型 `assets/font.ttf`
- **使用情境**：會被複製或修改的範本、圖片、圖示、樣板程式碼、字型、範例文件
- **好處**：把輸出資源與文件分開，讓 Claude 不必把檔案載入上下文就能使用

### 漸進式揭露的設計原則

技能使用三層載入系統來有效率地管理上下文：

1. **中繼資料（name + description）** —— 永遠在上下文中（約 100 字）
2. **SKILL.md 內文** —— 技能觸發時（<5 千字）
3. **內附資源** —— Claude 需要時（無限制*）

*無限制是因為腳本可以在不讀入上下文視窗的情況下執行。

## 技能建立流程

要建立技能，依序遵循「技能建立流程」，只有在有明確理由說明某步驟不適用時才跳過。

### 步驟 1：以具體範例理解技能

只有在技能的使用模式已經被清楚理解時才跳過這一步。即使是處理既有的技能，這一步仍然有價值。

要建立有效的技能，就要清楚理解技能將如何被使用的具體範例。這種理解可以來自使用者直接提供的範例，或經使用者回饋驗證過的產生範例。

例如，在建立圖片編輯技能時，相關的問題包括：

- 「圖片編輯技能應該支援哪些功能？編輯、旋轉，還有其他的嗎？」
- 「可以舉幾個這個技能會怎麼被使用的例子嗎？」
- 「我可以想像使用者會要求像『移除這張圖的紅眼』或『旋轉這張圖』這類的事。你還想像得到這個技能有其他的使用方式嗎？」
- 「使用者說什麼話時應該觸發這個技能？」

為了避免讓使用者應接不暇，避免在單一訊息中問太多問題。從最重要的問題開始，需要時再追問，效果更好。

當你對技能應該支援的功能有清楚的概念時，就結束這一步。

### 步驟 2：規劃可重用的技能內容

要把具體範例轉成有效的技能，對每個範例進行分析：

1. 考慮如何從零開始執行這個範例
2. 找出在反覆執行這些工作流程時，哪些腳本、參考資料與素材會有幫助

範例：建立 `pdf-editor` 技能來處理像「幫我旋轉這個 PDF」的請求時，分析顯示：

1. 旋轉 PDF 每次都需要重寫同樣的程式碼
2. 在技能中存放一個 `scripts/rotate_pdf.py` 腳本會有幫助

範例：設計 `frontend-webapp-builder` 技能來處理像「幫我做一個待辦事項 App」或「幫我做一個追蹤步數的儀表板」的請求時，分析顯示：

1. 撰寫前端網頁應用每次都需要同樣的 HTML/React 樣板
2. 在技能中存放一個包含樣板 HTML/React 專案檔的 `assets/hello-world/` 範本會有幫助

範例：建立 `big-query` 技能來處理像「今天有多少使用者登入？」的請求時，分析顯示：

1. 查詢 BigQuery 每次都需要重新探索資料表的結構與關聯
2. 在技能中存放一個記錄資料表結構的 `references/schema.md` 檔案會有幫助

要確立技能的內容，分析每個具體範例，建立要納入的可重用資源清單：腳本、參考資料與素材。

### 步驟 3：初始化技能

到了這個時候，就該實際建立技能了。

只有在要開發的技能已經存在、需要的是迭代或打包時，才跳過這一步。這種情況下，繼續下一步。

### 步驟 4：編輯技能

編輯（新產生的或既有的）技能時，記住這個技能是要給另一個 Claude 實例使用的。聚焦於納入對 Claude 有益且不顯而易見的資訊。考慮哪些程序性知識、領域專屬的細節或可重用的素材，能幫助另一個 Claude 實例更有效地執行這些任務。

#### 從可重用的技能內容開始

開始實作時，從上面找出的可重用資源開始：`scripts/`、`references/` 與 `assets/` 檔案。注意這一步可能需要使用者的輸入。例如，實作 `brand-guidelines` 技能時，使用者可能需要提供品牌素材或範本存放在 `assets/`，或提供文件存放在 `references/`。

此外，刪除技能不需要的範例檔案與目錄。初始化腳本會在 `scripts/`、`references/` 與 `assets/` 中建立範例檔案來示範結構，但大多數技能不會全部都需要。

#### 更新 SKILL.md

**寫作風格：** 整個技能使用 **祈使／不定詞形式**（以動詞開頭的指示）撰寫，而不是第二人稱。使用客觀、指示性的語言（例如「要完成 X，做 Y」，而不是「你應該做 X」或「如果你需要做 X」）。這能為 AI 的使用維持一致與清晰。

要完成 SKILL.md，回答以下問題：

1. 用幾句話說明，這個技能的目的是什麼？
2. 什麼時候應該使用這個技能？
3. 實務上，Claude 應該如何使用這個技能？上面開發的所有可重用技能內容都應該被參照，讓 Claude 知道如何使用它們。

2. 驗證通過後 **打包** 技能，建立一個以技能命名的 zip 檔（例如 `my-skill.zip`），包含所有檔案並維持適合分發的目錄結構。

### 步驟 6：迭代

測試技能之後，使用者可能會要求改善。這通常發生在剛使用完技能、對技能的表現記憶猶新的時候。

**迭代工作流程：**
1. 在真實的任務上使用技能
2. 注意到困難或沒效率的地方
3. 找出 SKILL.md 或內附資源應該如何更新
4. 實作變更並再次測試
