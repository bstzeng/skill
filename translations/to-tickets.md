# 拆成工單（To Tickets）

把計畫、規格或對話拆成一組**工單**：曳光彈式的垂直切片，每張都宣告**阻擋**它的工單。

issue 追蹤系統與分類標籤用語應該已經提供給你了。如果沒有，請使用者執行 `/setup-matt-pocock-skills`。

## 流程

### 1. 蒐集脈絡

從對話脈絡中已有的內容著手。如果使用者以參數傳入參照（規格路徑、issue 編號或 URL），就抓取它並閱讀完整內文與留言。

### 2. 探索程式碼庫（選用）

如果你還沒探索過程式碼庫，就去探索，以了解程式碼的現況。工單標題與描述應使用專案領域詞彙表的用語，並尊重你所碰觸區域的 ADR。

尋找可以先行重構（prefactor）、讓實作更容易的機會。「先讓變更變得容易，再做那個容易的變更。」

### 3. 草擬垂直切片

把工作拆成**曳光彈**工單。

<vertical-slice-rules>

- 每個切片貫穿每一層（schema、API、UI、測試），形成一條窄但「完整」的路徑：是垂直的，「不是」某一層的水平切片
- 完成的切片本身就能展示或驗證
- 每個切片的大小都能放進單一個全新的上下文視窗
- 任何先行重構都要先做

</vertical-slice-rules>

為每張工單標上**阻擋邊**：必須先完成、它才能開始的其他工單。沒有阻擋者的工單可以立刻開始。

**大範圍重構是垂直切片的例外。** **大範圍重構**是一個機械式的變更（重新命名欄位、更改共用符號的型別），其**影響半徑**遍及整個程式碼庫，所以一次編輯就會同時弄壞上千個呼叫點，沒有任何垂直切片能以全綠的狀態落地。不要硬把它塞進曳光彈；改以**擴張—收縮**的順序進行。先擴張：在舊形式旁邊加入新形式，讓什麼都不會壞。然後依影響半徑分批（依套件、依目錄）把呼叫點遷移過去，每批都是一張被擴張工單阻擋的工單，因為舊形式仍在，所以每批之間 CI 都保持全綠。最後收縮：在沒有任何呼叫者之後刪除舊形式，這張工單被每一批遷移工單阻擋。當連批次都無法各自保持全綠時，保留這個順序，但讓它們共用一個整合分支，全部阻擋最後一張整合與驗證工單；只有在那裡才保證全綠。

### 4. 向使用者確認

把提議的拆分以編號清單呈現。每張工單顯示：

- **標題**：簡短的描述性名稱
- **被阻擋於**：哪些其他工單（如果有）必須先完成
- **交付什麼**：這張工單讓哪個端到端行為能運作

詢問使用者：

- 粒度感覺對嗎？（太粗／太細）
- 阻擋邊正確嗎：每張工單是否只依賴真正卡住它的工單？
- 有沒有工單應該合併或進一步拆分？

反覆調整，直到使用者核准這個拆分。

### 5. 把工單發布到設定好的追蹤系統

發布核准的工單。**如何**發布取決於 `/setup-matt-pocock-skills` 設定的追蹤系統；工單本身在兩種情況下都一樣，只有阻擋邊的形式不同：

- **本機檔案** → 每張工單寫一個檔案，放在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md`，依相依順序（阻擋者優先）從 `01` 開始編號。每個檔案的「被阻擋於」列出它所依賴的編號/標題。使用下方的單張工單檔案模板：一個檔案一張工單，絕不合併成單一檔案。
- **真正的 issue 追蹤系統（GitHub、Linear……）** → 依相依順序（阻擋者優先）為每張工單發布一個 issue，讓每張工單的阻擋邊能引用真實的識別碼。平台有原生阻擋關係時就用它；否則把每張工單的「被阻擋於」設為阻擋它的 issue。如果來源是既有的 issue，就把每張工單設為它的子 issue（追蹤系統文件中的操作）。除非另有指示，否則套用 `ready-for-agent` 分類標籤；這些工單在設計上就是代理可以直接接手的。

處理**前沿**：所有阻擋者都已完成的工單。對於純線性的鏈，就是由上而下。

**不要**關閉或修改任何父 issue。
