# 領域建模（Domain Modeling）

在設計的同時，主動建立並磨利專案的領域模型。這是一門「主動」的紀律：挑戰用詞、發明邊界情境，並在詞彙表與決策成形的那一刻就寫下來。（單純「讀」`GLOSSARY.md` 取得詞彙不屬於本技能：那是任何技能都能做的一行習慣。本技能是用在你要「改變」模型、而不只是使用它的時候。）

## Session 進行中

### 對照詞彙表提出質疑

當使用者使用的術語與 `GLOSSARY.md` 既有用語衝突時，立刻指出來。「你的詞彙表把『取消』定義為 X，但你似乎指的是 Y。到底是哪個？」

### 磨利模糊的用語

當使用者使用含糊或一詞多義的術語時，提出一個精確的標準術語。「你說『帳戶』：你指的是 Customer（客戶）還是 User（使用者）？那是不同的東西。」

### 討論具體情境

討論領域關係時，用具體情境進行壓力測試。發明能探測邊界案例的情境，迫使使用者精確說明概念之間的界線。

### 與程式碼交叉比對

當使用者陳述某件事如何運作時，檢查程式碼是否一致。如果發現矛盾就提出來：「你的程式碼會取消整張訂單，但你剛剛說可以部分取消。哪個才對？」

### 即時更新 GLOSSARY.md

一個術語確定時，當場更新 `GLOSSARY.md`。不要累積起來一次處理：發生時就記錄。格式請依照 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)。

`GLOSSARY.md` 應完全不含實作細節。不要把 `GLOSSARY.md` 當成規格、草稿本或實作決策的存放處。它就是詞彙表，僅此而已。

### 節制地提議 ADR

只有在以下三點都成立時，才提議建立 ADR：

1. **難以反悔**：日後改變主意的成本是顯著的
2. **沒有脈絡會令人驚訝**：未來的讀者會疑惑「他們為什麼這樣做？」
3. **真正取捨的結果**：確實有其他選項，而你基於特定理由選了其中一個

三者缺一，就略過 ADR。格式請依照 [ADR-FORMAT.md](./ADR-FORMAT.md)。
