# 把腦力激盪的想法變成設計

透過自然的協作對話，幫助把想法變成完整成形的設計與規格。

先判斷這個請求需要多少流程，然後走完你的路徑：理解情境、精煉想法、提出設計，並取得你的人類夥伴的核准。

<HARD-GATE>
在你告訴人類夥伴你打算做什麼、且對方核准之前，「不要」呼叫任何實作技能、撰寫任何程式碼、建立任何專案骨架，或採取任何實作行動。這適用於下方「每一條」路徑上的「每一個」任務——儀式的多寡隨任務調整；核准關卡永遠不變。
</HARD-GATE>

## 三條路徑

在你的第一個問題之前，先把請求分類，並把分類說出來——「這看起來是有界的，所以我會在這裡提出一份簡短的設計，而不是寫一份規格」——讓你的人類夥伴可以推翻它：

- **試探（Spike）**——一個可行性問題（「我們能不能……」「有沒有可能……」「隨便做做就好」），產出的是一個答案，而不是你會保留的程式碼。用 2–3 句話說明問題與你要嘗試的做法，得到點頭後，在不犧牲正確性的前提下用最便宜的方式找出答案。沒有設計文件、沒有規格檔。以建議的形式回報發現；你做出來的任何東西都維持標示為拋棄式。
- **有界（Bounded）**——對這個 repo 中已存在之程式碼的範圍明確的變更：一個新旗標、一個小端點、一個單一檔案的修正。了解這類應用程式是什麼樣子還不夠——有界的意思是你要修改的流程已經在這裡可以讀到。如果沒有既有的流程可以修改，這個任務就不是有界的。問那些重要的釐清問題，在「聊天中」提出一份簡短的設計（幾句話到幾個短段落），然後「停下來」。只有在你的人類夥伴對那份設計說好之後，才開始實作——有界任務的核准，和架構級任務的核准一樣是硬性關卡。沒有規格檔、沒有實作計畫文件。
- **架構級（Architectural）**——新專案、新子系統、會重組元件之間如何組合或改變他人依賴之介面的變更。遵循完整流程：提問、方案、分段設計、書面規格，然後是 writing-plans 技能。

在兩條路徑之間猶豫時，選較重的那條。這個棘輪是單向的：任務進行中發現的隱藏複雜度會讓路徑升級——停下來、說出來、往上升一級。任務進行中沒有任何事會讓路徑降級。

## 反模式：「太簡單了，不需要核准」

每一條路徑都以你的人類夥伴在實作前核准你的意圖作結。一個待辦清單、一個單一函式的工具、一個設定變更——設計可能只是聊天中的兩句話，但你「必須」提出它並取得核准。「簡單」的任務正是未經檢視的假設造成最多白工的地方。隨簡單程度縮放的是產物，永遠不是核准。

## 警訊

| 念頭 | 現實 |
|---------|---------|
|「這太簡單了，不需要設計」| 簡單代表設計很短，不代表沒有設計。聊天中兩句話，然後核准。 |
|「我把它叫做有界，就可以跳過規格」| 為了跳過工作而找標籤，這本身「就是」猶豫——選較重的路徑。 |
|「它是有界的、設計很明顯——他們在讀的時候我就先開始」| 關卡是核准，不是設計的長度。提出，然後停下來直到你聽到「好」。 |
|「我了解這類應用程式，所以它是有界的」| 有界衡量的是 repo，不是你的熟悉程度。新專案沒有既有的流程——它是架構級的。 |
|「試探成功了，所以我要保留程式碼」| 試探的產出是答案。保留程式碼是一個新的請求——把它分類。 |
|「它變大了，但我快做完了——不需要重新分類」| 隱藏的複雜度會在任務進行中讓路徑升級。停下來並說出來。 |
|「他們核准了試探，所以後續的變更也核准了」| 每個任務都有自己的分類與自己的核准。 |

## 檢查清單

先分類、宣布路徑，然後為你路徑上的每一項建立一個任務，並依序完成。

**試探：**
1. **探索專案情境**——足以框定這次試探即可
2. **提出問題 + 試探計畫**——2–3 句話
3. **取得核准**——點頭就夠了
4. **調查**——在不犧牲正確性的前提下盡量便宜
5. **回報發現**——一個建議；把做出來的任何東西標示為拋棄式

**有界：**
1. **探索專案情境**——檢查檔案、文件、最近的提交
2. **問釐清問題**——一次一個，只問重要的
3. **在聊天中提出簡短設計**——做法、會動到的檔案、測試方式
4. **取得核准**——「停下來」等待明確的「好」；同一口氣提出設計又開始動手，就是跳過關卡
5. **實作**——以一般的開發工作流程進行（適用 TDD）；不需要計畫文件

**架構級：**
1. **探索專案情境**——檢查檔案、文件、最近的提交
2. **適時提供視覺輔助**——「不要」一開始就提。第一次遇到某個問題用展示真的會比描述更清楚時，再提出（作為獨立的一則訊息）；核准後它的瀏覽器分頁會為你開啟。如果從來沒有出現視覺性的問題，就永遠不要提。參見下方的「視覺輔助」章節。
3. **問釐清問題**——一次一個，理解目的／限制／成功標準
4. **提出 2–3 種做法**——附上取捨與你的建議
5. **提出設計**——依複雜度分段，每段之後取得使用者核准
6. **撰寫設計文件**——存到 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 並提交
7. **規格自我審查**——快速就地檢查佔位符、矛盾、模糊與範圍（見下方）
8. **使用者審閱書面規格**——在繼續之前請使用者審閱規格檔
9. **轉入實作**——呼叫 writing-plans 技能建立實作計畫

## 流程

下方的小節服務有界與架構級路徑（試探在「提出試探、得到點頭」就停止）。從 **探索做法** 開始的各節屬於架構級路徑的深度——對於有界的工作，情境加上幾個問題再加上聊天中的簡短設計，就是整個流程。

**理解想法：**

- 先查看目前專案的狀態（檔案、文件、最近的提交）
- 在問細節問題之前，先評估範圍：如果請求描述了多個獨立的子系統（例如「打造一個有聊天、檔案儲存、計費與分析的平台」），立即點出來。不要把問題花在精煉一個需要先拆解的專案的細節上。
- 如果專案大到無法放進單一份規格，幫助使用者拆解成子專案：有哪些獨立的部分、它們之間如何關聯、應該以什麼順序建造？然後透過一般的設計流程為第一個子專案做腦力激盪。每個子專案都有自己的「規格 → 計畫 → 實作」循環。
- 對於範圍適當的專案，一次問一個問題來精煉想法
- 可能的話偏好選擇題，但開放式問題也可以
- 每則訊息只問一個問題——如果某個主題需要更多探索，就拆成多個問題
- 專注於理解：目的、限制、成功標準

**探索做法：**

- 提出 2–3 種不同的做法並說明取捨
- 以對話的方式呈現選項，附上你的建議與理由
- 先講你建議的選項並解釋原因
- 無情地貫徹 YAGNI——從每個做法與設計中移除不必要的功能

**提出設計：**

- 一旦你相信自己理解要打造的是什麼，就提出設計
- 讓每一節的篇幅與其複雜度相稱：直接的部分幾句話即可，細膩的部分最多 200–300 字
- 每一節之後詢問到目前為止看起來是否正確
- 涵蓋：架構、元件、資料流、錯誤處理、測試
- 如果有地方說不通，準備好回頭釐清

**為隔離與清晰而設計：**

- 把系統拆成較小的單元，每個單元都有一個清楚的目的、透過定義良好的介面溝通，並且能被獨立理解與測試
- 對每個單元，你都應該能回答：它做什麼、怎麼使用它、它依賴什麼？
- 有人能不讀內部實作就理解一個單元在做什麼嗎？你能在不破壞使用者的情況下修改內部嗎？如果不能，邊界就需要調整。
- 較小、邊界清楚的單元對你來說也比較容易處理——對於能一次放進情境中的程式碼，你的推理會更好；檔案聚焦時，你的編輯也更可靠。當一個檔案變得很大，那通常是它做太多事的訊號。

**在既有的程式碼中工作：**

- 在提出變更之前先探索目前的結構。遵循既有的模式。
- 如果既有程式碼的問題會影響這項工作（例如檔案變得太大、邊界不清楚、職責糾纏），就把有針對性的改善納入設計——就像一個好的開發者會改善他正在處理的程式碼一樣。
- 不要提出無關的重構。專注於對目前目標有幫助的事情。

## 設計之後（架構級路徑）

**文件：**

- 把驗證過的設計（規格）寫到 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`
  - （使用者對規格位置的偏好會覆蓋這個預設）
- 如果有的話，使用 elements-of-style:writing-clearly-and-concisely 技能
- 把設計文件提交到 git

**規格自我審查：**
寫完規格文件後，用全新的眼光再看一次：

1. **佔位符掃描：** 有沒有「TBD」「TODO」、未完成的章節或模糊的需求？修正它們。
2. **內部一致性：** 有沒有章節互相矛盾？架構和功能描述相符嗎？
3. **範圍檢查：** 這是否聚焦到足以寫成單一份實作計畫，還是需要拆解？
4. **模糊檢查：** 有沒有任何需求可以被解讀成兩種不同的意思？如果有，選一種並寫明。

就地修正任何問題。不需要重新審查——修正後繼續前進即可。

**使用者審閱關卡：**
規格審查循環通過後，在繼續之前請使用者審閱書面規格：

> 「規格已寫好並提交到 `<path>`。請審閱一下，如果在我們開始撰寫實作計畫之前想做任何修改，請告訴我。」

等待使用者的回應。如果他們要求修改，就修改並重新跑規格審查循環。只有在使用者核准後才繼續。

**實作：**

- 呼叫 writing-plans 技能建立詳細的實作計畫
- 「不要」呼叫任何其他技能。writing-plans 就是下一步。

## 視覺輔助

一個在腦力激盪期間展示模型稿、圖表與視覺選項的瀏覽器輔助工具。它是一個工具——不是一種模式。接受輔助代表它可供那些適合視覺呈現的問題使用；並「不」代表每個問題都要透過瀏覽器。

**提供輔助（適時）：** 「不要」一開始就提。等到某個問題用展示真的會比用說的更清楚時——一個真正的模型稿／版面／圖表問題，而不只是 UI 的*主題*。第一次發生時再提出，作為獨立的一則訊息：
> 「接下來這部分如果我直接展示給你看可能會比較容易——我可以邊進行邊在瀏覽器分頁中整理模型稿、圖表與比較。這功能還很新，可能會耗用較多 token。要我這樣做嗎？我會幫你開啟。」

**這個提議「必須」是獨立的一則訊息。** 只有提議——沒有釐清問題、摘要或其他內容。等待使用者的回應。如果他們接受，以 `--open` 啟動伺服器，讓他們的瀏覽器自動開到第一個畫面。如果他們拒絕，就繼續只用文字，除非他們主動提起，否則不要再提。

**逐題決定：** 即使使用者接受了，也要「針對每一個問題」決定要用瀏覽器還是終端機。判斷標準：**使用者用看的會比用讀的更容易理解嗎？**

- **使用瀏覽器** 處理本身就是視覺的內容——模型稿、線框圖、版面比較、架構圖、並排的視覺設計
- **使用終端機** 處理文字內容——需求問題、概念性選擇、取捨清單、A/B/C/D 文字選項、範圍決策

關於 UI 主題的問題不會自動成為視覺問題。「在這個情境下，個性是什麼意思？」是概念性問題——使用終端機。「哪一種精靈（wizard）版面比較好？」是視覺問題——使用瀏覽器。

如果他們同意使用輔助，繼續之前先閱讀詳細指南：
`skills/brainstorming/visual-companion.md`
