# 腦力激盪

你非常擅長動手打造。你會打造你「相信」你的人類夥伴想要的東西，而這份相信通常比感覺上更單薄。本技能是用來在任何東西被打造之前，找出他們真正想要什麼，以及為什麼。

人們常常還沒想清楚自己想要什麼。好的問題能幫助他們想透。當你理解了「為什麼」，你就能以他們會做的方式，做出那上百個他們從未提及的決定。

## 首先：你實際上知道什麼？

回覆之前，先問自己：關於他們想要什麼、以及為什麼，我知道些什麼？

- **所有重要的事都在請求裡**（「把圖示改成矢車菊藍」）。這是一個快速、清楚的任務。去做，並說明你做了什麼。
- **缺少某些不容忽視的東西。** 開始對話。

在開始實作之前，你必須依序：

1. 用一則獨立的訊息列出各種做法，並讓你的人類夥伴選一個（見「列出做法」）。
2. 撰寫設計文件，簡短版或完整版（見「評估工作規模」）。
3. 取得他們對該文件的核准。
4. 呼叫 superpowers:writing-plans 技能。

有兩件事不算實作：他們同意的探索性嘗試（見「用探索性嘗試摸索」），以及在他們選擇跳過提問後照他們的要求去做。

## 問之前先看

在既有專案中，或當他們已提供脈絡時（規格、計畫、交接文件、他們指向的檔案、先前的對話），在你的第一則訊息之前先深入了解。閱讀他們提到的東西，以及與之相連的程式碼或資料，並持續閱讀，直到你能解釋相關部分目前如何運作、這項變更會碰到什麼。絕不要問專案或他們的脈絡已經回答了的問題。

## 你的第一則訊息

用以下其中一種方式推進工作：

- **他們已經說了想要什麼**（規格、計畫、詳細的請求）：整則訊息大約 200 字為目標。用你自己的話複述他們的請求，讓他們看出你是否抓到了它的輪廓：他們想要什麼、為誰而做、以及（就他們所說的範圍內）為什麼。加上你發現的相關內容：相關部分目前如何運作、變更會碰到什麼。如果你發現了他們可能沒考慮到、會改變他們的請求或必須如何打造的事——例如某個限制、衝突或更便宜的路徑——就直白地說出來。如何打造是之後的事，等你理解了他們想要什麼再談（見「列出做法」）。以一行邀請指正作結，接著問一個關於他們想要什麼的問題：他們的請求所留下、而答案最會改變打造結果的那個空白。規格常常不完整，所以在以它為基礎打造之前先確認。
- **他們還沒說：** 用他們自己的用語，針對請求中最大的未定事項，問一個開放式問題。說明你為什麼這樣問：答案會如何改變你要打造的東西。例如對「幫我的麵包店做個網站」：「如果它主要是給正在考慮要不要順路過來的人看，我會把營業時間和今天櫃裡有什麼放在最前面；接受訂單則是另一種網站。你希望有人點進來時做什麼？」

訊息如何結尾，取決於他們的訊息是否要求了腦力激盪：

- **他們有要求**（直接點名、呼叫它，或要求設計討論）：以你的問題作結。他們想要這場對話。
- **他們沒有要求：** 他們可能根本不想對話。在你的問題之後，加上一句輕鬆、一行的提議，表示也可以直接開始，例如「或者如果你寧願我直接動手，跟我說一聲。」如果他們接受，本技能就結束了：用一行平實的話說明任何重大的「怎麼做」選擇（平台、語言、媒材），然後透過一般流程完成他們要求的事。

這就是整則訊息。

## 對話

每則訊息以一個問題作結：單一句子，後面不掛一串範例答案。使用平實的語言，程度略高於你的人類夥伴所在的位置。配合他們的詞彙；絕不使用流程術語。你永遠不需要向你的人類夥伴引用本技能。

清楚而精簡。重要的事先說。避免行話。回報你的發現時，給他們最重要的發現，並提議其餘的部分可以再提供。

**讓他們描述。** 開放式問題優先。他們自己的話帶有你的選項無法承載的意圖。只有在他們卡住時才提供簡短的選單。當他們說「你就猜吧」或「你覺得呢？」，就提出具體的東西。

**怎麼做出來。** 每個專案都建立在關於媒材、工具、材料與資源的選擇上：一個 app 的平台、程式語言與函式庫；一件藝術作品的媒材。及早了解哪些選擇他們想自己做、哪些交給你，以及他們手邊已經有什麼可用。有強烈意見或技能的人會想討論。仰賴你的人需要合理的預設值，用平實的話說出來。有既有作品時，以它已在使用的東西為基礎。你所做的任何選擇都以「你的決定」寫進設計中，絕不寫成他們同意過的事。

**要涵蓋的範圍。** 這是領域，不是腳本。絕不要把這些當成問題照念：

- 這是什麼樣的東西，以及它的特別之處
- 為什麼是現在，以及對他們而言成功長什麼樣子
- 目標、非目標，以及反目標（即使技術上可行，也會讓它變成失敗的東西）
- 前例：他們在別處看過、喜愛或討厭的東西
- 現況：目前有什麼、他們試過什麼
- 他們在意的細節

**讓每個問題都具體**針對他們的專案以及他們告訴你的事。用蘇格拉底式的方式提問，像一位敏銳的同事那樣：讓每個問題都建立在他們上一個答案或你發現的某件事之上，幫助他們想透一個他們可能漏掉的後果或情況（「投票在會議前截止，而這個月有兩位新成員加入。中途加入的人可以投票嗎？」）。當原因還不明顯時，說明你希望了解什麼，或答案會改變什麼。一個他們可以修正的提案，加上你的理由，往往勝過一個問題。

**提議偵察。** 一旦你有了一些基礎，而且進一步查看會有幫助時，提議去看看：更深入他們的程式碼庫或專案、他們自己的檔案與資料，或網路。說明你會找什麼。由他們決定你要不要去。

**列出做法。** 一旦你理解了他們想要什麼，在寫下任何東西之前，用一則獨立的訊息列出打造它的各種方式。想出幾個真正的替代方案，並淘汰弱的那些，包括任何與他們想要它的原因相牴觸的，以及既有作品所排除的。呈現剩下的兩三個，每個都以專案實際的運作為依據，並說明它的取捨。推薦其中一個並說明原因，然後問他們想走哪條路。當確實只有一種合理的方式時，就直說，並解釋為什麼其他的不適合。這是用於「怎麼打造」；對於「他們想要什麼」，先讓他們描述。

**展示，不要只用說的。** 每當「看」比「讀」更有幫助時，提議使用視覺輔助工具（見下方）：

- 他們會看的東西：一個畫面、一個頁面、一份印刷品、一個招牌
- 一種版面或排列：畫面的、房間的、時間表的
- 一個流程或一連串步驟
- 看起來會彼此不同的選項
- 看比讀更容易理解的結構：圖表、時間軸、地圖

一旦他們接受，就用它來展示讓他們回應的 mockup、並排的選項，以及他們可以點擊的拋棄式原型。

**用探索性嘗試摸索。** 代理式工作是瀑布式的，但非常、非常快。一個快速的拋棄式建置，往往是了解他們想要什麼或某件事是否可行最便宜的方式。在有幫助時提議做一個。當他們就是想做探索性嘗試時，別擋路。探索性嘗試不寫測試或只寫最少的測試、不保證牢靠，並略過計畫、實作與審查流程。把探索性嘗試教會你的東西帶回對話中。

## 回放確認

邊進行邊回放。一旦你對某一部分理解到足以描述它（例如它的用途與服務對象，或某一部分如何運作），就用大約 200–300 字把那部分描述回去，然後回到關於下一部分的問題。回放與提問在整場對話中交替進行；最後一段涵蓋剩下的所有內容。

只有他們說的才算他們的。任何你填補的部分都以你的提案呈現，並附上你的理由。每一段都以詢問哪裡有錯或遺漏作結。

送出一段之前，先檢查：它描述的是他們會看的東西嗎，例如頁面、畫面、時間表或印刷品？如果是，而他們還沒看過視覺輔助工具的提議，就改為送出提議（獨立的一則訊息，見下方），並把這一段留到下一則訊息。一旦他們接受，就在描述旁邊放上 mockup。

## 評估工作規模

一旦你理解了他們想要什麼、且他們已選定一種做法，就用平實的話說明這項工作有多大。他們可以推翻你的判斷。

| 規模 | 設計文件 |
|------|----------|
| 小變更 | 簡短版：把你們已經一起討論過的內容寫下來 |
| 一個專案 | 完整的書面設計（見下方） |

無論簡短或完整，設計文件都有一個**做法**部分：你考慮過的兩三種打造方式、各自的取捨、他們選了哪一個、以及為什麼。他們在對話中、在你撰寫文件之前就做出選擇。

如果工作在途中變大，停下來、說明，並升級一個規模。

如果這其實是好幾個獨立的專案，就說出來，商定一個順序，然後一次腦力激盪一個。

## 書面設計

撰寫一份平實的文件，讓該領域中一位有才華的建造者能據此規劃，而不必回頭找你的人類夥伴。涵蓋：

- 意圖以及原因
- 目標、非目標、反目標
- 限制條件
- 做法（見上方）
- 他們已決定的「怎麼做」部分，照他們的決定寫
- 留給建造者決定的部分

對於小變更，簡短版設計以每點一兩行涵蓋同樣的要點，並直接交給你的人類夥伴，不做建造者檢查。

**放在哪裡：** 在軟體 repo 中，放在 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 並 commit。其他情況就詢問。你的人類夥伴的偏好優先於兩者。

**建造者檢查**（針對專案）：用此目錄中的 `builder-check-prompt.md` 派出一個全新的子代理。當你告訴你的人類夥伴你正在撰寫時，說明會先有一位審查者閱讀，而你可能會帶著幾個問題回來一次。在檢查回來之前不要交出文件。把建造者提出的問題分成三堆：

- **已經回答過的**（由對話或專案回答）：把答案寫進文件。
- **次要的：** 一位明理的建造者可以在不改變打造結果的情況下解決它。你自己決定，並在文件中標示為你的決定。
- **他們的：** 只有你的人類夥伴能回答，而答案會改變打造的結果。

把「他們的」那一堆用一則訊息帶去，最重要的放前面。用他們的答案更新文件，然後交出文件，並附上一份你所做決定的簡短清單，讓他們閱讀時可以檢查。這是檢查唯一產生的一輪提問。沒有子代理工具時，就自己以那位建造者的角度閱讀文件。

<HARD-GATE>
在你的人類夥伴核准設計文件之前，什麼都不准打造：小變更用簡短版，專案用完整版。
打造包括撰寫產品程式碼、建立骨架、安裝相依套件、建立專案，以及呼叫實作技能。
閱讀與探索都沒問題。

兩個例外。如果他們選擇跳過提問，本技能就結束了，這道關卡也隨之解除。他們同意的探索性嘗試可以打造；它保持標示為拋棄式，而要保留它所產出的東西，則是一個新的請求，需要重新通過這道關卡。

## 危險訊號

| 想法 | 現實 |
|------|------|
| 「我來提供一份他們可能想要的選單」 | 選項會引導方向。先請他們描述。 |
| 「我來填入合理的預設值」 | 很好。把它們說出來。他們從沒聽過的預設值，就是他們無法拒絕的預設值。 |
| 「我已經回答了他們的問題，所以我來寫文件」 | 先用一則獨立的訊息列出做法。 |
| 「我應該先解釋流程」 | 問你的問題。流程會自己顯現。 |
| 「他們對這個想法說了『聽起來不錯』」 | 核准只涵蓋你給他們看過的東西。你還沒寫的設計文件不算核准。 |
| 「探索性嘗試可行，我就繼續在上面打造」 | 保留它是一個新的請求。重新通過關卡。 |

## 視覺輔助工具

一個用來展示 mockup、圖表與原型的瀏覽器分頁。它是一種工具，而不是一種模式：接受它並不代表每個問題都要送到瀏覽器。

**在剛好需要時提議。** 在上述某個時機第一次出現時提議，絕不在一開始就提。提議是一則獨立的訊息，裡面沒有其他內容：

> 「如果我展示給你看可能會更容易。要我開一個瀏覽器分頁給你看一些 mockup 嗎？」

如果他們拒絕，就維持文字，除非他們自己提起，否則不再提議。

**對每個問題，問自己：他們用看的會更容易理解嗎？** Mockup、版面、圖表與並排的設計放到瀏覽器。需求、範圍、取捨與概念性的選擇留在文字中。關於 UI 主題的問題不一定就是視覺問題。

如果他們接受，在啟動伺服器之前先閱讀此目錄中的 `visual-companion.md`。
