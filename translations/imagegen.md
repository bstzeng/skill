# 圖片生成技能

為目前的專案產生或編輯圖片（例如網站素材、遊戲素材、UI mockup、產品 mockup、線框圖、Logo 設計、寫實圖片或資訊圖表）。

## 頂層模式與規則

本技能恰好有兩種頂層模式：

- **預設的內建工具模式（優先）：** 內建的 `image_gen` 工具，用於一般的圖片生成與編輯。不需要 `OPENAI_API_KEY`。
- **備用 CLI 模式（僅限明確要求）：** `scripts/image_gen.py` CLI。只有在使用者明確要求 CLI 路徑時才使用。需要 `OPENAI_API_KEY`。

只有在明確的 CLI 備案中，CLI 才提供三個子指令：

- `generate`
- `edit`
- `generate-batch`

規則：
- 所有一般的圖片生成與編輯請求，預設使用內建的 `image_gen` 工具。
- 絕不自動切換到 CLI 備案。
- 如果內建工具失敗或無法使用，告訴使用者有 CLI 備案，以及它需要 `OPENAI_API_KEY`。只有在使用者明確要求該備案時才繼續。
- 如果使用者明確要求 CLI 模式，使用內附的 `scripts/image_gen.py` 工作流程。不要建立一次性的 SDK 執行器。
- 絕不修改 `scripts/image_gen.py`。如果缺少什麼，在做任何其他事之前先詢問使用者。

內建工具的存檔路徑政策：
- 在內建工具模式下，Codex 預設把產生的圖片存在 `$CODEX_HOME/*` 下。
- 不要把作業系統的暫存目錄描述成、或依賴它作為內建工具的預設目的地。
- 不要描述或依賴內建 `image_gen` 工具上的目的地路徑參數（如果有的話）。如果需要特定位置，先產生，然後從 `$CODEX_HOME/generated_images/...` 移動或複製所選的輸出。
- 內建模式下的存檔路徑優先順序：
  1. 如果使用者指名了目的地，就把所選的輸出移動或複製到那裡。
  2. 如果圖片是給目前專案使用的，在結束之前把最終選定的圖片移動或複製到工作區。
  3. 如果圖片只是用於預覽或腦力激盪，就在對話中直接顯示；底層的檔案可以留在預設的 `$CODEX_HOME/*` 路徑。
- 絕不讓一個被專案引用的素材只存在預設的 `$CODEX_HOME/*` 路徑。
- 除非使用者明確要求取代，否則不要覆寫既有的素材；改為建立一個並列、帶版本的檔名，例如 `hero-v2.png` 或 `item-icon-edited.png`。

兩種模式共用的提示詞指引在 `references/prompting.md` 與 `references/sample-prompts.md`。

只用於 CLI 備用模式的文件/資源：
- `references/cli.md`
- `references/image-api.md`
- `references/codex-network.md`
- `scripts/image_gen.py`

## 何時使用
- 產生一張新圖片（概念美術、產品照、封面、網站主視覺）
- 使用一張或多張參考圖片的風格、構圖或氛圍，產生一張新圖片
- 編輯既有的圖片（局部重繪、光線或天氣轉換、背景替換、移除物件、合成、透明背景）
- 為一項任務產出許多素材或變體

## 何時不要使用
- 延伸或配合 repo 中既有的 SVG/向量圖示集、Logo 系統或插畫庫
- 建立更適合直接用 SVG、HTML/CSS 或 canvas 產出的簡單形狀、圖表、線框圖或圖示
- 當來源檔已經以可編輯的原生格式存在時，對專案本地的素材做小幅編輯
- 任何使用者明顯想要決定性的程式碼原生輸出、而不是生成點陣圖的任務

## 決策樹

思考兩個獨立的問題：

1. **意圖：** 這是一張新圖片，還是既有圖片的編輯？
2. **執行策略：** 這是一個素材，還是許多素材/變體？

意圖：
- 如果使用者想修改既有的圖片、同時保留其中的部分，就把請求視為**編輯**。
- 如果使用者提供的圖片只是作為風格、構圖、氛圍或主題指引的參考，就把請求視為**產生**。
- 如果使用者沒有提供任何圖片，就把請求視為**產生**。

內建編輯的語意：
- 內建編輯模式用於已經在對話脈絡中可見的圖片，例如附加的圖片或在此執行緒中稍早產生的圖片。
- 如果使用者想用內建工具編輯一個本機圖片檔，先用內建的 `view_image` 工具載入它，讓圖片在對話脈絡中可見，然後再進行內建的編輯流程。
- 不要承諾能透過內建工具編輯任意的檔案系統路徑。
- 如果某個本機檔案仍需要直接的檔案路徑控制、遮罩或其他只有 CLI 才有的明確參數，只有在使用者要求時才使用明確的 CLI 備案。
- 對於編輯，積極地保留不變的部分，並預設以非破壞的方式儲存。

執行策略：
- 在預設的內建路徑中，為每個要求的素材或變體各發出一次 `image_gen` 呼叫，以產出多個素材或變體。
- 在明確的 CLI 備用路徑中，只有在使用者明確選擇了 CLI 模式且需要許多提示/素材時，才使用 CLI 的 `generate-batch` 子指令。

除非使用者明確要求修改既有的圖片，否則假設使用者想要一張新圖片。

## 工作流程
1. 決定頂層模式：預設為內建，只有在明確要求時才用備用 CLI。
2. 決定意圖：`generate` 或 `edit`。
3. 決定輸出是只供預覽，還是要給目前的專案使用。
4. 決定執行策略：單一素材 vs 重複的內建呼叫 vs CLI `generate-batch`。
5. 一開始就蒐集輸入：提示詞、確切的文字（逐字）、限制/避免清單，以及任何輸入圖片。
6. 對每張輸入圖片，明確標示它的角色：
   - 參考圖片
   - 編輯目標
   - 輔助的插入/風格/合成輸入
7. 如果編輯目標只在本機檔案系統上、而你要留在內建路徑，先用 `view_image` 檢視它，讓圖片在對話脈絡中可用。
8. 如果使用者要求的是照片、插畫、sprite、產品圖、橫幅或其他明確屬於點陣風格的素材，就使用 `image_gen`，而不是以 SVG/HTML/CSS 占位物代替。如果請求的是應該配合 repo 既有原生 SVG/向量/程式碼素材的圖示、Logo 或 UI 圖形，就優先直接編輯那些素材。
9. 依具體程度補充提示詞：
   - 如果使用者的提示詞已經具體詳細，就把它正規化成清楚的規格，不加入創意上的要求。
   - 如果使用者的提示詞很籠統，只有在能實質改善輸出品質時，才加入有品味的補充。
10. 預設使用內建的 `image_gen` 工具。
11. 如果使用者明確選擇了 CLI 備案，那時、也只有那時，才使用備用專屬文件中關於品質、`input_fidelity`、遮罩、輸出格式、輸出路徑與網路設定的內容。
12. 檢查輸出並驗證：主題、風格、構圖、文字正確性，以及不變的部分/避免的項目。
13. 以單一針對性的修改反覆調整，然後再檢查。
14. 對於只供預覽的工作，在對話中直接顯示圖片；底層的檔案可以留在預設的 `$CODEX_HOME/generated_images/...` 路徑。
15. 對於要給專案使用的工作，把選定的產出物移動或複製到工作區，並更新任何使用它的程式碼或參照。絕不讓一個被專案引用的素材只存在預設的 `$CODEX_HOME/generated_images/...` 路徑。
16. 對於批次，除非使用者明確要求保留被淘汰的變體，否則只在工作區中保存選定的最終版本。
17. 對於任何要放進工作區的素材，一律回報最終的存檔路徑，加上最終的提示詞，以及使用的是內建工具還是備用 CLI 模式。

## 提示詞補充

把使用者的提示詞重新整理成結構化、以製作為導向的規格。讓使用者的目標更清楚、更可執行，但不要盲目加入細節。

把這當作提示詞塑形的指引，而不是一份封閉的 schema。只使用有幫助的行，並在能實質提升清晰度時，加一行簡短的額外標籤行。

### 具體程度政策

依使用者提示詞的具體程度，決定多少補充是恰當的：

- 如果提示詞已經具體詳細，保留那份具體程度，只做正規化/結構化。
- 如果提示詞很籠統，在能實質改善結果時，你可以加入有品味的補充。

允許的補充：
- 構圖或取景的提示
- 精緻程度或預期用途的提示
- 實用的版面指引
- 支持所述請求、合理的場景具體化

不允許的補充：
- 請求中沒有暗示的額外角色或物件
- 沒有暗示的品牌名稱、標語、配色或敘事情節
- 任意指定在某一側的擺放，除非周圍的版面支持它

## 使用情境分類（確切的代稱）

把每個請求歸到以下其中一類，並在提示詞與參考中保持代稱一致。

產生：
- photorealistic-natural ——有真實質感與自然光線的隨性/編輯風格生活場景。
- product-mockup ——產品/包裝照、型錄圖片、周邊商品概念。
- ui-mockup ——應用程式/網頁介面的 mockup 與線框圖；要指定想要的擬真度。
- infographic-diagram ——有結構化版面與文字的圖表/資訊圖表。
- logo-brand ——Logo/標誌的探索，適合轉為向量。
- illustration-story ——漫畫、兒童繪本插畫、敘事場景。
- stylized-concept ——以風格為主的概念美術、3D/風格化渲染。
- historical-scene ——符合時代考據/世界知識的場景。

編輯：
- text-localization ——翻譯/替換圖片中的文字，保留版面。
- identity-preserve ——試穿、把人放進場景中；鎖定臉部/身體/姿勢。
- precise-object-edit ——移除/替換特定的元素（包括室內的替換）。
- lighting-weather ——只改變一天中的時間/季節/氛圍。
- background-extraction ——透明背景 / 乾淨的去背。
- style-transfer ——套用參考的風格，同時改變主題/場景。
- compositing ——多張圖片的插入/合併，並配合光線/透視。
- sketch-to-render ——把草圖/線稿轉成寫實的渲染。

## 撰寫提示詞的最佳實踐
- 把提示詞組織成：場景/背景 -> 主題 -> 細節 -> 限制。
- 包含預期用途（廣告、UI mock、資訊圖表），以設定模式與精緻程度。
- 寫實照片使用攝影機/構圖的語言。
- 只有在使用者明確要求向量輸出或非圖片的占位物時，才使用 SVG/向量替代品。
- 引用確切的文字，並指定字體排印 + 擺放位置。
- 對於棘手的字，逐字母拼出，並要求逐字渲染。
- 對於多張圖片的輸入，以索引參照圖片，並描述它們該如何被使用。
- 對於編輯，每次迭代都重複不變的部分，以減少偏移。
- 以單一變更的後續調整進行迭代。
- 如果提示詞很籠統，只加入能實質幫上忙的額外細節。
- 如果提示詞已經很詳細，就正規化它，而不是擴充它。
- 只限明確的 CLI 備案：`quality`、`input_fidelity`、遮罩、輸出格式與輸出路徑的指引，見 `references/cli.md` 與 `references/image-api.md`。

### 暫存與輸出慣例
這些慣例只適用於明確的 CLI 備案。它們不描述內建 `image_gen` 的輸出行為。

- 用 `--out` 或 `--out-dir` 控制輸出路徑；保持檔名穩定且具描述性。

### 環境
- 即時 API 呼叫必須設定 `OPENAI_API_KEY`。
- 使用內建的 `image_gen` 工具時，不要向使用者索取 `OPENAI_API_KEY`。

如果缺少金鑰，給使用者這些步驟：
1. 在 OpenAI 平台介面中建立 API 金鑰：https://platform.openai.com/api-keys
2. 在他們的系統中把 `OPENAI_API_KEY` 設為環境變數。
3. 需要時，提議引導他們為自己的作業系統/shell 設定環境變數。

如果在這個環境中無法安裝，告訴使用者缺少哪個相依項目，以及如何把它安裝進他們目前使用的環境。
