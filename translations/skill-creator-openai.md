# 技能製作器

本技能提供建立有效技能的指引。

## 關於技能

技能是模組化、自成一體的資料夾，透過提供專門的知識、工作流程與工具來擴充 Codex 的能力。把它們想成特定領域或任務的「入職指南」——它們把 Codex 從一個通用代理，轉變成一個具備任何模型都無法完全擁有的程序性知識的專門代理。

### 技能提供什麼

1. 專門的工作流程 ——特定領域的多步驟程序
2. 工具整合 ——處理特定檔案格式或 API 的說明
3. 領域專業 ——公司特有的知識、schema、商業邏輯
4. 內附資源 ——用於複雜與重複任務的腳本、參考與素材

## 核心原則

### 精簡為王

上下文視窗是公共財。技能與 Codex 需要的其他一切共享上下文視窗：系統提示、對話歷史、其他技能的中繼資料，以及實際的使用者請求。

**預設假設：Codex 已經非常聰明。** 只加入 Codex 還沒有的脈絡。質疑每一段資訊：「Codex 真的需要這段解釋嗎？」以及「這一段值得它的 token 成本嗎？」

優先使用精簡的範例，而不是冗長的解釋。

### 設定適當的自由度

讓具體程度配合任務的脆弱程度與變化程度：

**高自由度（以文字為主的指示）**：當有多種有效的做法、決策取決於脈絡，或以經驗法則引導做法時使用。

**中自由度（偽程式碼或帶參數的腳本）**：當存在偏好的模式、可以接受某些變化，或設定會影響行為時使用。

**低自由度（具體的腳本、很少參數）**：當操作脆弱且容易出錯、一致性至關重要，或必須遵循特定順序時使用。

把 Codex 想成在探索一條路：兩側是懸崖的窄橋需要具體的護欄（低自由度），而開闊的原野則允許許多路線（高自由度）。

#### SKILL.md（必要）

每個 SKILL.md 都包含：

- **前置資料**（YAML）：包含 `name` 與 `description` 欄位。這是 Codex 用來判斷何時使用該技能的唯一欄位，因此在描述技能是什麼、何時應該使用時，清楚且全面非常重要。
- **內文**（Markdown）：使用技能的說明與指引。只有在技能被觸發「之後」才會載入（如果有被觸發的話）。

#### 代理中繼資料（建議）

- 用於技能清單與標籤的、面向 UI 的中繼資料
- 產生值之前先閱讀 references/openai_yaml.md，並遵循其描述與限制
- 建立：透過閱讀技能，產生面向人類的 `display_name`、`short_description` 與 `default_prompt`
- 把這些值以 `--interface key=value` 傳給 `scripts/generate_openai_yaml.py` 或 `scripts/init_skill.py`，以決定性的方式產生
- 更新時：驗證 `agents/openai.yaml` 仍與 SKILL.md 一致；過時就重新產生
- 只有在明確提供時，才包含其他選用的介面欄位（圖示、品牌色）
- 欄位定義與範例見 references/openai_yaml.md

#### 內附資源（選用）

##### 腳本（`scripts/`）

用於需要決定性可靠度、或會被反覆重寫之任務的可執行程式碼（Python/Bash 等）。

- **何時包含**：當同一段程式碼被反覆重寫，或需要決定性的可靠度時
- **範例**：用於旋轉 PDF 任務的 `scripts/rotate_pdf.py`
- **好處**：節省 token、具決定性，可以在不載入上下文的情況下執行
- **注意**：Codex 仍可能需要閱讀腳本，以便修補或做環境專屬的調整

##### 參考（`references/`）

要視需要載入上下文、為 Codex 的流程與思考提供資訊的文件與參考資料。

- **何時包含**：用於 Codex 工作時應該參考的文件
- **範例**：財務 schema 用 `references/finance.md`、公司 NDA 範本用 `references/mnda.md`、公司政策用 `references/policies.md`、API 規格用 `references/api_docs.md`
- **使用情境**：資料庫 schema、API 文件、領域知識、公司政策、詳細的工作流程指南
- **好處**：讓 SKILL.md 保持精簡，只在 Codex 判斷需要時才載入
- **最佳實踐**：如果檔案很大（超過 1 萬字），在 SKILL.md 中包含 grep 搜尋模式
- **避免重複**：資訊應該存在 SKILL.md 或參考檔其中之一，而不是兩者都有。除非真的是技能的核心，否則詳細資訊優先放在參考檔——這能讓 SKILL.md 保持精簡，同時讓資訊可被找到又不會霸佔上下文視窗。SKILL.md 中只保留必要的程序性指示與工作流程指引；把詳細的參考資料、schema 與範例移到參考檔。

##### 素材（`assets/`）

不打算載入上下文、而是在 Codex 產出的輸出中使用的檔案。

- **何時包含**：當技能需要會在最終輸出中使用的檔案時
- **範例**：品牌素材用 `assets/logo.png`、PowerPoint 範本用 `assets/slides.pptx`、HTML/React 樣板用 `assets/frontend-template/`、字體排印用 `assets/font.ttf`
- **使用情境**：會被複製或修改的範本、圖片、圖示、樣板程式碼、字型、範例文件
- **好處**：把輸出資源與文件分開，讓 Codex 能在不載入上下文的情況下使用檔案

#### 技能中不要包含什麼

技能只應包含直接支援其功能的必要檔案。**不要**建立多餘的文件或輔助檔案，包括：

- README.md
- INSTALLATION_GUIDE.md
- QUICK_REFERENCE.md
- CHANGELOG.md
- 等等

技能只應包含 AI 代理完成手邊工作所需的資訊。它不應包含關於建立它的過程、設定與測試程序、面向使用者的文件等輔助脈絡。建立額外的文件檔只會增加雜亂與混淆。

### 漸進式揭露設計原則

技能使用三層載入系統，有效率地管理上下文：

1. **中繼資料（name + description）** ——永遠在上下文中（約 100 字）
2. **SKILL.md 內文** ——技能觸發時（少於 5 千字）
3. **內附資源** ——Codex 視需要載入（無上限，因為腳本可以在不讀進上下文視窗的情況下執行）

#### 漸進式揭露模式

讓 SKILL.md 內文只保留精華，並維持在 500 行以內，以減少上下文膨脹。接近這個上限時，把內容拆到獨立的檔案。把內容拆到其他檔案時，非常重要的是要從 SKILL.md 參照它們，並清楚說明何時該閱讀它們，以確保技能的讀者知道它們存在、以及何時使用。

**關鍵原則：** 當技能支援多種變體、框架或選項時，SKILL.md 中只保留核心工作流程與選擇指引。把各變體專屬的細節（模式、範例、設定）移到獨立的參考檔。

## 技能建立流程

建立技能包含以下步驟：

1. 以具體範例理解技能
2. 規劃可重用的技能內容（腳本、參考、素材）
3. 初始化技能（執行 init_skill.py）
4. 編輯技能（實作資源並撰寫 SKILL.md）
5. 驗證技能（執行 quick_validate.py）
6. 依實際使用迭代

依序遵循這些步驟，只有在有明確理由說明它們不適用時才略過。

### 技能命名

- 只使用小寫字母、數字與連字號；把使用者提供的標題正規化為連字號格式（例如「Plan Mode」-> `plan-mode`）。
- 產生名稱時，產生少於 64 個字元的名稱（字母、數字、連字號）。
- 優先使用簡短、以動詞開頭、描述動作的詞組。
- 當能提升清晰度或觸發效果時，以工具作為命名空間（例如 `gh-address-comments`、`linear-address-issue`）。
- 技能資料夾的名稱要與技能名稱完全相同。

### 步驟 1：以具體範例理解技能

只有在技能的使用模式已經被清楚理解時，才略過這一步。即使是處理既有技能，它仍然很有價值。

要建立有效的技能，需清楚理解技能將如何被使用的具體範例。這份理解可以來自使用者直接提供的範例，或經使用者回饋驗證過的產生範例。

例如，在打造一個 image-editor 技能時，相關的問題包括：

- 「image-editor 技能應該支援什麼功能？編輯、旋轉，還有其他的嗎？」
- 「你能舉一些這個技能會怎麼被使用的例子嗎？」
- 「我可以想像使用者會要求像『移除這張圖片的紅眼』或『旋轉這張圖片』這樣的事。你還想像得到這個技能有其他用法嗎？」
- 「使用者會說什麼話，應該觸發這個技能？」

為了避免讓使用者應接不暇，避免在單一訊息中問太多問題。從最重要的問題開始，視需要再追問，效果會更好。

當對技能應支援的功能有了清楚的認識時，就結束這一步。

### 步驟 2：規劃可重用的技能內容

要把具體範例轉成有效的技能，逐一分析每個範例：

1. 思考如何從零執行這個範例
2. 找出在反覆執行這些工作流程時，哪些腳本、參考與素材會有幫助

範例：在打造一個處理「幫我旋轉這份 PDF」這類查詢的 `pdf-editor` 技能時，分析顯示：

1. 旋轉 PDF 每次都需要重寫同樣的程式碼
2. 在技能中存放一個 `scripts/rotate_pdf.py` 腳本會很有幫助

範例：在設計一個處理「幫我做一個待辦清單 app」或「幫我做一個追蹤步數的儀表板」這類查詢的 `frontend-webapp-builder` 技能時，分析顯示：

1. 撰寫前端網頁應用程式每次都需要同樣的 HTML/React 樣板
2. 在技能中存放一個包含 HTML/React 樣板專案檔的 `assets/hello-world/` 範本會很有幫助

範例：在打造一個處理「今天有多少使用者登入？」這類查詢的 `big-query` 技能時，分析顯示：

1. 查詢 BigQuery 每次都需要重新探索資料表的 schema 與關聯
2. 在技能中存放一份記載資料表 schema 的 `references/schema.md` 檔會很有幫助

要確定技能的內容，分析每個具體範例，建立一份要包含的可重用資源清單：腳本、參考與素材。

### 步驟 4：編輯技能

編輯（新產生的或既有的）技能時，記得這個技能是建立給另一個 Codex 實例使用的。包含對 Codex 有益且不顯而易見的資訊。思考哪些程序性知識、領域專屬的細節或可重用的素材，能幫助另一個 Codex 實例更有效地執行這些任務。

#### 從可重用的技能內容開始

開始實作時，從上面找出的可重用資源開始：`scripts/`、`references/` 與 `assets/` 檔案。注意這一步可能需要使用者的輸入。例如，在實作 `brand-guidelines` 技能時，使用者可能需要提供要存放在 `assets/` 中的品牌素材或範本，或要存放在 `references/` 中的文件。

加入的腳本必須透過實際執行來測試，以確保沒有 bug 且輸出符合預期。如果有很多類似的腳本，只需要測試具代表性的樣本，在確保全部都能運作的信心與完成所需時間之間取得平衡。

如果你使用了 `--examples`，刪除技能不需要的任何占位檔。只建立實際需要的資源目錄。

#### 更新 SKILL.md

**撰寫準則：** 一律使用祈使/不定詞形式。

##### 前置資料

以 `name` 與 `description` 撰寫 YAML 前置資料：

- `name`：技能名稱
- `description`：這是你的技能的主要觸發機制，幫助 Codex 理解何時使用該技能。
  - 同時包含技能做什麼，以及何時使用它的具體觸發條件/情境。
  - 把所有「何時使用」的資訊都放在這裡——不要放在內文中。內文只在觸發之後才載入，所以內文中的「何時使用本技能」章節對 Codex 沒有幫助。
  - `docx` 技能的描述範例：「全面的文件建立、編輯與分析，支援追蹤修訂、註解、格式保留與文字擷取。當 Codex 需要處理專業文件（.docx 檔）以進行：(1) 建立新文件、(2) 修改或編輯內容、(3) 處理追蹤修訂、(4) 加入註解，或任何其他文件任務時使用」

不要在 YAML 前置資料中包含任何其他欄位。

##### 內文

撰寫使用技能及其內附資源的說明。

### 步驟 6：迭代

測試技能之後，使用者可能會要求改進。這通常發生在剛使用完技能、對技能的表現記憶猶新的時候。

**迭代流程：**

1. 在真實任務上使用技能
2. 留意卡關或沒有效率之處
3. 找出 SKILL.md 或內附資源應該如何更新
4. 實作變更並再次測試
