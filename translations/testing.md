# 測試

本技能提供全方位的測試能力，包括測試策略、自動化設定、測試驅動開發（TDD）、測試撰寫最佳實務、覆蓋率分析、CI/CD 整合，以及用 Playwright 測試網頁應用。

## 何時使用本技能

- 為專案建立測試基礎設施時
- 建立測試策略與測試計畫時
- 撰寫單元、整合或 E2E 測試時
- 實作 TDD／測試先行的開發時
- 分析測試覆蓋率與品質時
- 把測試整合進 CI/CD 流水線時
- 用 Playwright 測試網頁應用時
- 除錯測試失敗或改善測試可靠性時
- 撰寫測試 fixture、mock 資料或 factory 函式時
- mock 外部相依（API、資料庫、檔案系統）時
- 組織測試檔案結構與測試組時
- 測試非同步程式碼、Promise 或事件驅動的行為時
- 為 UI 元件實作快照測試時
- 設定測試覆蓋率門檻時

## 本技能做什麼

1. **測試策略**：設計全面的測試策略（單元、整合、E2E）
2. **測試自動化**：建立測試框架與自動化工具
3. **TDD 方法**：實作測試驅動開發的工作流程（紅—綠—重構）
4. **撰寫測試**：以適當的模式撰寫聚焦、可維護的測試
5. **覆蓋率分析**：分析並改善測試覆蓋率
6. **CI/CD 整合**：把測試整合進持續整合流水線
7. **網頁應用測試**：使用 Playwright 測試網頁應用
8. **測試品質**：改善測試的可靠性與可維護性

## 測試策略

### 測試金字塔

**建議的分配：**

- **單元測試**：70% —— 快速、隔離、測試個別函式
- **整合測試**：20% —— 測試元件之間的互動
- **E2E 測試**：10% —— 測試完整的使用者工作流程

**測試類型：**

- 功能測試（順利路徑、邊界情況、錯誤處理）
- 非功能測試（效能、安全、無障礙）
- 回歸測試（防止破壞性變更）
- 冒煙測試（關鍵路徑驗證）

### 框架選擇

**JavaScript/TypeScript：**

- 單元／整合用 Jest、Vitest、Mocha
- E2E 用 Playwright、Cypress
- 元件測試用 React Testing Library

**Python：**

- 單元／整合用 pytest
- E2E 用 Selenium、Playwright
- 標準函式庫測試用 unittest

**Java：**

- 單元測試用 JUnit
- 整合用 TestNG
- E2E 用 Selenium

**Go：**

- 內建的 testing 套件
- 斷言用 Testify

**Rust：**

- 內建的測試框架
- 用 Cargo test 執行測試

## 測試驅動開發（TDD）

TDD 是一種 **設計技巧**，不只是測試技巧。它透過小而有紀律的步驟，產出設計更好、更容易維護的程式碼。

### 核心原則

**先寫測試，再寫程式碼。永遠如此。** TDD 迫使你思考：

- 我需要什麼行為？
- 我怎麼知道它能運作？
- 最簡單的實作是什麼？

### 三大定律（絕不違反）

1. 沒有先寫一個失敗的測試，**絕不寫任何正式程式碼**
2. **只寫足夠的測試**來呈現一個失敗
3. **只寫足夠的程式碼**讓那個測試通過

### 紅—綠—重構循環

**階段 1：紅——寫一個失敗的測試**

1. 寫「一個」定義預期行為的測試
2. 執行測試——確認它「失敗」
3. 確認它因為「正確的」原因失敗（不是語法錯誤）
4. 還「不要」寫實作

**階段 2：綠——最小實作**

1. 寫「最少的」程式碼讓測試通過
2. 抗拒加入額外功能的衝動
3. 執行測試——確認它「通過」
4. 如果測試仍然失敗，修正實作（不是測試）

**階段 3：重構——整理程式碼**

1. 移除重複的程式碼（DRY）
2. 改善命名讓它更清楚
3. 把複雜的邏輯抽成函式
4. 執行「所有」測試——全程必須保持綠燈
5. 檢查變更行的測試覆蓋率

重構之後，為下一個行為開始新的紅燈階段。

## 覆蓋率分析

### 覆蓋率目標

**建議的門檻：**

- **行**：80%+
- **函式**：80%+
- **分支**：80%+
- **敘述**：80%+

**關鍵路徑：**

- 關鍵的商業邏輯一律以 100% 覆蓋為目標
- 認證與授權
- 金流處理
- 資料驗證

### 覆蓋率缺口

**常見缺口：**

- 錯誤處理路徑
- 邊界情況
- 臨界條件
- 整合點

**改善策略：**

- 找出沒有被測試的程式碼路徑
- 為錯誤情境加入測試
- 測試邊界情況與臨界值
- 提高整合測試的覆蓋率

## CI/CD 整合

### 測試流水線

**階段：**

1. **單元測試**：快速回饋，每次提交都執行
2. **整合測試**：在 pull request 上執行
3. **E2E 測試**：合併到 main 之前執行
4. **效能測試**：在 main 分支上執行

**品質關卡：**

- 所有測試必須通過
- 覆蓋率必須達到門檻
- 沒有嚴重的安全問題
- 達到效能基準

## 用 Playwright 測試網頁應用

### 輔助腳本

本技能在 `scripts/` 中包含 Python 輔助腳本：

- **`with_server.py`** —— 管理伺服器的生命週期（支援多個伺服器）。一律先用 `--help` 執行以查看用法。

  ```bash
  # Single server
  python scripts/with_server.py --server "npm run dev" --port 5173 -- python your_automation.py

  # Multiple servers (e.g., backend + frontend)
  python scripts/with_server.py \
    --server "cd backend && python server.py" --port 3000 \
    --server "cd frontend && npm run dev" --port 5173 \
    -- python your_automation.py
  ```

## 最佳實務

### 測試品質

1. **隔離**：測試應該彼此獨立，可以任意順序執行
2. **確定性**：測試應該產生一致的結果
3. **快速**：單元測試應該執行得很快（每個 < 100ms）
4. **清楚**：測試名稱應該描述它測試什麼
5. **可維護**：程式碼變更時，測試應該容易更新

### TDD 最佳實務

1. **每個測試一個行為**：每個測試驗證「一個」行為
2. **具描述性的名稱**：測試名稱描述被測試的行為
3. **獨立的測試**：測試之間不互相依賴
4. **快速的測試**：mock 外部相依以保持測試快速
5. **清楚的斷言**：斷言清楚地呈現在驗證什麼

### 要避免的常見錯誤

- ❌ 一次寫多個測試（一次寫一個測試）
- ❌ 跳過重構階段（綠燈後一律重構）
- ❌ 先實作再寫測試（刪掉程式碼，從測試開始）
- ❌ 在綠燈階段過度設計（能通過的最簡單做法）
- ❌ 寫出一開始就通過的測試（必須先失敗）

### 測試維護

- 需求改變時審查並更新測試
- 移除過時的測試
- 重構測試以減少重複
- 讓測試資料 factory 保持最新
- 監控測試執行時間
