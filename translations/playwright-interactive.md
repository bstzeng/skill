# Playwright 互動式技能

使用一個常駐的 `js_repl` Playwright 工作階段來除錯本機的網頁或 Electron 應用程式，在多次反覆之間保持相同的控制代碼存活，並執行功能 QA 加上視覺 QA，除非程序的擁有權改變，否則不必重啟整套工具鏈。

- 本技能必須啟用 `js_repl`。

- 你也可以用 `--enable js_repl` 開啟新的工作階段（等同於 `-c features.js_repl=true`）。
- 啟用 `js_repl` 之後，開啟一個新的 Codex 工作階段，讓工具清單重新整理。
- 目前請在停用沙箱的情況下執行這個工作流程：以 `--sandbox danger-full-access`（或等同於 `sandbox_mode=danger-full-access` 的設定）啟動 Codex。這是在沙箱內的 `js_repl` + Playwright 支援尚未完成期間的暫時性要求。
- 在你需要除錯的同一個專案目錄中執行安裝設定。
- 把 `js_repl_reset` 當作復原工具，而不是例行清理。重設核心會摧毀你的 Playwright 控制代碼。

## 核心工作流程

1. 測試前先寫一份簡短的 QA 清單：
   - 從三個來源建立清單：使用者要求的需求、你實際實作的使用者可見功能或行為，以及你預期在最終回應中提出的主張。
   - 在這三個來源中出現的任何項目，在簽核之前都必須對應到至少一項 QA 檢查。
   - 列出你打算簽核的使用者可見主張。
   - 列出每一個有意義的使用者面向控制項、模式切換或已實作的互動行為。
   - 列出每個控制項或已實作行為可能造成的狀態變化或畫面變化。
   - 把這份清單當作功能 QA 與視覺 QA 共用的涵蓋範圍清單。
   - 對每一個主張或「控制項－狀態」組合，記下預定的功能檢查、必須進行視覺檢查的特定狀態，以及你預期擷取的證據。
   - 如果某項需求在視覺上很核心但很主觀，就把它轉換成可觀察的 QA 檢查，而不是讓它隱而不宣。
   - 加入至少 2 個可能暴露脆弱行為的探索性或非順利路徑情境。
2. 執行一次 bootstrap 區塊。
3. 在常駐的 TTY 工作階段中啟動或確認任何需要的開發伺服器。
4. 啟動正確的執行環境，並持續重用相同的 Playwright 控制代碼。
5. 每次程式碼變更後，僅限渲染器的變更就重新載入，主程序／啟動相關的變更就重新啟動。
6. 用一般的使用者輸入執行功能 QA。
7. 執行一輪獨立的視覺 QA。
8. 確認視窗適配，並擷取支持你主張所需的截圖。
9. 只有在任務真的完成時，才清理 Playwright 工作階段。

## 選擇工作階段模式

對於網頁應用程式，預設使用明確的 viewport，並把原生視窗模式當作另一輪獨立的驗證。

- 例行的反覆修改、斷點檢查、可重現的截圖、快照比對與模型輔助的定位，都使用明確的 viewport。這是預設，因為它在不同機器間都很穩定，並避免了主機視窗管理員的變異。
- 當你需要確定性的高 DPI 行為時，保留明確的 viewport 並加上 `deviceScaleFactor`，而不是直接切換到原生視窗模式。
- 當你需要驗證啟動時的視窗大小、作業系統層級的 DPI 行為、瀏覽器外框的互動，或可能取決於主機顯示設定的 bug 時，使用原生視窗模式（`viewport: null`）做一輪獨立的有頭（headed）檢查。
- 對於 Electron，一律假設是原生視窗行為。Electron 透過 Playwright 以 `noDefaultViewport` 啟動，所以把它當成真正的桌面視窗，並在調整任何大小之前先檢查啟動時的大小與版面。
- 當簽核同時取決於版面斷點與真實的桌面行為時，兩輪都要做：先用明確的 viewport 做確定性的 QA，再用原生視窗驗證做最終的環境特定檢查。
- 把切換模式視為重設 context。不要把模擬 viewport 的 `context` 重用於原生視窗那一輪，反之亦然；關閉舊的 `page` 與 `context`，然後為新模式建立新的。

## 檢查清單

### 工作階段循環

- Bootstrap `js_repl` 一次，然後在多次反覆之間保持相同的 Playwright 控制代碼存活。
- 從目前的工作區啟動目標執行環境。
- 進行程式碼變更。
- 依該變更使用正確的方式重新載入或重新啟動。
- 如果探索中發現額外的控制項、狀態或可見主張，就更新共用的 QA 清單。
- 重新執行功能 QA。
- 重新執行視覺 QA。
- 只有在目前的狀態就是你要評估的狀態時，才擷取最終產物。

### 重新載入的判斷

- 僅限渲染器的變更：重新載入既有的 page 或 Electron 視窗。
- 主程序、preload 或啟動相關的變更：重新啟動 Electron。
- 對程序擁有權或啟動程式碼出現新的不確定：重新啟動，而不是用猜的。

### 功能 QA

- 簽核時使用真實的使用者控制：鍵盤、滑鼠、點擊、觸控，或等效的 Playwright 輸入 API。
- 至少驗證一條端到端的關鍵流程。
- 確認該流程的可見結果，而不只是內部狀態。
- 對於即時或大量動畫的應用程式，在實際的互動時序下驗證行為。
- 依照共用的 QA 清單逐項進行，而不是臨時抽查。
- 在簽核前，每一個明顯可見的控制項至少都要涵蓋一次，而不只是主要的順利路徑。
- 對於清單中可逆的控制項或有狀態的切換，測試完整的循環：初始狀態、改變後的狀態，以及回到初始狀態。
- 腳本化的檢查通過後，用一般輸入做 30–90 秒的簡短探索，而不是只走預定的路徑。
- 如果探索揭露了新的狀態、控制項或主張，就把它加入共用的 QA 清單，並在簽核前涵蓋它。
- `page.evaluate(...)` 與 `electronApp.evaluate(...)` 可以檢查或佈置狀態，但不算作簽核用的輸入。

### 視覺 QA

- 把視覺 QA 與功能 QA 分開看待。
- 使用測試前定義、並在 QA 期間更新的同一份共用 QA 清單；不要從另一份隱含的清單開始視覺涵蓋。
- 重述使用者可見的主張，並明確逐一驗證；不要假設功能通過就能證明視覺主張。
- 一個使用者可見的主張，在它應被感知的特定狀態中被檢查之前，都不算簽核。
- 捲動之前先檢查初始的 viewport。
- 確認初始畫面明顯支持介面的主要主張；如果某個核心承諾的元素在那裡無法清楚察覺，就視為 bug。
- 檢查所有必要的可見區域，而不只是主要的互動介面。
- 檢查共用 QA 清單中已列出的狀態與模式，當任務是互動式時，至少包含一個有意義的互動後狀態。
- 如果動態或轉場是體驗的一部分，除了穩定後的終點，至少還要檢查一個轉場中的狀態。
- 如果標籤、疊加層、註解、導引或高亮應該追蹤變動的內容，在相關狀態變化後驗證這個關係。
- 對於動態或取決於互動的視覺，檢查夠久以判斷穩定性、圖層與可讀性；不要靠單一張截圖簽核。
- 對於載入或互動後可能變得更密集的介面，檢查你在 QA 中能達到的最密集的真實狀態，而不只是空白、載入中或收合的狀態。
- 如果產品有定義的最小支援 viewport 或視窗大小，就在那個大小做一輪獨立的視覺 QA；否則，選一個較小但仍真實的大小並明確檢查。
- 區分「存在」與「實作好」：如果一個預定的操作提示技術上存在，但因為對比太弱、被遮擋、被裁切或不穩定而無法清楚察覺，就視為視覺失敗。
- 在你評估的狀態中，如果任何必要的可見區域被裁切、截斷、遮擋或被推到 viewport 之外，即使頁面層級的捲動數值看起來可以接受，也要視為 bug。
- 尋找裁切、溢出、變形、版面失衡、間距不一致、對齊問題、難以閱讀的文字、對比太弱、圖層錯亂與彆扭的動態狀態。
- 除了正確性，也要判斷美感品質。UI 應該讓人感覺是有意為之、一致，並且就這個任務而言賞心悅目。
- 簽核時偏好 viewport 截圖。整頁截圖只作為次要的除錯產物，當某個區域需要更仔細檢查時，擷取一張聚焦的截圖。
- 如果動態讓截圖模稜兩可，稍等 UI 穩定下來，再擷取你真正要評估的畫面。
- 簽核前，明確問自己：這個介面有哪個可見的部分我還沒有仔細檢查過？
- 簽核前，明確問自己：如果使用者仔細看，哪個可見的缺陷最可能讓這個成果出糗？

### 簽核

- 功能路徑以一般使用者輸入通過。
- 涵蓋範圍明確對照共用的 QA 清單：註明實際演練了哪些需求、已實作的功能、控制項、狀態與主張，並指出任何刻意排除的項目。
- 視覺 QA 涵蓋了整個相關介面。
- 每一個使用者可見的主張，都有對應的視覺檢查，以及在該主張重要的狀態與 viewport 或視窗大小下擷取並審閱過的截圖產物。
- 預定的初始畫面，以及任何必要的最小支援 viewport 或視窗大小，都通過了視窗適配檢查。
- 如果產品是在視窗中啟動，在任何手動調整大小或重新定位之前，已檢查過啟動時的大小、位置與初始版面。
- UI 不只是能用；就這個任務而言，它在視覺上是一致的，美感上也不薄弱。
- 功能正確性、視窗適配與視覺品質必須各自通過；其中一項通過不代表其他項目也通過。
- 對於互動式產品，已完成簡短的探索，且回應中提到了那次探索涵蓋了什麼。
- 如果截圖審閱與數值檢查在任何時候出現分歧，在簽核前已調查過這個差異；截圖中可見的裁切是需要解決的失敗，而不是數值可以推翻的。
- 簡短地附上負面確認：你檢查過、但沒有發現的主要缺陷類別。
- 已執行清理，或你刻意讓工作階段保持存活以便後續工作。

## 截圖範例

如果你打算透過 `codex.emitImage(...)` 輸出截圖，預設使用下一節中正規化為 CSS 的路徑。那些是會被模型解讀、或用於基於座標之後續動作的截圖的標準範例。原始擷取只作為對保真度敏感之除錯的例外；原始擷取的例外範例放在正規化指引之後。

### 給模型看的截圖（預設）

如果你會用 `codex.emitImage(...)` 輸出截圖讓模型解讀，在輸出之前，把你擷取的那個確切區域正規化為 CSS 像素。這樣一來，如果之後用回覆來點擊，回傳的座標會與 Playwright 的 CSS 像素對齊，同時也能減少圖片資料大小與模型的 token 成本。

預設不要輸出原始的原生視窗截圖。只有在你明確需要裝置像素的保真度時才跳過正規化，例如 Retina 或 DPI 瑕疵的除錯、像素精確的渲染檢查，或其他原始像素比資料大小更重要的保真度敏感情境。對於不會輸出給模型、只在本機檢查的情況，原始擷取沒問題。

不要假設在原生視窗模式（`viewport: null`）下 `page.screenshot({ scale: "css" })` 就夠了。在 macOS Retina 顯示器上的 Chromium，有頭的原生視窗截圖即使要求了 `scale: "css"`，仍可能以裝置像素大小回傳。同樣的注意事項也適用於透過 Playwright 啟動的 Electron 視窗，因為 Electron 以 `noDefaultViewport` 執行，`appWindow.screenshot({ scale: "css" })` 仍可能回傳裝置像素的輸出。

網頁與 Electron 視窗使用不同的正規化路徑：

- 網頁：偏好直接使用 `page.screenshot({ scale: "css" })`。如果原生視窗的 Chromium 仍回傳裝置像素的輸出，就在目前的頁面內用 canvas 調整大小；不需要暫用頁面。
- Electron：不要把 `appWindow.context().newPage()` 或 `electronApp.context().newPage()` 當作暫用頁面。Electron 的 context 無法可靠地支援這條路徑。在主程序中用 `BrowserWindow.capturePage(...)` 擷取，用 `nativeImage.resize(...)` 調整大小，並直接輸出那些位元組。

## 視窗適配檢查（必要）

不要因為主要元件可見，就假設截圖可以接受。簽核前，同時用截圖審閱與數值檢查，明確驗證預定的初始畫面符合產品需求。

- 簽核前先定義預定的初始畫面。對於可捲動的頁面，這是首屏（above-the-fold）的體驗。對於類似應用程式的外殼、遊戲、編輯器、儀表板或工具，這是完整的互動介面加上使用它所需的控制項與狀態。
- 把截圖當作適配的主要證據。數值檢查是用來支持截圖的；它們不能推翻可見的裁切。
- 在預定的初始畫面中，如果任何必要的可見區域被裁切、截斷、遮擋或被推到 viewport 之外，即使頁面層級的捲動數值看起來可以接受，簽核也算失敗。
- 當產品本來就設計為可捲動，而且初始畫面仍傳達核心體驗、並露出主要的行動呼籲或必要的起始情境時，捲動是可以接受的。
- 對於固定外殼的介面，如果需要捲動才能到達主要互動介面的一部分或必要的控制項，捲動就不是可接受的權宜之計。
- 不要只依賴文件的捲動數值。固定高度的外殼、內部窗格與隱藏溢出的容器，可能會裁切必要的 UI，而頁面層級的捲動檢查看起來仍然正常。
- 檢查區域的邊界，而不只是文件的邊界。驗證每一個必要的可見區域在啟動狀態下都能放進 viewport。
- 對於 Electron 或桌面應用程式，在任何手動調整大小或重新定位之前，同時驗證啟動時的視窗大小與位置，以及渲染器的初始可見版面。
- 通過視窗適配檢查只證明預定的初始畫面可見、沒有非預期的裁切或捲動。它不能證明 UI 在視覺上正確或美感上成功。

## 常見的失敗模式

- `Cannot find module 'playwright'`：在目前的工作區執行一次性設定，並在使用 `js_repl` 之前確認能 import。
- Playwright 套件已安裝但缺少瀏覽器執行檔：執行 `npx playwright install chromium`。
- `page.goto: net::ERR_CONNECTION_REFUSED`：確認開發伺服器仍在常駐的 TTY 工作階段中執行，重新檢查連接埠，並偏好使用 `http://127.0.0.1:<port>`。
- `electron.launch` 卡住、逾時或立即結束：確認本機的 `electron` 相依套件，確認 `args` 目標，並確保任何渲染器開發伺服器在啟動前就已在執行。
- `Identifier has already been declared`：重用既有的頂層綁定、換一個新名字，或把程式碼包在 `{ ... }` 中。只有在核心真的卡住時才使用 `js_repl_reset`。
- 處理 Electron 時出現 `browserContext.newPage: Protocol error (Target.createTarget): Not supported`：不要把 `appWindow.context().newPage()` 或 `electronApp.context().newPage()` 當作暫用頁面；使用「給模型看的截圖」一節中 Electron 專用的截圖正規化流程。
- `js_repl` 逾時或被重設：重新執行 bootstrap 區塊，並用更短、更聚焦的區塊重建工作階段。
- 瀏覽器啟動或網路操作立即失敗：確認工作階段是以 `--sandbox danger-full-access` 啟動，必要時以該方式重新啟動。
