# 技能製作器（Skill Creator）

一個用來建立新技能、並反覆改進它們的技能。

從高層來看，建立技能的流程是這樣的：

- 決定你想讓技能做什麼，以及大致上要怎麼做
- 撰寫技能的草稿
- 設計幾個測試提示，並在其上執行「可使用該技能的 Claude」
- 協助使用者以定性與定量方式評估結果
  - 在執行於背景進行的同時，如果還沒有定量評估就先草擬一些（如果已經有，你可以照用，或在你覺得需要時修改）。然後向使用者解釋它們（如果原本就有，就解釋現有的那些）
  - 使用 `eval-viewer/generate_review.py` 腳本把結果呈現給使用者看，也讓他們查看定量指標
- 根據使用者對結果的評估回饋改寫技能（以及若定量評測中出現任何明顯缺陷時）
- 重複直到滿意為止
- 擴大測試集，以更大規模再試一次

使用本技能時，你的工作是判斷使用者處在這個流程的哪個位置，然後介入協助他們推進各階段。例如，他們可能會說「我想做一個做 X 的技能」。你可以幫忙縮小他們的意思、撰寫草稿、撰寫測試案例、了解他們想怎麼評估、執行所有提示，然後重複。

另一方面，他們可能已經有技能的草稿了。這種情況下，你可以直接進入循環中的評估/迭代部分。

當然，你應該永遠保持彈性，如果使用者說「我不需要跑一堆評估，就跟著感覺走吧」，你也可以照做。

然後在技能完成之後（但順序同樣是有彈性的），你還可以執行技能描述改進器——我們有一個獨立的腳本專門做這件事——來優化技能的觸發。

懂了嗎？懂了。

## 與使用者溝通

使用技能製作器的人，對程式術語的熟悉程度差異很大。如果你還沒聽說（你怎麼可能聽說，這是最近才開始的），現在有一股趨勢：Claude 的能力正激勵水電工打開他們的終端機，父母和祖父母上網搜尋「如何安裝 npm」。另一方面，大部分使用者可能都相當熟悉電腦。

所以請留意脈絡線索，了解該如何措辭！在預設情況下，給你一點概念：

- 「評估（evaluation）」與「評測（benchmark）」處於邊緣，但還可以
- 對於「JSON」與「斷言（assertion）」，在未加解釋就使用之前，你需要看到使用者明確知道這些是什麼的線索

如果有疑慮，簡短解釋術語是可以的；如果你不確定使用者是否懂，可以隨時附上簡短的定義來說明術語。

## 建立技能

### 捕捉意圖

從理解使用者的意圖開始。目前的對話可能已經包含使用者想要捕捉的工作流程（例如他們說「把這個變成一個技能」）。如果是這樣，先從對話歷史中擷取答案——使用的工具、步驟順序、使用者做過的修正、觀察到的輸入/輸出格式。使用者可能需要補足缺口，並應在進入下一步之前確認。

1. 這個技能應該讓 Claude 能做什麼？
2. 這個技能應該在什麼時候觸發？（使用者的哪些說法/情境）
3. 預期的輸出格式是什麼？
4. 我們應該建立測試案例來驗證技能有效嗎？輸出可客觀驗證的技能（檔案轉換、資料擷取、程式碼生成、固定的工作流程步驟）能從測試案例中受益。輸出主觀的技能（寫作風格、藝術）通常不需要。依技能類型建議適當的預設做法，但讓使用者決定。

### 訪談與研究

主動詢問關於邊界情況、輸入/輸出格式、範例檔案、成功標準與相依項目的問題。在這部分釐清之前，先不要撰寫測試提示。

檢查可用的 MCP——如果對研究有用（搜尋文件、尋找類似技能、查詢最佳實踐），在有子代理時透過子代理平行研究，否則直接進行。帶著脈絡準備好，減少使用者的負擔。

### 撰寫 SKILL.md

根據使用者訪談，填入這些組成部分：

- **name**：技能識別名稱
- **description**：何時觸發、做什麼。這是主要的觸發機制——要同時包含技能做什麼「以及」何時使用的具體情境。所有「何時使用」的資訊都放在這裡，而不是內文中。注意：目前 Claude 有「觸發不足」的傾向——在技能有用時卻不使用它們。為了對抗這點，請把技能描述寫得稍微「強勢」一點。例如，與其寫「如何建立一個簡單快速的儀表板來顯示 Anthropic 內部資料」，你可以寫「如何建立一個簡單快速的儀表板來顯示 Anthropic 內部資料。只要使用者提到儀表板、資料視覺化、內部指標，或想顯示任何種類的公司資料，即使他們沒有明確要求『儀表板』，也務必使用這個技能。」
- **compatibility**：必要的工具、相依項目（選填，很少需要）
- **技能的其餘部分 :)**

### 寫作風格

試著向模型解釋為什麼某些事很重要，而不是用沉重陳腐的「必須」。運用心智理論，試著讓技能具通用性，而不是極度狹隘地只適用於特定範例。先寫出草稿，然後以全新的眼光審視並改進它。

## 執行與評估測試案例

本節是一個連續的流程——不要中途停下。**不要**使用 `/skill-test` 或任何其他測試技能。

把結果放在與技能目錄同層的 `<skill-name>-workspace/` 中。在工作區內，依迭代組織結果（`iteration-1/`、`iteration-2/` 等），其中每個測試案例各有一個目錄（`eval-0/`、`eval-1/` 等）。不要一開始就建立全部——邊進行邊建立目錄即可。

### 步驟 2：在執行進行時草擬斷言

不要只是等執行完成——你可以有效利用這段時間。為每個測試案例草擬定量斷言，並向使用者解釋。如果 `evals/evals.json` 中已有斷言，就檢閱它們並解釋它們檢查什麼。

好的斷言可客觀驗證，並有具描述性的名稱——它們在評測檢視器中應該清楚易讀，讓快速瀏覽結果的人立刻理解每個斷言檢查什麼。主觀的技能（寫作風格、設計品質）較適合定性評估——不要把斷言硬套在需要人類判斷的事物上。

草擬完成後，用斷言更新 `eval_metadata.json` 檔與 `evals/evals.json`。也要向使用者解釋他們將在檢視器中看到什麼——定性輸出與定量評測都要。

### 步驟 4：評分、彙整並啟動檢視器

所有執行都完成後：

1. **為每個執行評分**——產生一個評分子代理（或直接評分），讓它閱讀 `agents/grader.md` 並根據輸出評估每個斷言。把結果存到每個執行目錄中的 `grading.json`。grading.json 的 expectations 陣列必須使用 `text`、`passed` 與 `evidence` 欄位（而不是 `name`/`met`/`details` 或其他變體）——檢視器依賴這些確切的欄位名稱。對於可以用程式檢查的斷言，撰寫並執行腳本，而不是用肉眼看——腳本更快、更可靠，而且可以跨迭代重用。

2. **彙整成評測**——從 skill-creator 目錄執行彙整腳本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   這會產生 `benchmark.json` 與 `benchmark.md`，包含每種設定的通過率、時間與 token 數，附平均值 ± 標準差以及差值。如果手動產生 benchmark.json，檢視器預期的確切 schema 請見 `references/schemas.md`。
把每個 with_skill 版本放在其基準對照之前。

3. **進行分析** ——閱讀評測資料，找出彙整統計可能隱藏的模式。要注意什麼請見 `agents/analyzer.md`（「Analyzing Benchmark Results」一節）——例如不論有沒有技能都一定通過的斷言（無鑑別力）、高變異的評估（可能不穩定），以及時間/token 的取捨。

4. **啟動檢視器**，同時呈現定性輸出與定量資料：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   第 2 次以後的迭代，還要傳入 `--previous-workspace <workspace>/iteration-<N-1>`。

   **Cowork / 無頭環境：** 如果無法使用 `webbrowser.open()`，或環境沒有顯示器，就使用 `--static <output_path>` 寫出一個獨立的 HTML 檔，而不是啟動伺服器。當使用者點擊「Submit All Reviews」時，回饋會下載成 `feedback.json` 檔。下載後，把 `feedback.json` 複製到工作區目錄，供下一次迭代讀取。

注意：請使用 generate_review.py 建立檢視器；不需要自己寫客製的 HTML。

5. **告訴使用者**類似這樣的話：「我已經在你的瀏覽器中開啟結果。有兩個分頁——『Outputs』讓你逐一點閱每個測試案例並留下回饋，『Benchmark』顯示定量比較。看完後回到這裡告訴我。」

### 使用者在檢視器中看到什麼

「Outputs」分頁一次顯示一個測試案例：
- **Prompt**：所給的任務
- **Output**：技能產出的檔案，盡可能直接渲染
- **Previous Output**（第 2 次以後的迭代）：摺疊區塊，顯示上一次迭代的輸出
- **Formal Grades**（如果有執行評分）：摺疊區塊，顯示斷言通過/失敗
- **Feedback**：一個會在輸入時自動儲存的文字框
- **Previous Feedback**（第 2 次以後的迭代）：他們上次的意見，顯示在文字框下方

「Benchmark」分頁顯示統計摘要：每種設定的通過率、時間與 token 用量，以及每個評估的細目與分析觀察。

透過上一個/下一個按鈕或方向鍵瀏覽。完成時，他們點擊「Submit All Reviews」，把所有回饋存到 `feedback.json`。

## 改進技能

這是循環的核心。你已經執行了測試案例，使用者也審閱了結果，現在你需要根據他們的回饋讓技能變得更好。

### 如何思考改進

1. **從回饋中歸納。** 這裡發生的大局是：我們試著建立能被使用上百萬次（也許字面上就是，也許更多，誰知道）、跨越許多不同提示的技能。你和使用者在這裡只反覆迭代少數幾個範例，是因為這樣能推進得更快。使用者對這些範例瞭若指掌，評估新輸出很快。但如果你和使用者共同開發的技能只對那些範例有效，它就毫無用處。與其加入瑣碎的過度擬合修改，或令人窒息的嚴格「必須」，如果有某個頑固的問題，你可以試著擴展思路、使用不同的比喻，或建議不同的工作模式。嘗試的成本相對低，也許你會找到很棒的東西。

2. **讓提示保持精簡。** 移除沒有發揮作用的東西。務必閱讀逐字紀錄，而不只是最終輸出——如果看起來技能讓模型浪費大量時間做沒有生產力的事，你可以試著拿掉造成這種行為的技能部分，看看會發生什麼。

3. **解釋為什麼。** 努力解釋你要求模型做的每件事背後的**原因**。今天的 LLM 很*聰明*。它們有良好的心智理論，在好的架構下能超越死板的指示，真正把事情做成。即使使用者的回饋很簡短或帶著挫折，也要試著真正理解任務、使用者為什麼這樣寫、以及他們實際寫了什麼，然後把這份理解傳達到指示中。如果你發現自己在用全大寫寫 ALWAYS 或 NEVER，或使用超級死板的結構，那是一個黃色警訊——可能的話，換個框架並解釋理由，讓模型理解你要求的事為什麼重要。那是更人性、更有力、也更有效的做法。

4. **找出測試案例間的重複工作。** 閱讀測試執行的逐字紀錄，注意子代理是否都各自寫了類似的輔助腳本，或對某件事採取了同樣的多步驟做法。如果 3 個測試案例都讓子代理寫了一個 `create_docx.py` 或 `build_chart.py`，這就是技能應該內附該腳本的強烈訊號。寫一次，放進 `scripts/`，並告訴技能使用它。這能讓未來的每次呼叫都不必重新發明輪子。

這項任務相當重要（我們在這裡試圖每年創造數十億美元的經濟價值！），而你的思考時間不是瓶頸；慢慢來，好好反覆思量。我建議先寫出修訂草稿，再以全新的眼光審視並改進。真心盡力進入使用者的腦袋，理解他們想要與需要什麼。

### 迭代循環

改進技能之後：

1. 把你的改進套用到技能上
2. 把所有測試案例重新執行到新的 `iteration-<N+1>/` 目錄中，包括基準執行。如果你在建立新技能，基準永遠是 `without_skill`（沒有技能）——它在各次迭代中保持不變。如果你在改進既有技能，就自行判斷什麼適合作為基準：使用者帶來的原始版本，或上一次迭代。
3. 以指向上一次迭代的 `--previous-workspace` 啟動審閱器
4. 等待使用者審閱並告訴你他們完成了
5. 閱讀新的回饋、再次改進、重複

持續進行，直到：
- 使用者說他們滿意了
- 回饋全都是空的（一切看起來都很好）
- 你沒有取得有意義的進展

## 進階：盲測比較

當你想對技能的兩個版本做更嚴謹的比較時（例如使用者問「新版本真的比較好嗎？」），有一套盲測比較系統。細節請閱讀 `agents/comparator.md` 與 `agents/analyzer.md`。基本概念是：把兩個輸出交給一個獨立的代理，不告訴它哪個是哪個，讓它判斷品質。然後分析勝出者為什麼勝出。

這是選用的，需要子代理，大多數使用者用不到。人工審閱循環通常就足夠了。

## 描述優化

SKILL.md 前置資料中的 description 欄位，是決定 Claude 是否呼叫技能的主要機制。建立或改進技能之後，主動提議優化描述以提升觸發準確率。

### 步驟 1：產生觸發評估查詢

建立 20 個評估查詢——混合「應觸發」與「不應觸發」的情況。存成 JSON：

{{CODE:11}}

查詢必須真實，是 Claude Code 或 Claude.ai 使用者真正會輸入的內容。不是抽象的請求，而是具體、明確、有相當細節的請求。例如檔案路徑、關於使用者工作或處境的個人脈絡、欄位名稱與值、公司名稱、URL。一點點背景故事。有些可能是小寫，或包含縮寫、錯字或口語。混合使用不同長度，並聚焦在邊界案例，而不是讓它們涇渭分明（使用者會有機會確認它們）。

不好：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

好：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`（「好，我老闆剛寄給我這個 xlsx 檔（在我的下載資料夾，檔名大概是 'Q4 sales final FINAL v2.xlsx'），她要我加一欄顯示利潤率百分比。營收應該在 C 欄、成本在 D 欄吧」）

對於**應觸發**的查詢（8–10 個），考慮涵蓋範圍。你需要同一意圖的不同說法——有些正式、有些隨意。包含使用者沒有明確點名技能或檔案類型、但顯然需要它的情況。加入一些不常見的使用情境，以及這個技能與其他技能競爭但應該勝出的情況。

對於**不應觸發**的查詢（8–10 個），最有價值的是差一點就命中的那些——與技能共享關鍵字或概念、但其實需要不同東西的查詢。想想相鄰的領域、天真的關鍵字比對會觸發但不應該觸發的模糊措辭，以及查詢觸及技能能做的事、但在那個情境下其他工具更合適的情況。

要避免的關鍵：不要讓不應觸發的查詢明顯無關。拿「寫一個費氏數列函式」當 PDF 技能的負面測試太簡單了——它什麼都沒測到。負面案例應該真的有難度。

### 步驟 2：與使用者一起審閱

使用 HTML 模板把評估集呈現給使用者審閱：

1. 從 `assets/eval_review.html` 讀取模板
2. 替換占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 評估項目的 JSON 陣列（外面不加引號——這是 JS 變數指定）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能的名稱
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能目前的描述
3. 寫入暫存檔（例如 `/tmp/eval_review_<skill-name>.html`）並開啟：`open /tmp/eval_review_<skill-name>.html`
4. 使用者可以編輯查詢、切換是否應觸發、新增/移除項目，然後點擊「Export Eval Set」
5. 檔案會下載到 `~/Downloads/eval_set.json`——如果有多個（例如 `eval_set (1).json`），檢查下載資料夾中最新的版本

這一步很重要——不好的評估查詢會產生不好的描述。

### 步驟 3：執行優化循環

告訴使用者：「這會花一些時間——我會在背景執行優化循環，並定期查看進度。」

把評估集存到工作區，然後在背景執行：

這會自動處理完整的優化循環。它把評估集分成 60% 訓練集與 40% 保留測試集，評估目前的描述（每個查詢執行 3 次以取得可靠的觸發率），然後呼叫 Claude 根據失敗之處提出改進。它在訓練集與測試集上重新評估每個新描述，最多迭代 5 次。完成後，它會在瀏覽器中開啟一份 HTML 報告，顯示每次迭代的結果，並回傳包含 `best_description` 的 JSON——依測試分數而非訓練分數選出，以避免過度擬合。

### 技能觸發如何運作

理解觸發機制有助於設計更好的評估查詢。技能以名稱＋描述出現在 Claude 的 `available_skills` 清單中，Claude 根據該描述決定是否參考某個技能。重要的是要知道：Claude 只會在它無法輕易自行處理的任務上參考技能——像「讀這個 PDF」這樣簡單、單一步驟的查詢，即使描述完美相符也可能不會觸發技能，因為 Claude 可以直接用基本工具處理。複雜、多步驟或專門的查詢，在描述相符時會可靠地觸發技能。

這代表你的評估查詢應該夠有分量，讓 Claude 真的能從參考技能中受益。像「讀檔案 X」這樣的簡單查詢是糟糕的測試案例——無論描述品質如何，它們都不會觸發技能。

### 步驟 4：套用結果

從 JSON 輸出中取出 `best_description`，更新技能的 SKILL.md 前置資料。向使用者展示修改前後並回報分數。

## Claude.ai 專屬說明

在 Claude.ai 中，核心工作流程相同（草稿 → 測試 → 審閱 → 改進 → 重複），但因為 Claude.ai 沒有子代理，有些機制會改變。以下是需要調整之處：

**執行測試案例**：沒有子代理代表沒有平行執行。對每個測試案例，閱讀技能的 SKILL.md，然後依照其指示自己完成測試提示。一次做一個。這比獨立的子代理不嚴謹（技能是你寫的，也是你在執行，所以你有完整的脈絡），但它是一個有用的合理性檢查——而人工審閱步驟能彌補這一點。略過基準執行——只要用技能完成所要求的任務即可。

**審閱結果**：如果你無法開啟瀏覽器（例如 Claude.ai 的虛擬機沒有顯示器，或你在遠端伺服器上），就完全略過瀏覽器審閱器。改為直接在對話中呈現結果。對每個測試案例，展示提示與輸出。如果輸出是使用者需要查看的檔案（像 .docx 或 .xlsx），把它存到檔案系統並告訴他們在哪裡，讓他們可以下載檢查。直接在對話中詢問回饋：「看起來如何？有什麼想改的嗎？」

**評測**：略過定量評測——它依賴基準比較，而沒有子代理時這種比較沒有意義。專注於使用者的定性回饋。

**迭代循環**：與先前相同——改進技能、重新執行測試案例、詢問回饋——只是中間沒有瀏覽器審閱器。如果你有檔案系統，仍然可以把結果組織到迭代目錄中。

**描述優化**：本節需要 `claude` CLI 工具（特別是 `claude -p`），只有 Claude Code 才有。如果你在 Claude.ai 上就略過。

**盲測比較**：需要子代理。略過。

**打包**：`package_skill.py` 腳本在任何有 Python 與檔案系統的地方都能運作。在 Claude.ai 上，你可以執行它，讓使用者下載產出的 `.skill` 檔。

**更新既有技能**：使用者可能是要求你更新既有的技能，而不是建立新的。這種情況下：
- **保留原本的名稱。** 記下技能的目錄名稱與 `name` 前置資料欄位——原封不動地使用它們。例如，如果已安裝的技能是 `research-helper`，就輸出 `research-helper.skill`（而不是 `research-helper-v2`）。
- **編輯前先複製到可寫入的位置。** 已安裝的技能路徑可能是唯讀的。複製到 `/tmp/skill-name/`，在那裡編輯，並從副本打包。
- **如果手動打包，先在 `/tmp/` 中準備**，然後再複製到輸出目錄——直接寫入可能因權限而失敗。

## Cowork 專屬說明

如果你在 Cowork 中，主要需要知道的是：

- 你有子代理，所以主要工作流程（平行產生測試案例、執行基準、評分等）都能運作。（不過，如果你遇到嚴重的逾時問題，改成依序而非平行執行測試提示也是可以的。）
- 你沒有瀏覽器或顯示器，所以產生評估檢視器時，使用 `--static <output_path>` 寫出獨立的 HTML 檔，而不是啟動伺服器。然後提供一個連結，讓使用者點擊在他們的瀏覽器中開啟 HTML。
- 不知為何，Cowork 的設定似乎讓 Claude 不太傾向在執行測試後產生評估檢視器，所以再強調一次：無論你在 Cowork 還是 Claude Code 中，執行測試後，你都應該先產生評估檢視器讓人類查看範例，然後才自己修訂技能並嘗試修正，而且要使用 `generate_review.py`（而不是自己寫精品 HTML 程式碼）。先說聲抱歉，但我要用全大寫了：在自己評估輸入「之前」先產生評估檢視器！你要盡快把它們呈現在人類面前！
- 回饋的運作方式不同：因為沒有執行中的伺服器，檢視器的「Submit All Reviews」按鈕會把 `feedback.json` 下載成檔案。然後你可以從那裡讀取它（你可能需要先請求存取權）。
- 打包可以運作——`package_skill.py` 只需要 Python 與檔案系統。
- 描述優化（`run_loop.py` / `run_eval.py`）在 Cowork 中應該也能正常運作，因為它是透過子程序使用 `claude -p`，而不是瀏覽器；但請把它留到你完全完成技能、且使用者同意技能狀態良好之後再做。
- **更新既有技能**：使用者可能是要求你更新既有的技能，而不是建立新的。請遵循上方 claude.ai 一節中的更新指引。
