# 改善程式碼庫架構

找出架構上的摩擦點並提出**加深機會**：把淺模組變成深模組的重構。目標是可測試性與 AI 可導航性。

這個指令以專案的領域模型為*依據*，並建立在共同的設計詞彙之上：

- 用「codebase-design」呼叫 Skill 工具，取得架構詞彙（**模組**、**介面**、**深度**、**接縫**、**轉接器**、**槓桿**、**區域性**）及其原則（刪除測試、「介面就是測試面」、「一個轉接器 = 假想的接縫，兩個 = 真實的接縫」）。在每個建議中精確使用這些術語，不要偏離成「元件」「服務」「API」或「邊界」。
- `GLOSSARY.md` 中的領域語言為好的接縫命名；`docs/adr/` 中的 ADR 記錄了這個指令不應重新爭論的決策。

## 流程

### 1. 探索

**掃描前先界定範圍：YAGNI。** 加深一個模組的回報，在於讓日後對它的修改更容易，所以要對程式碼庫中最近有變動的部分給予額外權重。在看之前，先決定*要看哪裡*：

- 如果使用者指定了方向（某個模組、子系統、痛點），就照做，並略過下面的推論。
- 否則，回顧一大段 commit 歷史（`git log --oneline`），找出程式碼庫的熱點——那些一再出現的檔案與區域——讓這些路徑優先吸引你的注意。如果變更很分散、沒有明顯熱點，就擴大範圍。

先閱讀專案的領域詞彙表（`GLOSSARY.md`）以及你所碰觸區域的任何 ADR。

然後產生一個擁有全新上下文視窗的子代理來走訪程式碼庫。不要遵循僵化的經驗法則；有機地探索，並記下你在哪裡感受到摩擦：

- 哪裡要理解一個概念，就必須在許多小模組之間來回跳轉？
- 哪裡的模組是**淺的**，介面幾乎和實作一樣複雜？
- 哪裡為了可測試性而抽出了純函式，但真正的 bug 卻藏在它們被呼叫的方式裡（缺乏**區域性**）？
- 哪裡緊密耦合的模組跨過了它們的接縫而外洩？
- 程式碼庫的哪些部分沒有測試，或很難透過目前的介面測試？

對任何你懷疑是淺的東西套用**刪除測試**：刪掉它會讓複雜度集中，還是只是把它移到別處？「是，會集中」就是你要找的訊號。

### 2. 以 HTML 報告呈現候選項目

把一個自成一體的 HTML 檔寫到作業系統的暫存目錄，讓任何東西都不會落到 repo 中。從 `$TMPDIR` 解析暫存目錄，退而使用 `/tmp`（Windows 上為 `%TEMP%`），並寫入 `<tmpdir>/architecture-review-<timestamp>.html`，讓每次執行都得到新檔案。幫使用者開啟它（Linux 用 `xdg-open <path>`、macOS 用 `open <path>`、Windows 用 `start <path>`），並告訴他們絕對路徑。

報告使用**透過 CDN 載入的 Tailwind** 做版面與樣式，並在圖／流程／序列能可靠傳達結構時使用**透過 CDN 載入的 Mermaid** 繪製圖表。混合使用 Mermaid 與手工 CSS/SVG 視覺：關係呈圖狀時（呼叫圖、相依關係、序列）用 Mermaid；想要更具編輯感的呈現時（質量圖、剖面圖、收合動畫）用手工 div/SVG。每個候選項目都要有**前後對照視覺化**。要視覺化。

每個候選項目渲染一張卡片，包含：

- **檔案**：涉及哪些檔案/模組
- **問題**：為什麼目前的架構造成摩擦
- **解法**：用淺白的語言描述會改變什麼
- **好處**：以區域性與槓桿來說明，以及測試會如何改善
- **前／後圖**：並排、自行繪製，說明淺的程度與加深後的樣子
- **建議強度**：`Strong`（強烈建議）、`Worth exploring`（值得探索）、`Speculative`（推測性）三者之一，以徽章呈現

報告以**首要建議**一節作結：你會先處理哪個候選項目、為什麼。

**領域用 GLOSSARY.md 的詞彙，架構用 `/codebase-design` 的詞彙。** 如果 `GLOSSARY.md` 定義了「Order（訂單）」，就說「訂單收件模組」，而不是「FooBarHandler」，也不是「訂單服務」。

**ADR 衝突**：如果某個候選項目與既有 ADR 矛盾，只有在摩擦真實到值得重新檢視該 ADR 時才提出。在卡片中清楚標示（例如一個警告區塊：_「與 ADR-0007 矛盾，但值得重新討論，因為……」_）。不要列出 ADR 所禁止的每一個理論性重構。

完整的 HTML 骨架、圖表模式與樣式指引請見 [HTML-REPORT.md](HTML-REPORT.md)。

**先不要**提出介面。檔案寫好之後，詢問使用者：「你想深入探索哪一個？」

### 3. 拷問循環

使用者挑選候選項目後，用「grilling」呼叫 Skill 工具，與他們一起走過決策樹：限制條件、相依關係、加深後模組的形狀、接縫後面放什麼、哪些測試能留下。

副作用在決策成形時當場發生；用「domain-modeling」呼叫 Skill 工具，邊進行邊讓領域模型保持最新：

- **用一個不在 `GLOSSARY.md` 中的概念為加深後的模組命名？** 把該術語加入 `GLOSSARY.md`。若檔案不存在就延遲建立。
- **在對話中磨利了一個模糊的術語？** 當場更新 `GLOSSARY.md`。
- **使用者以關鍵理由拒絕了候選項目？** 提議寫 ADR，措辭為：_「要不要我把這個記錄成 ADR，讓未來的架構審查不會再建議它？」_ 只有在未來的探索者真的需要這個理由來避免重複建議時才提議；略過一時性的理由（「現在不值得」）與不言自明的理由。
- **想為加深後的模組探索替代介面？** 用「codebase-design」呼叫 Skill 工具，並使用其「設計兩次」的平行子代理模式。
