# Overkill

把目前的問題推進到務實答案之外的一步。呈現超出基準需求的進階資料結構、分散式系統演算法、小眾框架、設計模式與前沿工具——並以校準過的複雜度量尺排序，讓使用者看到每一個選項真正的範圍與學習面。

## 何時使用本技能

- 使用者已有可運作或提議中的解法，並要求 `overkill`、`overkill this`、`/overkill`、`overkill --max`、`overkill --advanced` 或 `overkill --current`。
- 使用者問「這個的進階版本是什麼？」「做成企業級／FAANG 等級／面向未來」「給我極致的版本」或「讓我看看務實答案之外有什麼」。
- 使用者正在為了學習、技術盡職調查，或出於好奇某類問題有哪些前沿技巧，而探索設計空間。

當使用者想要最簡單且足夠的解法、MVP 或直接的生產環境建議時，不要使用本技能。本技能探索的是設計空間中極致的那一端；把它的輸出當成預設建議會造成誤導。如果不確定使用者的意圖，先問一個釐清問題。

## 本技能做什麼

1. **重述基準**：用一句話指出目前的務實解法，讓每個替代方案都有固定的參照點。
2. **提出 3–6 個進階替代方案**：每個來自不同的類別（資料結構、演算法、框架、設計模式、工具），在要求的複雜度範圍內，從最廣為人知排到最冷門。
3. **以校準過的複雜度量尺（🔥 1–10）為每個選項評分**，量尺在各次回應之間錨定一致，讓分數可以跨呼叫比較。
4. **產出比較表**，依要求的模式調整——預設是以學習者為導向的表格，`--advanced` 模式則是以維運者為導向的表格。
5. 為每個選項 **呈現學習資源與技能輪廓**，讓使用者能把建議當成學習路徑來行動，而不只是架構參考。

## 如何使用

### 基本用法

{{CODE:1}}

當使用者不帶任何旗標呼叫 `overkill` 時，**在產出輸出之前先暫停，詢問要套用哪些模式。** 以多選選擇器呈現三種模式（或在沒有結構化提示的環境中用編號清單），讓使用者可以選擇任意組合——或都不選，採用預設行為。每個選項使用以下確切的說法：

- **`--max`** —— 只限最高複雜度的選項（🔥 7/10 以上）。當你已經知道中等的選項、只想看前沿時選這個。
- **`--advanced`** —— 把比較表換成以維運者為導向的欄位（維運負擔、招募難度、到第一次提交的時間）。如果你在評估實際的導入成本而不是學習，選這個。
- **`--current`** —— 用網路搜尋擷取最新的參考資料並驗證專案的健康狀態。會增加延遲。用於研究，或參考資料必須反映快速變動領域的現況時。

使用者選擇之後（任何子集，包括都不選），套用所選的模式產出回應。選擇只限於這一次呼叫——在同一段對話中的後續 `overkill` 呼叫不要沿用；每次都重新詢問。

如果使用者呼叫 `overkill` 時已經帶了 **任何** 旗標（例如 `overkill --max`、`overkill --current`、`overkill --advanced --current`），就完全跳過選擇器，照他們傳入的旗標執行。選擇器是為了讓不知道有這些模式的使用者看到它們；已經傳入旗標的使用者已經做了選擇。

在所有情況下，回應都會回傳 3–6 個排序後的替代方案，附複雜度分數、學習連結、技能輪廓，以及每個方案在未來哪種規模情境下會有回報。

### 進階用法

{{CODE:2}}

把提出的替代方案限制在 🔥 7/10 以上的選項。適合已經知道中等複雜度選項、只想看前沿的使用者。

{{CODE:3}}

把比較表換成以維運者為導向的欄位——維運負擔、招募難度、到第一次提交的時間——而不是預設以學習者為導向的欄位。給評估實際導入成本的主管、資深工程師或平台負責人使用。

{{CODE:4}}

選擇使用網路搜尋。本技能會驗證推薦的框架／執行環境／函式庫是否仍在維護、呈現在模型訓練截止之後發表的論文或一手文件，並在「延伸學習」欄位中偏好較新的權威參考而非舊的。用於使用者在做研究、技術盡職調查，或想要反映快速變動領域現況的引用時。預設模式維持離線且確定性；`--current` 以延遲與一致性換取時效。

旗標可以自由組合：`overkill --max --advanced --current`。

## 輸出格式

單一回應，依序包含三個區塊。

### 1. 重述基準

用一句話說明目前在討論什麼。如果對話太模糊、無法辨識基準，在繼續之前先問使用者一個釐清問題。

### 2. Overkill 替代方案（3–6 個選項）

每個選項依照這個範本：

{{CODE:5}}

在選定的複雜度範圍內，依 **最廣為人知 → 最冷門** 排序。混合不同類別——不要回傳六個框架。目標是橫跨以下類別的多樣性：

- **資料結構**：跳躍串列、持久化／不可變樹、HAMT、Bloom／Cuckoo／Quotient 過濾器、Count-Min Sketch、HyperLogLog、簡潔資料結構、小波樹、手指樹、Roaring bitmap、Y-Fast Trie、van Emde Boas 樹。
- **演算法**：無鎖／無等待的變體、MVCC、CRDT、Raft／Paxos、向量時鐘、有界負載的一致性雜湊、hopscotch／Robin Hood 雜湊、FM-index、學習式索引、近似最近鄰（HNSW、FAISS）。
- **框架／執行環境（廣為人知 → 小眾）**：Kubernetes、gRPC、Kafka → Temporal、NATS JetStream、Materialize、ScyllaDB → Pony、Pharo、Unison、Roc、BEAM 上的 Gleam、Verona。
- **設計模式**：CQRS + 事件溯源、六角架構／Ports & Adapters、Saga、Outbox、Actor 模型、Free monad／tagless final、相依反轉的外掛架構、以能力為基礎的安全。
- **工具／基礎設施**：OpenTelemetry + Tempo + Loki + Grafana + Prometheus、eBPF 可觀測性（Pixie、Parca）、服務網格（Istio、Linkerd、Cilium）、Nix flakes + devShells、Bazel／Pants／Buck2、形式驗證（TLA+、Alloy、Coq、Lean）、性質測試 + 變異測試 + 模糊測試、混沌工程（Litmus、Chaos Mesh）。

### 3. 比較表

**預設模式** —— 以學習者為導向的欄位：

| 做法 | 複雜度 | 培養的技能 | 延伸學習 | 回報的門檻 |

**`--advanced` 模式** —— 以維運者為導向的欄位：

| 做法 | 複雜度 | 到第一次提交的時間 | 維運負擔 | 招募難度 | 回報的門檻 |

兩種模式的複雜度都使用同樣的 🔥 N/10 量尺。「回報的門檻」應該以具體的規模、負載或組織條件表示，說明該選項從什麼時候開始值回成本（例如「每天 ≥10⁹ 個事件」「多區域雙活且 RPO=0」「團隊規模 >50 且各自獨立部署」）。

## `--current` 的行為

當使用者傳入 `--current` 時，在準備回應的過程中使用網路搜尋與網頁擷取。具體來說：

1. 對任何比成熟選項更年輕或較不主流的推薦框架、執行環境或函式庫，**驗證專案健康狀態**。檢查專案的主要 repository 或網站，看最近的提交活動、最新的發布日期，以及任何明確的棄用或移交公告。如果專案已停滯、被放棄或被取代，就換成目前的對應方案，或在「是什麼」那一行加註，避免讓使用者走向已經死掉的工具。
2. **更新「延伸學習」連結。** 偏好既權威 *又* 夠新、能反映技術現況的參考：權威論文加上近 1–2 年的後續或修訂（若有的話）；目前網址的一手文件，而不是訓練資料中的快照；如果技術已有實質演進，偏好被廣泛引用的新部落格文章而不是舊的。每個選項保持 1–3 個連結——目標是時效，而不是數量。
3. 如果在模型訓練截止之後出現了會實質改變回應的 **重大新選項**（例如新的共識協定、已進入生產就緒的執行環境、取代舊技術的論文），就把它呈現出來。依它們目前的地位（而不是新穎程度）放進排序規則（廣為人知 → 冷門）中。
4. **控制搜尋次數的預算。** 每個需要更新的選項目標是一次聚焦的搜尋，而不是地毯式掃描。對參考資料持久且穩定的選項，完全跳過搜尋（例如一篇 1990 年代關於基礎資料結構的論文不需要重新檢查）。
5. **優雅降級。** 如果目前的環境無法使用網路搜尋或網頁擷取，不要阻擋回應。退回離線行為，並加上一行給使用者的說明：「要求了 `--current`，但此環境無法存取網路；回應使用訓練截止時的參考資料。」不要默默產出看起來過時的內容卻當作是最新的。

## 複雜度量尺

錨定 🔥 N/10 分數，讓它們在各次回應之間保持校準：

- 🔥 1–2：替換函式庫或單一個新的抽象。數小時內可交付；審查負擔極小。
- 🔥 3–4：在程式碼庫中引入新的模式。需要數天到數週的重構；預期全團隊都要熟悉。
- 🔥 5–6：新的執行環境相依（佇列、快取、sidecar）。增加一個維運面向與一個要守護的 SLO。
- 🔥 7–8：引入分散式系統的問題——共識、複製、部分失敗。需要值班輪替與操作手冊。
- 🔥 9：研究等級。實作依賴一手文獻；很少有生產環境的參考。
- 🔥 10：需要招募專家，或使用全球使用者很少的執行環境／語言。長期維護是一項策略性的承諾。

如果使用者傳入 `--max`，只回傳 🔥 7 以上的選項。

## 語氣

嚴肅、技術上精確且充滿好奇。把使用者當作已經知道務實答案、想理解其外還有什麼的工程師——那些他們否則永遠不會接觸到的技巧、取捨與前沿想法。以設計審查的嚴謹度說明每個選項：真實的機制、真實的失敗模式、真實的成本。目標是深度與視野，不是幽默。不要評論某個選項「荒謬」或「可笑」——複雜度分數與培養的技能那一行會客觀地呈現這一點。

## 範例

**使用者**：「我用一個以 delivery ID 為鍵的程序內 set 來對 webhook 投遞去重。overkill」

**輸出**（節錄）：

> **基準：** 一個以 delivery ID 為鍵的程序內 set，用來在單一節點上對 webhook 投遞去重。
>
> #### 帶 TTL 的 Redis SET —— 複雜度：🔥 2/10
> **是什麼：** 以 `SADD` 搭配每個鍵的 `EXPIRE`，提供跨程序共享的去重時間窗。
> **如何超越基準：** 去重狀態在程序重啟後仍然存在，並在多個投遞 worker 之間保持一致。
> **培養的技能：** Redis 資料結構的慣用法、以 TTL 為基礎的記憶體預算、為共享快取的部分可用性做設計。
> **延伸學習：** [Redis SET 文件](https://redis.io/commands/set/)、[把 Redis 當快取：模式指南](https://redis.io/docs/latest/develop/use/patterns/)。
> **值得的情境：** 水平擴展的投遞 worker（≥2 個節點），程序內狀態會不一致，且「至少一次」語意已不再可接受。
>
> #### 以 Kafka 壓縮主題為底的 Roaring Bitmap —— 複雜度：🔥 8/10
> **是什麼：** delivery ID 被雜湊到稠密的整數空間，並以 Roaring Bitmap 追蹤；權威狀態從 Kafka 壓縮主題重播，讓任何消費者都能確定性地重建去重集合。
> **如何超越基準：** 在數十億 ID 規模下的 O(1) 成員測試、日誌結構的持久性，以及可為新消費者或災難復原重播的狀態。
> **培養的技能：** 壓縮 bitmap 工程、雜湊分布分析、Kafka 日誌壓縮語意、可重播的狀態機設計。
> **延伸學習：** [Roaring Bitmaps 論文（Chambi 等，2014）](https://arxiv.org/abs/1402.6407)、[Kafka 日誌壓縮](https://kafka.apache.org/documentation/#compaction)。
> **值得的情境：** 在數週的時間窗內保留 ≥10⁹ 個 delivery ID，且有多個獨立的消費者必須在沒有共享資料庫的情況下對去重狀態達成一致。
>

## 提示

- 在提出替代方案之前先辨識基準。沒有固定的參照點，複雜度分數就沒有意義。
- 偏好類別的多樣性，而不是單一類別的深度。六個框架的回應，教得比橫跨資料結構、演算法、框架、模式與工具的回應還少。
- 讓「延伸學習」連結保持持久——論文、一手文件、被廣泛引用的文章。避免會失效的部落格文章。在 `--current` 模式下，當技術已有實質演進時，偏好近期的權威來源。
- 每次都對照錨定清單校準分數。分數在不同呼叫之間漂移，會使量尺失去意義。
- 如果使用者在 `--advanced` 模式，就著重維運成本的框架——受眾是在做實際的導入決策，而不是在探索。
- 在 `--current` 模式下，刻意控制搜尋預算。每個需要更新的選項做一次聚焦的查詢，勝過四次零散的查詢。基礎技術（1990 年代的資料結構論文、已定案的演算法）通常完全不需要重新驗證。

## 常見使用情境

- 工程師正在實作一個功能，想在決定採用簡單選項之前理解完整的設計空間。
- 資深或首席工程師正在準備技術設計文件，想要一份進階替代方案的調查，以便引用並排除。
- 團隊正在對廠商的說法（「他們用了 X」）做技術盡職調查，想了解 X 實際上位於複雜度光譜的哪裡。
- 工程師正在選擇學習專案，想要一條以真實問題為錨點、而不是抽象主題的學習路徑。
- 平台或資深工程師（在 `--advanced` 模式）正在評估某項前沿技術對其組織的導入成本。

## 最後的話

本技能是給想把問題推進到務實答案之外一步的探索者與工程師——讓他們看到存在於領域邊緣的進階資料結構、分散式系統技巧與前沿工具。把每個建議都當作值得認真研究的對象，而不是笑點。複雜度分數與培養的技能那一行，是誠實的成本訊號；使用者有能力決定要怎麼運用。本技能的工作是準確地擴展使用者對「可能性」的認識。
