# OpenAI 文件

使用 developers.openai.com MCP 伺服器，從 OpenAI 開發者文件提供權威、最新的指引。「Docs MCP」指的是 `mcp__openaiDeveloperDocs__search_openai_docs` 與 `mcp__openaiDeveloperDocs__fetch_openai_doc`；對於 API 參考、schema、參數或必要欄位的問題，可用時也使用 `mcp__openaiDeveloperDocs__get_openapi_spec`。官方網域的網路搜尋，是在這些工具無法使用或沒有幫助之後的備案。廣泛的 Codex 問題，在 Docs MCP 之前先使用手冊輔助工具。本技能也負責模型選擇、API 模型遷移與提示詞升級的指引。

## API 金鑰設定

對於建構、執行、設定、除錯或實作以 API 為後端的應用程式、腳本、CLI、產生器或工具的請求，可用時先使用 `openai-platform-api-key`。在那道憑證關卡解決之後，再視需要回到這裡查詢最新文件。

對於只問文件的問題、引用、模型/API 指引、概念解說，以及不需要建構或執行以 API 為後端之產出物的範例，直接使用本技能。

## 工作流程設定

### 來源優先順序

- 對於 Codex 自我知識，使用下方的 Codex 來源路線；它決定何時使用手冊輔助工具、Docs MCP 或有界的不確定性。
- 對於非 Codex 的 OpenAI 文件問題，使用 `mcp__openaiDeveloperDocs__search_openai_docs` 找出最相關的文件頁面。
- 對於非 Codex 的 OpenAI 文件問題，在回答之前用 `mcp__openaiDeveloperDocs__fetch_openai_doc` 抓取相關頁面。如果搜尋結果雜亂，就執行一次更窄的 Docs MCP 搜尋；當知道或找到任何看似合理的官方 OpenAI 文件 URL 時，在依賴網路搜尋的內容之前，先試著透過 Docs MCP 抓取那個 URL。
- 對於 API 參考、schema、參數或必要欄位的問題，可用時使用 `mcp__openaiDeveloperDocs__get_openapi_spec`，搭配相關的指南或參考頁面驗證 API 的形狀。
- 只有在你需要在沒有明確查詢的情況下瀏覽或探索非 Codex 頁面時，才使用 `mcp__openaiDeveloperDocs__list_openai_docs`。
- 對於模型選擇、「最新模型」或預設模型的問題，先抓取 `https://developers.openai.com/api/docs/guides/latest-model.md`。如果無法取得，就載入 `references/latest-model.md`。
- 對於模型升級或提示詞升級，只有在目標是最新/目前/預設或未指定時，才執行 `node scripts/resolve-latest-model-info.js`；否則保留明確要求的目標。
- 保留明確的目標請求：如果使用者指名了目標模型，例如「遷移到 GPT-5.4」，即使 `latest-model.md` 列出了更新的模型，也保留所要求的目標。只把較新的指引當作選擇性的提及。
- 如果需要目前的遠端指引，直接抓取回傳的遷移指南與提示指南兩個 URL。如果直接抓取失敗，使用 MCP/搜尋備案；如果那也失敗，使用內附的備用參考，並揭露使用了備案。

## OpenAI 產品快照

1. Apps SDK：透過提供網頁元件 UI，以及一個把你應用程式的工具公開給 ChatGPT 的 MCP 伺服器，來打造 ChatGPT 應用程式。
2. Responses API：一個統一的端點，專為代理工作流程中有狀態、多模態、會使用工具的互動而設計。
3. Chat Completions API：從構成一段對話的訊息清單產生模型回應。
4. Codex：OpenAI 用於軟體開發的程式設計代理，能撰寫、理解、審查與除錯程式碼。
5. gpt-oss：以 Apache 2.0 授權發布的開放權重 OpenAI 推理模型（gpt-oss-120b 與 gpt-oss-20b）。
6. Realtime API：打造低延遲、多模態的體驗，包括自然的語音對語音對話。
7. Agents SDK：一套打造代理應用程式的工具組，讓模型能使用工具與脈絡、交棒給其他代理、串流部分結果，並保留完整的追蹤。

## Codex 自我知識

對於關於 Codex 本身的問題，使用這條路徑：設定、擴充、操作、疑難排解、本機狀態、產品介面，或 Codex 的行為該放在哪裡。程式碼庫只是提到了外掛、技能、hook、MCP 伺服器、瀏覽器或自動化，並不足以構成理由。對於一般的軟體任務，直接回答該軟體任務；如果被問到 Codex 自我知識是否適用，就簡短回答那個後設問題，然後繼續完成所要求的產出物。

### 來源路線

對於廣泛的 Codex 綜合整理，Codex 手冊是第一個來源。把手冊與 Docs MCP 視為不同的管道，而不是可互換的官方文件來源。對於已公開給使用者的 Codex 產品解答，來源路線是完整的：手冊、這條路線要求時的 Docs MCP、官方 OpenAI 網路備案，以及當問題與某項能力有關時、目前 session 中所呈現的可呼叫能力。developers.openai.com 以外的知識庫，不在這條公開產品解答的路線內。

對於廣泛的 Codex 行為、設定、客製化、技能、外掛、MCP、hook、`AGENTS.md`、自動化、介面、本機狀態或系統地圖的問題：

1. 當同一執行緒中的手冊與大綱路徑仍然新鮮時，重用它們。
2. 否則，在一般可寫入的 session 中，先執行技能本地的輔助工具。只有在 session 明確為唯讀、無法執行 shell，或可見的政策顯示不允許暫存快取時，才不嘗試就略過它。
3. 預設情況下，輔助工具會依此順序選擇第一個可用的暫存快取目錄：`$TMPDIR/openai-docs-cache`、`%TEMP%\openai-docs-cache`、`%TMP%\openai-docs-cache`、`/private/tmp/openai-docs-cache`，然後是 `/tmp/openai-docs-cache`。只有工作區的寫入權限，不足以作為這個暫存快取。
4. 除非你需要覆寫快取目錄，否則直接執行輔助工具。當原生的 `fetch` 無法使用、或存在代理環境變數時，輔助工具會退回使用 `curl`，所以不需要 shell 專屬的代理前綴。把 `<skill-dir>` 解析為本技能的實際目錄；在複製到本機的評估工作目錄中，這通常是 `.codex/skills/openai-docs`：

輔助工具會驗證新鮮度、寫出 `codex-manual.md`，並產出 `codex-manual.outline.md`。大綱把來源頁面與標題對應到行號範圍；用它選擇相關的手冊章節，然後閱讀或搜尋針對性的手冊章節以取得 Codex 產品事實。用技能目錄找到並執行輔助工具；輔助工具成功之後，以回傳的手冊與大綱路徑作為 Codex 產品事實與術語涵蓋檢查的搜尋範圍。

對於後續的 Codex 問題，重用同一執行緒中的手冊與大綱路徑。當手冊是大約一天以前抓取的、路徑無法使用、路徑來自另一個執行緒或來源不確定，或缺少可能是最新的資訊且有過時的可能時，先重新整理。

對於手冊現在是否夠新、能否依賴的問題，在允許暫存快取時執行輔助工具，並以它回傳的狀態、手冊路徑與大綱路徑為依據回答。

如果手冊解決了某項 Codex 主張，就從它回答，並停止為那項主張擴大來源；如果文件查詢只是使用者更廣泛任務的一個相依項目，就繼續那個任務。手冊的來源頁面與已知的錨點，足以作為手冊所涵蓋內容的引用依據。

如果因為 session 是唯讀、無法執行 shell 或不允許暫存快取而略過輔助工具，下一個來源是 Docs MCP：在任何網路備案之前，先呼叫 `mcp__openaiDeveloperDocs__search_openai_docs`，然後對相關的結果呼叫 `mcp__openaiDeveloperDocs__fetch_openai_doc`。

如果使用者指名了一個新鮮的手冊沒有使用的 Codex 術語或模式，就在手冊中搜尋明顯相鄰的概念，然後回答說這個確切的術語沒有記載，並使用最接近的有記載術語。如果提示問的是該術語如何對應到 Codex 的行為，就從相鄰的手冊章節解決這個對應。如果在那一輪手冊查詢之後，這個確切的術語仍然很重要或可能是最新的，就在給出有界的不確定性之前，做一次窄範圍的 Docs MCP 搜尋/抓取；否則，對該術語或對應主張的來源查詢就完成了。

只有在手冊無法取得、輔助工具失敗、不允許暫存快取、另一項重要主張缺少或可能過時，或使用者明確需要針對特定頁面的引用時，才使用最窄的官方下一個來源。優先做一次具體的 Docs MCP 搜尋，如果它回傳了明顯相關的頁面，就做一次抓取；對於未解決的 Codex 能力名稱、縮寫、排程術語或確切的錯誤文字，這個 Docs MCP 步驟是網路搜尋之前的下一個來源。在手冊加上任何允許的 Docs MCP 補缺之後，把剩下的缺口以有界的不確定性處理。只有在那條 Docs MCP 路徑無法使用或沒有幫助之後，才使用官方網域的網路備案。如果主張仍然無法確立，就以有界的不確定性停下。如果官方文件/手冊與目前 session 中已呈現的可呼叫能力相衝突，就說明這個衝突，並在那個環境中優先採用經驗證的目前 session 行為。

對於未記載或看起來是私有的模型代稱、產品模式標籤、權限標籤、帳戶存取路徑或推出名稱，以目前的公開文件與有界的不確定性回答。這些標籤不是離開公開來源路線的理由。

對於客服類型的診斷，優先以手冊逐層回答，而不是針對特定供應商的網路查詢：已安裝/已啟用的外掛、內附的應用程式或連接器授權、MCP 設定、工作區/管理員政策、重新啟動或新執行緒的預期，然後如果仍未解決，才是客服或回饋。

如果來源路線仍然無法確立某項主張，就回傳有界的不確定性，或導向客服、管理員或產品回饋，而不是擴大調查。

對於未解決的產品術語，以手冊加上允許的官方下一個來源回答。如果那些來源無法確立該術語，就以那些來源為依據、以有界的不確定性回答。

### 介面地圖

當 Codex 的名詞或持久指示介面有重疊時，推薦符合範圍的最小介面：

- 提示或執行緒脈絡 -> 一次性任務的限制。
- `AGENTS.md` -> 持久的 repo 慣例、指令、驗證步驟與審查預期；較近的巢狀檔案適用於其子樹。
- 專案的 `.codex/config.toml` -> 受信任 repo 的 Codex 設定，例如沙箱、MCP、hook、模型或推理預設值。
- 全域設定或全域指引 -> 跨 repo 的個人預設值。
- 技能 -> 附參考或腳本的可重用任務工作流程。
- 外掛 -> 可安裝的套件，包含技能加上指令、工具、MCP 設定、hook、素材、應用程式或 marketplace 中繼資料。
- MCP 伺服器或應用程式連接器 -> 即時的外部資料/動作，或經授權的私有應用程式/工作區資料。對於私有的 Google Docs、Calendar、Slack、GitHub、Notion 與類似的資料，使用連接器，而不是網路搜尋或模型記憶。
- 自動化 -> 排程的檢查、提醒、監控或後續工作；當在既有執行緒中保持連續性很重要時，使用執行緒心跳。
- Hook -> 圍繞工具呼叫、指令或檔案編輯的生命週期強制執行。

拆開混合範圍的請求，而不是硬給一個答案。例如：「一律做 X，但只針對這個 PR」預設是目前這次執行的提示/執行緒脈絡；只有在它應該持續時才用 `AGENTS.md` 或專案設定，只有機械性的強制執行才用 hook，只有排程或後續工作才用自動化。

需要時使用這份快速產品地圖：CLI 是以終端機為主的本機 repo 工作；IDE 擴充功能是附著在編輯器上的程式設計；Codex 應用程式是桌面上的規劃、審查與互動式工作；雲端/網頁是託管的平行/外包工作；Browser Use/應用程式內瀏覽器是由 Codex 控制的網頁測試；Chrome 擴充功能使用使用者的 Chrome 設定檔；Computer Use 控制桌面應用程式與作業系統 UI。讓 `config.toml` 的預設值、`requirements.toml` 的限制，以及託管/管理員政策保持分開。

### 邊界與輸出

- API 金鑰驗證並不代表能存取 ChatGPT、雲端任務或連接器。對於外掛/應用程式/驗證失敗，在回答之前檢查套件可用性、外掛的安裝/啟用狀態、連接器/應用程式授權、MCP 設定、重新啟動/重新整理的預期、工作區政策，以及各介面的可用性。
- 沙箱或網路拒絕需要有範圍的權限提升，並附上清楚的理由。破壞性的指令、在工作區之外寫入，或廣泛的存取變更，需要明確的核准。
- 記憶可以提供使用者偏好或脈絡，但明確的提示指示優先，而且記憶不是目前外部事實的來源。
- 對於肯定的介面選擇答案，使用這個形狀：建議、原因、要避免什麼，以及所使用的手冊/來源證據。
- 當確實需要針對特定頁面的 Codex 引用時，這些錨點通常適用：`AGENTS.md` 用 `concepts/customization#agents-guidance`，技能用 `concepts/customization#skills`，外掛用 `plugins/build#plugin-structure`，MCP 用 `concepts/customization#mcp`，hook 用 `config-advanced#hooks`，執行緒自動化用 `app/automations#thread-automations`，設定用 `config-reference#configtoml`。

## 如果缺少 MCP 伺服器

如果 MCP 工具失敗，或沒有可用的 OpenAI 文件資源：

1. 自己執行安裝指令：`codex mcp add openaiDeveloperDocs --url https://developers.openai.com/mcp`
2. 如果因為權限/沙箱而失敗，立即以提升的權限重試同一個指令，並附上一句話的核准理由。
3. 只有在提升權限的嘗試也失敗時，才請使用者執行安裝指令。
4. 請使用者重新啟動 Codex。
5. 重新啟動後重新執行文件搜尋/抓取。

## 工作流程

1. 釐清請求是一般的文件查詢、模型選擇、模型字串升級、提示詞升級指引，還是更廣泛的 API/供應商遷移。
2. 對於 Codex 自我知識的請求，遵循上方的 Codex 自我知識來源程序。
3. 對於模型選擇或升級的請求，當使用者要求最新/目前/預設的指引時，優先使用目前的遠端文件，而不是內附的參考。
   - 抓取 `https://developers.openai.com/api/docs/guides/latest-model.md`。
   - 找出最新的模型 ID，以及明確的遷移或提示指引連結。
   - 優先使用最新模型頁面上的明確連結，而不是推導出來的 URL。
   - 對於明確指名模型的請求，保留所要求的模型目標。只把較新的遠端指引當作選擇性的提及。
   - 對於動態的最新/目前/預設升級，執行 `node scripts/resolve-latest-model-info.js`，然後可能的話直接抓取回傳的兩個指南 URL。
   - 如果直接抓取指南失敗，使用開發者文件 MCP 工具或官方 OpenAI 網域搜尋找到相同的指南內容。
   - 如果遠端文件無法取得，使用內附的備用參考，並說明使用了備用指引。
4. 對於模型升級，讓變更保持窄範圍：只在安全時，更新現行的 OpenAI API 模型預設值以及直接相關的提示詞。
5. 除非使用者明確要求升級它們，否則保持歷史文件、範例、評估基準、測試資料、供應商比較、供應商登錄表、價格表、別名預設值、低成本備用路徑，以及模稜兩可的舊模型用法不變。
6. 除非使用者明確要求，否則不要把 SDK、工具、IDE、外掛、shell、驗證與供應商環境的遷移，混入模型與提示詞的升級中。
7. 如果某項升級需要 API 介面變更、schema 重新接線、工具處理器變更，或超出字面上替換模型字串與編輯提示詞的實作工作，就把它回報為受阻或需要確認。
8. 對於一般的文件查詢，從一個精簡、像標題一樣、由 2–6 個必要詞組成的搜尋查詢開始。不要把使用者的完整問題變成關鍵字清單。抓取最好的頁面以及所需的確切段落，並以簡潔的引用回答。
