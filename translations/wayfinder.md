一個鬆散的點子來了，對一個代理 session 來說太大，而且籠罩在迷霧中：從這裡到**目的地**的路還看不見。導航（wayfinding）的重點是找到那條路，而不是直衝目的地。本技能把那條路畫成 repo issue 追蹤系統上的一張**共用地圖**，然後一次處理一張**決策工單**（其解答是一個決策的問題，而不是要執行的建構切片），直到路線清晰。

每項工作的目的地都不同，而為它命名是繪製地圖的第一步：它會形塑每一張工單。它可能是一份要交出去並反覆修改的規格、一個在規劃開始前要定案的決策，或一個原地進行的變更，例如資料結構遷移。地圖不限領域：工程工作、課程內容，任何符合這種形狀的東西都可以。

## 規劃，而不是動手做

Wayfinder 預設是**規劃**：每張工單解決一個決策，當路變清晰、在有人去動手之前已沒有需要決定的事時，地圖就完成了。想直接動手做的衝動，通常是你已經到達地圖邊緣、該交棒的訊號。一項工作可以在它的**備註**中覆寫這一點，把執行也帶進地圖本身，但除此之外，產出決策，而不是交付成果。

## 以名稱稱呼

每張地圖與工單都是一個 issue，所以它有一個**名稱**：它的標題。在人類會閱讀的所有內容中（敘述、地圖的「目前的決策」），用名稱稱呼它，絕不用單純的 id、編號或代稱。一整牆的 `#42, #43, #44` 無法閱讀；名稱一眼就懂。id 與 URL 並不會消失；名稱包著它的連結，但它們放在名稱*之內*，絕不取代名稱。

## 地圖

地圖是這個 repo 的 issue 追蹤系統上的單一 issue，標籤為 `wayfinder:map`，是標準的產出物。它的工單是地圖的子 issue。

地圖是一份**索引**，而不是儲存庫。它列出已做的決策，並指向保存其細節的工單；一個決策只存在一個地方——它的工單——所以地圖從不重述它，只給要點並連結。

**地圖、其子工單、阻擋關係與前沿查詢實際存放在哪裡，取決於追蹤系統。** issue 追蹤系統應該已經提供給你了。如果沒有，請使用者執行 `/setup-matt-pocock-skills`。查閱追蹤系統文件中的「Wayfinding operations」一節，了解*這個* repo 如何表達它們。如果沒有提供任何追蹤系統，預設使用本機 Markdown 追蹤系統。

每張工單都帶有一個 `wayfinder:<type>` 標籤，為 `research`、`prototype`、`grilling`、`task` 之一（見[工單類型](#ticket-types)）。`wayfinder:` 標籤是地圖與其工單唯一會帶的標籤，絕不帶像 `ready-for-agent` 這樣的分類標籤：它們是決策，不是實作工作。

一個 session 要**認領**一張工單，就把它指派給驅動這張地圖的開發者，而且要**最先**做，在任何工作之前，讓同時進行的其他 session 略過它。那個被指派者*就是*認領：開啟中、未指派的工單就是未被認領的。

阻擋關係使用追蹤系統**原生**的相依關係：這很重要，因為它會在追蹤系統自己的 UI 中把前沿*視覺化*，讓人不必打開地圖就看得到什麼可以接手。只有缺少原生阻擋功能的追蹤系統，才退而使用內文慣例。當阻擋某張工單的每張工單都關閉時，它就**解除阻擋**；**前沿**是開啟中、未被阻擋、未被認領的子 issue，也就是已知範圍的邊緣。

答案不是內文的一部分；它在解決時記錄（見[推進地圖](#work-through-the-map)）。解決工單時建立的素材，從 issue 連結過去，而不是貼進來。

## 工單類型

每張工單要嘛是 **HITL**（human in the loop，與一位能代表自己發言的人類一起處理），要嘛是 **AFK**，由代理獨自驅動。HITL 工單只能透過那種即時交流來解決；代理絕不代替人類那一方發言（一個自問自答的拷問代理就違反了這一點）。

- **研究**（AFK）：閱讀文件、第三方 API，或知識庫等本機資源，找出某個決策所等待的事實。由一個以「research」呼叫 Skill 工具的子代理解決。當需要目前工作目錄以外的知識時使用。
- **原型**（HITL）：以「prototype」呼叫 Skill 工具，做出一個便宜、粗略、具體、可供回應的產出物（大綱、草稿、存根，或 UI／邏輯程式碼），以提高討論的具體程度。把原型以素材的形式連結。當「它該長什麼樣」或「它該怎麼運作」是關鍵問題時使用。
- **拷問**（HITL）：對話。預設的情況。一律呼叫 Skill 工具兩次，分別用「grilling」與「domain-modeling」。
- **任務**（HITL 或 AFK）：在能做出某個*決策*之前必須先完成的手動工作：沒有東西要決定、做原型或研究，但討論在它完成前會卡住。註冊一個服務以便評估它的 API、開通存取權限、搬移資料以便看清它的形狀。這是唯一*動手做*而不是做決定的類型，它之所以存在，是因為它能解除某個決策的阻擋，而不是因為它能交付目的地。代理能做的就自己來（AFK）；否則就交給人類一份精確的檢查清單（HITL）。工作完成時即解決；答案記錄做了什麼，以及後續工單所依賴的任何結果事實（憑證位置、新的 URL、資料列數）。

## 戰爭迷霧

地圖*刻意*不完整：不要畫出你還看不見的東西。在目前的工單之外是**戰爭迷霧**：那些你看得出即將到來、但因為取決於仍未解決的問題而還無法確定的決策與調查，只有模糊的輪廓。解決一張工單會驅散它前方的迷霧，把現在已能具體說明的東西，一次一個地升格為新的工單，直到通往目的地的路變得清晰、不再有任何工單。

地圖的**尚未具體化**一節，就是寫下那片模糊景象的地方：疑似的問題、之後要重訪的區域。它是*朝向*目的地、尚未被發現的前沿：這裡的一切都在範圍內，只是還不夠清晰到可以開工單。依你看得到的程度，寫得粗略或完整都可以；它同時也是給協作者看的路標，告訴他們這項工作往哪裡去。

**迷霧還是工單？** 判斷標準是你現在能不能精確地陳述問題，*而不是*你現在能不能回答它。

- **開工單**：當問題已經很清晰時，即使它被阻擋、你還無法處理它。
- **尚未具體化**：當你還無法把它說得那麼清楚時。不要預先把迷霧切成工單大小的碎片：它比工單更粗，一片迷霧在前沿抵達時，可能升格成好幾張工單，也可能一張都沒有。

**尚未具體化**不包含已經決定的事（目前的決策）、已經是現行工單的事，以及範圍外的事（下一節）。

## 範圍外

迷霧只會朝*向*目的地聚集。目的地確定了範圍，所以超出它的工作就是**範圍外**：它不是迷霧，也不屬於**尚未具體化**。它在地圖上有自己的**範圍外**一節：你有意識地從*這一項*工作中排除的事。讓它落在這裡的是範圍，而不是清晰度。

範圍外的工作永遠不會升格（前沿停在目的地），所以只有在目的地被重新劃定時它才會回來，而且是以一項新工作的形式，而不是接續。

把某件事排除在範圍外，是一個界定範圍的動作，而不是路線上的一步。當一張已存在的工單後來證實位於目的地之外（在繪製時被誤納入範圍，或被某個解答揭露），就**關閉它**（關閉的工單毫無疑問地不在前沿上），並在**範圍外**一節留下一行：要點加上為什麼它在範圍外，並連結那張關閉的工單。它不會進入**目前的決策**，那裡記錄的是實際走過的路線；範圍邊界不是路線上的一步。

## 呼叫方式

兩種模式。無論哪一種，**每個 session 絕不解決超過一張工單**，研究工單除外。

### 繪製地圖

使用者帶著一個鬆散的點子呼叫。

1. **為目的地命名。** 呼叫 Skill 工具兩次，分別用「grilling」與「domain-modeling」，確定這張地圖要找路通往的地方：規格、決策或變更。目的地確定了範圍，所以要最先確定。
2. **繪製前沿。** 再拷問一次，這次是**廣度優先**：在整個空間中展開，而不是深入任何單一線索，找出開放中的決策以及現在就能採取的第一步。**如果這沒有揭露任何迷霧**（通往目的地的路已經很清楚，整趟旅程小到一個 session 就能完成），你就不需要地圖。停下來，詢問使用者想如何進行。
3. **建立地圖**（標籤 `wayfinder:map`）：填好目的地與備註，「目前的決策」留空，把迷霧勾勒在**尚未具體化**中。
4. **建立你現在就能具體說明的工單**，作為地圖的子 issue，然後在**第二輪**接上阻擋邊（issue 要先有 id 才能互相參照）。也在那一輪用真實的 id 寫交叉參照：占位的 `#<n>` 會自動連到不相關的 issue。接線會把它們分成前沿與被阻擋的；你還無法具體說明的一切都留在迷霧中：**尚未具體化**一節。
5. **派出研究子代理。** 對你剛建立的每張 `research` 工單，啟動一個擁有全新上下文視窗、以「research」呼叫 Skill 工具的子代理平行解決它，把發現記錄在一個拋棄式的 `research/<name>` 分支上，並從工單放一個脈絡指標過去。推送該分支但不開 PR：它永遠不會被合併。
6. 停下來：繪製地圖是一個 session 的工作；它不親手解決任何東西。

### 推進地圖

使用者帶著一張地圖（URL 或編號）呼叫。工單是**選填**的：沒有指定時，由你挑選下一個決策，而不是使用者。

1. 載入**地圖**：低解析度的檢視，而不是每張工單的內文。
2. 選擇工單。如果使用者指名了一張，就用它。否則依序取前沿上的第一張工單。**認領它**：在任何工作之前把它指派給自己。
3. 依它的 `wayfinder:<type>` 標籤所指的類型解決它（見[工單類型](#ticket-types)）。要讀標籤，而不只是內文：內文從不說明類型。**視需要放大**：需要時抓取任何相關或已關閉工單的完整內文；為 `## Notes` 區塊中指名的技能呼叫 Skill 工具。拿不定主意時，呼叫 Skill 工具兩次，分別用「grilling」與「domain-modeling」。
4. 記錄解答：把答案貼成一則**解答留言**、**關閉**該 issue，並在地圖的「目前的決策」中**附加一個脈絡指標**。
5. 加入新浮現的工單（先建立再接線）；把解答已讓它能具體說明的迷霧升格，並把每一片升格的迷霧從**尚未具體化**中清除，讓它只以新工單的形式存在。如果解答揭露某張工單（這張或另一張）位於目的地之外，就**把它排除在範圍外**，而不是在路線上解決它。如果這個決策讓地圖的其他部分失效，就更新或刪除那些工單。

使用者可能會平行執行未被阻擋的工單，所以要預期其他 session 會同時在編輯追蹤系統。
