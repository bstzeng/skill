# 子代理驅動開發

為每個任務或問題派發全新的子代理來建立並執行計畫，並在每個任務或每批任務之後審查程式碼與輸出。

**核心原則：** 每個任務一個全新子代理 + 任務之間或之後審查 = 高品質、快速迭代。

透過代理執行計畫：

- 同一個工作階段（沒有脈絡切換）
- 每個任務一個全新子代理（沒有脈絡污染）
- 每個或每批任務之後進行程式碼審查（及早抓到問題）
- 更快的迭代（任務之間不需要人介入）

## 支援的執行類型

### 依序執行

當你有彼此相關、需要依序執行的任務或問題時，依序調查或修改是最好的方式。

每個任務或問題派一個代理。讓它依序工作。在每個任務或問題之後審查輸出與程式碼。

**何時使用：**

- 任務彼此緊密耦合
- 任務應該依序執行

### 平行執行

當你有多個不相關的任務或問題（不同的檔案、不同的子系統、不同的 bug）時，依序調查或修改會浪費時間。每個任務或調查都是獨立的，可以平行進行。

每個獨立的問題領域派一個代理。讓它們同時工作。

**何時使用：**

- 任務大致上是獨立的
- 可以在所有任務完成後做整體審查

### 警訊

**絕不：**

- 跳過任務之間的程式碼審查
- 帶著未修正的嚴重問題繼續
- 平行派發多個實作子代理（會衝突）
- 沒有讀計畫中的任務就實作

**如果子代理任務失敗：**

- 以具體的指示派發修正用的子代理
- 不要試著自己手動修（脈絡污染）

## 平行執行的流程

載入計畫、批判性地審閱、分批執行任務，並在批次之間回報以供審查。

**核心原則：** 分批執行，並設有讓架構師審查的檢查點。

**開始時宣告：**「我正在使用 executing-plans 技能來實作這份計畫。」

### 步驟 1：載入並審閱計畫

1. 讀取計畫檔
2. 批判性地審閱——找出對計畫的任何疑問或疑慮
3. 如果有疑慮：開始之前先向你的人類夥伴提出
4. 如果沒有疑慮：建立 TodoWrite 並進行

### 步驟 2：執行一批

**預設：前 3 個任務**

對每個任務：

1. 標記為 in_progress
2. 完全照每個步驟做（計畫的步驟都很小）
3. 依指定執行驗證
4. 標記為 completed

### 步驟 3：回報

一批完成時：

- 呈現實作了什麼
- 呈現驗證的輸出
- 說：「準備好接受回饋了。」

### 步驟 4：繼續

依回饋：

- 需要時套用變更
- 執行下一批
- 重複直到完成

### 步驟 5：完成開發

所有任務都完成並驗證後：

- 宣告：「我正在使用 finishing-a-development-branch 技能來完成這項工作。」
- **必要的子技能：** 使用 superpowers:finishing-a-development-branch
- 依該技能驗證測試、提出選項、執行選擇

### 何時停下來尋求協助

**在以下情況立即停止執行：**

- 在批次中途遇到阻礙（缺少相依、測試失敗、指示不清楚）
- 計畫有關鍵的缺口，無法開始
- 你不理解某個指示
- 驗證一再失敗

**尋求釐清，而不是用猜的。**

### 何時回到先前的步驟

**在以下情況回到審閱（步驟 1）：**

- 夥伴依你的回饋更新了計畫
- 根本的做法需要重新思考

**不要硬闖阻礙**——停下來並詢問。

### 記住

- 先批判性地審閱計畫
- 完全照計畫的步驟做
- 不要跳過驗證
- 計畫說要參考技能時就參考
- 批次之間：只回報並等待
- 被阻礙時停下來，不要用猜的

## 平行調查的流程

平行執行的特例：當你有多個不相關的失敗，可以在沒有共享狀態或相依的情況下調查時。

### 1. 找出獨立的領域

依壞掉的東西把失敗分組：

- 檔案 A 的測試：工具核准流程
- 檔案 B 的測試：批次完成行為
- 檔案 C 的測試：中止功能

每個領域都是獨立的——修正工具核准不會影響中止的測試。

### 2. 建立聚焦的代理任務

每個代理會得到：

- **具體的範圍：** 一個測試檔或子系統
- **清楚的目標：** 讓這些測試通過
- **限制：** 不要改其他的程式碼
- **預期的輸出：** 你發現了什麼、修了什麼的摘要

### 代理提示的結構

好的代理提示是：

1. **聚焦的** —— 一個清楚的問題領域
2. **自足的** —— 包含理解問題所需的所有脈絡
3. **對輸出很具體** —— 代理應該回傳什麼？

### 常見錯誤

**❌ 太廣：**「修好所有測試」——代理會迷失
**✅ 具體：**「修好 agent-tool-abort.test.ts」——範圍聚焦

**❌ 沒有脈絡：**「修好那個競態條件」——代理不知道在哪裡
**✅ 有脈絡：** 貼上錯誤訊息與測試名稱

**❌ 沒有限制：** 代理可能會重構所有東西
**✅ 有限制：**「不要改正式的程式碼」或「只修測試」

**❌ 輸出模糊：**「修好它」——你不知道改了什麼
**✅ 具體：**「回傳根本原因與變更的摘要」

### 何時「不」使用

**相關的失敗：** 修好一個可能會修好其他的——先一起調查
**需要完整的脈絡：** 理解問題需要看到整個系統
**探索性除錯：** 你還不知道是什麼壞了
**共享狀態：** 代理之間會互相干擾（編輯同樣的檔案、使用同樣的資源）

### #驗證

代理回來之後：

1. **審閱每份摘要** —— 理解改了什麼
2. **檢查衝突** —— 代理是否改了同樣的程式碼？
3. **執行完整測試組** —— 確認所有修正能一起運作
4. **抽查** —— 代理可能會犯系統性的錯誤
