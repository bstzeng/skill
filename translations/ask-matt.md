# 問 Matt（Ask Matt）

你不會記得每個技能，所以就問吧。

在陳述某個技能做什麼、或建議略過某個步驟之前，先讀那個技能的 SKILL.md：這裡的摘要只供定位方向。

**流程**是一條穿越各技能的路徑。大多數路徑沿著一條**主要流程**前進，另有兩條**匯入路徑**併入其中。其他一切要嘛是獨立的，要嘛是在底下運作的詞彙層。

## 主要流程：點子 → 上線

大部分工作會走的路線。你有一個點子，想把它做出來。

1. **`/grill-with-docs`** 以訪談磨利點子。只要你是**在一個工作目錄中工作**，就從這裡開始：它是有狀態的，會把學到的東西保存在 `GLOSSARY.md` 與 ADR 中。（沒有工作目錄？改用 `/grill-me`，見「獨立技能」。兩者執行同一個 `/grilling` 基本元件；`grill-with-docs` 會留下書面紀錄，所以只要有 repo 可以留，它就是兩者中較好的那個。）
2. **分岔：你能在對話中解決每個問題嗎？** 如果某個問題需要一個能執行的答案（狀態、商業邏輯、你必須親眼看到的 UI），就繞道去做原型，兩個方向都以 **`/handoff`** 銜接（原型存在它自己的目錄中，這正是 `/handoff` 的用途；見「階段邊界」）：
   - 用 **`/handoff`** 交出去，然後針對那個檔案開一個新 session，
   - 用 **`/prototype`** 以拋棄式程式碼回答問題，
   - 再用 **`/handoff`** 把學到的東西交回來，並在原本的點子討論串中引用它。
3. **分岔：這是需要多個 session 的建構嗎？**
   - **是** → **`/to-spec`**（把討論轉成規格），然後 **`/to-tickets`** 把它拆成曳光彈式工單，每張都宣告其**阻擋邊**。接著以兩種方式之一處理工單：
     - 每張工單用 **`/implement`**，**每張之間都 `/clear` 上下文**。在本機追蹤系統上，那是 `.scratch/<feature>/issues/` 下每張工單一個檔案，由你手動依阻擋者優先處理；在真正的追蹤系統上，阻擋邊會變成原生的阻擋連結，所以任何阻擋者都已完成的工單都可以被接手。每張工單都自成一體，所以上一張的上下文可以丟棄。
     - 用 **`/implement-spec`** 一次跑完整份規格。它把工單讀成一張**任務圖**，在可開始的**前沿**上平行執行實作子代理，並把一切落在同一個**整合分支**上。當你寧可編排整個建構、而不是自己逐張驅動工單時，就用它。
   - **否** → 直接在這裡、同一個上下文視窗中用 **`/implement`**。

   無論哪種，程式碼都是透過驅動 **`/tdd`**（一次一個紅綠切片）建構出來的，並以 **`/code-review`** 收尾，對 diff 做雙軸審查（規範 + 規格）。`/implement` 每張工單都會跑這兩者；`/implement-spec` 的每個實作者都驅動 `/tdd`，並對整合分支跑一次 `/code-review`。當你只想以測試優先建構一個具體行為、不需要完整規格時，單獨使用 **`/tdd`**；每當你想針對某個固定點審查一個分支或 PR 時，單獨使用 **`/code-review`**。

   當工作以 pull request 送出時，**`/pr`** 會形塑 PR 內文：最能呈現變更的最小視覺、證明它能運作的前後對照證據，以及一個「單向門或雙向門」的判斷。它由模型自動呼叫，所以代理每次寫 PR 時都會用到。

4. **`/retro`** 讓循環閉合。在一次建構之後，尤其是出了狀況的那種，它會回顧整個 session，並建議修改代理的**環境**，而不是程式碼：導航指引、自動化檢查、`/code-review` 所強制的程式碼標準、引導檔、工具。機械性的錯誤變成決定性的檢查；判斷性的問題變成程式碼標準。下一次建構就會從更好的環境開始。

### 上下文衛生

讓步驟 1–3 保持在**一個不間斷的上下文視窗**中（在 `/to-tickets` 之前不要壓縮或清除），讓拷問、規格與工單都建立在同一份思考之上。之後每個 `/implement` 都從頭開始，以工單為依據工作。在 `/retro` 所回顧的那個 session 中、清除之前執行它；清除之後，就改成指向那個 session 的紀錄。

這件事的上限是**[智慧區（smart zone）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏銳推理的視窗範圍（在最先進的模型上約 15 萬 token）。如果某個 session 在 `/to-tickets` 之前就接近這個上限，不要在退化的狀態下硬撐；在最近的階段邊界執行 `/compact` 再繼續（見「階段邊界」）。

## 匯入路徑

會產生工作、然後併入主要流程的起始情境。

- **Bug 與請求越堆越多** → **`/triage`**。它讓 issue 通過分類角色，產出可交給代理的 issue，之後由 **`/implement`** 接手。

  分類只用於**不是你建立的** issue：bug 回報、新進的功能請求、任何未經整理就進來的東西。`/to-tickets` 產出的工單已經可以交給代理，所以**不要分類它們**。

- **有東西壞了** → **`/diagnosing-bugs`**。用於困難的那種：第一眼看不出來的 bug、時有時無的不穩定、在兩個已知良好狀態之間悄悄出現的退化。在擁有**緊湊的回饋循環**（一個已經會因*這個* bug 變紅的指令）之前，它拒絕提出理論，然後以回歸測試修正。修好之後，在同一個 session 中執行 **`/retro`**，問問什麼能預防這個 bug；如果真正的發現是沒有好的接縫可以鎖住它，那就是 **`/improve-codebase-architecture`** 的工作。

- **一項龐大、模糊的工作：一個全新專案或一個龐大的功能建構，一個 session 放不下** → **`/wayfinder`**，這裡最耗腦力的流程。當從這裡到目的地的路還看不見時，它會在 issue 追蹤系統上繪製一張由**決策工單**組成的**共用地圖**，並一次解決一張，產出**決策而非交付成果**，直到迷霧散去、道路清晰。**`/grill-with-docs`** 磨利的是你在一個 session 中就能掌握的點子，wayfinder 則是給你掌握不了的點子，而且它更慢、更密集，所以只把它留給這種情況，絕不用在範圍明確的功能上。

  當地圖清晰時，**它會交棒，而不是自己建構**：在 **`/to-spec`** 處併入主要流程，把地圖上相互連結的決策收斂成一份可建構的計畫，然後照常 `/to-tickets` 與 `/implement`。把地圖直接接到 `/implement` 會略過這個收斂，丟掉連結起來的細節，所以只有在這項工作最後證實真的很小時，才直接進 `/implement`。

## 程式碼庫健康

不是功能工作，只是維護。

- **`/improve-codebase-architecture`** 在你有空檔時就可以跑，讓程式碼庫保持適合代理在其中運作。它會找出**加深模組的機會**；挑選其中一個就會*產生一個點子*，你可以在 `/grill-with-docs` 處把它帶入主要流程。它是找出候選項目的勘查；**`/codebase-design`**（見下方）則是你設計所選項目的工作台。

## 底層詞彙

兩個由模型自動呼叫、在其他技能*底下*運作的參考，各自是其詞彙的唯一真實來源。當問題出在**用詞**而不是流程時，直接使用它們；或者讓上面的技能把它們拉進來。

- **`/domain-modeling`**：磨利專案的*領域*語言：挑戰一個模糊的術語、解決一個一詞多義的字（「帳戶」身兼三職）、把一個難以反悔的決策記錄成 ADR。它是 `/grill-with-docs` 所驅動、讓 `GLOSSARY.md` 保持乾淨詞彙表的主動紀律。
- **`/codebase-design`** 是深模組的詞彙（模組、介面、深度、接縫、轉接器、槓桿、區域性），用來設計模組的*形狀*：在乾淨接縫上、小介面背後的大量行為。`/tdd` 與 `/improve-codebase-architecture` 都使用這套語言。

## 階段邊界

**階段**是一個 session 內的一段工作：拷問、實作、QA。在兩個階段之間的**邊界**上，你有五個選項，而在它們之間做選擇，是這整張地圖中最模糊的決定：

- **繼續**：留在原地。不花任何成本，也不失去任何東西。
- **`/clear`**：清空視窗，當這裡的一切都與接下來的事無關時。
- **`/handoff`** 寫出一份可攜的 Markdown 檔。範圍很窄：只用於**新的主控環境**、**新的目錄**、**同事**，或在**階段中途**分出一個支線任務。它換到的是可攜性。
- **子代理**：把一個範圍明確的任務送到它自己的視窗，並取得一份回報。
- **`/compact`** 壓縮這段上下文，並用它來啟動一個新的 session。它是**預設選項**，位於決策樹的底部，而不是第一個想到的。

閱讀 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 取得有順序的決策樹：五個問題、每個分岔背後的理由，以及為什麼第一手來源的成本讓**繼續**成為最先要排除的選項。在邊界**上**做決定；在階段中途，就繼續，或把剩下的拆給子代理。

## 獨立技能

完全不在主要流程上。

- **`/grill-me`**：與 `/grill-with-docs` 相同的毫不留情訪談，但是**無狀態**的：它不在本機保存任何東西，也不建立 `GLOSSARY.md`。當你**不是在工作目錄中工作**時使用（磨利一份計畫、一個設計、一篇文章，任何底下沒有 repo 的東西）。如果你在工作目錄中，改用 `/grill-with-docs`：它執行相同的訪談並留下書面紀錄，所以嚴格來說它比較好。
- **`/grilling`** 是訪談的基本元件本身：輪次、前沿、事實是代理的工作而決策是你的。`/grill-me` 與 `/grill-with-docs` 是兩個有名稱的入口，而 `/triage`、`/wayfinder` 與 `/improve-codebase-architecture` 都在內部執行它。只有在你想要沒有任何包裝的訪談時，才直接使用它。
- **`/prototype`** 是一個回答單一設計問題的小型拋棄式程式：這個狀態模型感覺對嗎，或這個 UI 應該長什麼樣子。「拋棄式」是對程式碼寫法的限制，而不是承諾要銷毀它：答案會整合進正式程式碼，而原型本身則作為**第一手來源**保存在 main 之外的 `prototype/<name>` 分支上，並從實作 issue 指向它。它是主要流程步驟 2 中的繞道，但任何時候遇到難以在紙上解決的設計問題都可以用它。
- **`/research`**：把閱讀的苦工交給**背景代理**：它以**第一手來源**調查一個問題，然後在 repo 中留下一份附有引用的 Markdown 檔。它在閱讀時你可以繼續工作。它產出的檔案，是要在 `/grill-with-docs` 處*帶入*主要流程的材料，因為研究是為思考提供養分，而不是取代思考。
- **`/to-questionnaire`** 在阻擋你的東西不在你的腦袋或程式碼庫中、而是在**別人**的腦袋裡時登場，它會寫一份問卷讓他們填寫。它是 `/grill-me` 的反面：它不是就主題訪談你，而是就**寄送**訪談你（要寄給誰、你需要拿回什麼），並把問題對準缺口。拿回來的東西是 `/grill-with-docs` 或 `/to-spec` 的材料。
- **`/wizard`** 用於只有**人類**才能做的步驟：佈建基礎設施、設定憑證或 CI 機密、點過一個不熟悉的第三方後台、執行一次性的遷移或切換。它會產生一個互動式 bash 腳本，開啟每個 URL、擷取每個值，並寫入 `.env` 與 GitHub secrets，讓這套程序不再是你每次都要向代理重新解釋的東西。它由模型自動呼叫，所以代理一碰到只有你能通過的牆就會用它。如果代理自己就能做，它就應該自己做；這是給真正需要人類參與的地方。
- **`/wait-what`** 是修正一則沒傳達到的訊息的方法。在對話中途、任何其他技能之內都可以使用，代理會用白話文、以 `GLOSSARY.md` 的詞彙，補上你缺少的脈絡，重新說明它剛剛說的話。它是事後補救；`/grill-with-docs` 才是事前的解藥，因為及早約定一套共同語言，才能讓術語根本不會出現。
- **`/teach`**：以目前目錄作為有狀態的工作區，跨多個 session 學習一個概念。
- **`/writing-for-agents`** 是撰寫給代理閱讀之文件的參考：技能、AGENTS.md、被指向的文件。

## 前置條件

**`/setup-matt-pocock-skills`**：在你的第一個工程流程之前執行，設定其他技能所預設的 issue 追蹤系統、分類標籤與文件配置。也支援自訂的 issue 追蹤系統。
