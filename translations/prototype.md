# 原型（Prototype）

原型是**回答一個問題的拋棄式程式碼**。問題決定了原型的形狀。

## 選擇分支

根據使用者的提示、周邊程式碼，或（若使用者在場）直接詢問，判斷要回答的是哪個問題：

- **「這個邏輯／狀態模型感覺對嗎？」** → [LOGIC.md](LOGIC.md)。建立一個可分享的單一 HTML 檔（自由操作按鈕＋分頁式導覽流程），把狀態機推過那些在紙上很難推理的情境，而且非開發者也能操作。
- **「這應該長什麼樣子？」** → [UI.md](UI.md)。在單一路由上產生數個截然不同的 UI 版本，透過 URL 查詢參數與底部浮動列切換。

兩個分支產出的東西非常不同，選錯會浪費整個原型。如果問題確實模稜兩可、又聯絡不到使用者，就預設選擇與周邊程式碼較相符的分支（後端模組 → 邏輯；頁面或元件 → UI），並在原型最上方寫明這個假設。

## 兩者都適用的規則

1. **從第一天起就是拋棄式的，並清楚標示。** 把原型程式碼放在靠近它實際會被使用的地方（它所服務的模組或頁面旁邊），讓脈絡一目了然，但命名要讓隨意看過的人也知道這是原型、不是正式程式。拋棄式 UI 路由要遵守專案既有的路由慣例，不要發明新的頂層結構。
2. **極易執行。** UI 原型用專案任務執行器的一個指令就能啟動：`pnpm <name>`、`python <path>`、`bun <path>` 等。邏輯示範則是使用者雙擊就能開的單一 HTML 檔。無論哪種，啟動都不需要動腦。
3. **預設不做持久化。** 狀態存在記憶體中。持久化是原型要「檢驗」的對象，而不是它該依賴的東西。如果問題明確涉及資料庫，就連到暫存 DB 或本機檔案，並用清楚的「PROTOTYPE，請刪除我」命名。
4. **不要打磨。** 不寫測試，除了讓原型「能跑」之外不做錯誤處理，不做抽象化。重點是快速學到東西。
5. **把狀態攤開。** 每個操作之後（邏輯）或每次切換版本時（UI），印出或渲染完整的相關狀態，讓使用者看到什麼改變了。
6. **完成後要保存。** 把經過驗證的決策整合進正式程式碼，然後把原型本身當作**第一手資料**保存：commit 到一個拋棄式分支（不進 main），並在實作 issue 上留下指向該分支的脈絡連結。也要把答案（結論以及它解決的問題）記錄在 issue 或 commit 中。main 分支只保留經過驗證的決策。
