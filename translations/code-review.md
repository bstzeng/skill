對 `HEAD` 與使用者提供的固定點之間的 diff 進行雙軸審查：

- **規範（Standards）**：程式碼是否符合此 repo 文件化的程式碼標準？
- **規格（Spec）**：程式碼是否忠實實作了原始的 issue / 規格？

兩個軸以**平行子代理**執行，讓它們不會互相汙染上下文，然後由本技能彙整其發現。每個子代理都以全新的上下文視窗啟動。

issue 追蹤系統應該已經提供給你。如果沒有，請使用者執行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定比較點

使用者說的是什麼，什麼就是固定點（commit SHA、分支名稱、tag、`main`、`HEAD~5` 等）。如果他們沒有指定，就詢問。

把 diff 指令記錄一次：`git diff <fixed-point>...HEAD`（三個點，因此比較對象是 merge-base）。也用 `git log <fixed-point>..HEAD --oneline` 記下 commit 清單。

在進一步動作之前，確認固定點能解析（`git rev-parse <fixed-point>`）且 diff 不是空的。錯誤的參照或空 diff 應該在這裡失敗，而不是在兩個平行子代理裡失敗。

### 2. 找出規格來源

依以下順序尋找原始規格：

1. commit 訊息中的 issue 參照（`#123`、`Closes #45`、GitLab `!67` 等），依追蹤系統文件中的流程抓取。
2. 使用者以參數傳入的路徑。
3. `docs/`、`specs/` 或 `.scratch/` 下與分支名稱或功能相符的規格檔。
4. 如果都找不到，詢問使用者規格在哪裡。如果他們說沒有，**規格**子代理就會略過並回報「無可用規格」。

### 3. 找出規範來源

搜尋 repo 中每一個說明程式碼應如何撰寫的檔案。若存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`，它一定要在清單上。

在 repo 所記載的任何內容之上，規範軸永遠帶著下方的**程式碼異味基準**：一組固定的 Fowler 程式碼異味（《重構》第 3 章），即使 repo 什麼都沒記載也適用。有兩條規則約束它：

- **Repo 優先。** 文件化的 repo 標準永遠勝出；如果它認可某件基準會標記的事，就壓下該異味。
- **永遠是判斷題。** 每個異味都是一個標註的經驗法則（「可能有依戀情結」），絕不是硬性違規。和這裡的任何標準一樣，略過工具已經強制執行的部分。

每個異味的寫法是*它是什麼* → *如何修正*；拿它與 diff 比對：

- **神秘命名（Mysterious Name）**：函式、變數或型別的名稱無法透露它做什麼或存放什麼。→ 重新命名；如果想不出誠實的名字，代表設計本身很模糊。
- **重複程式碼（Duplicated Code）**：相同的邏輯形狀在變更中出現於多個區塊或檔案。→ 抽出共同的形狀，兩處都呼叫它。
- **依戀情結（Feature Envy）**：一個方法存取另一個物件的資料多於自己的。→ 把方法移到它所依戀的資料上。
- **資料泥團（Data Clumps）**：同樣幾個欄位或參數總是一起出現（一個想要誕生的型別）。→ 把它們打包成一個型別，傳遞那個型別。
- **基本型別偏執（Primitive Obsession）**：用基本型別或字串代表一個值得擁有自己型別的領域概念。→ 為該概念建立專屬的小型別。
- **重複的 switch（Repeated Switches）**：同一個型別上的同一個 `switch`/`if` 連鎖在整個變更中重複出現。→ 改用多型，或兩處共用一個對照表。
- **散彈式修改（Shotgun Surgery）**：一個邏輯變更迫使 diff 中許多檔案出現零散修改。→ 把會一起變動的東西集中到一個模組。
- **發散式變化（Divergent Change）**：一個檔案或模組因為好幾個不相關的原因被修改。→ 拆分，讓每個模組只為一個原因而改變。
- **誇誇其談的通用性（Speculative Generality）**：為規格中不存在的需求加入的抽象、參數或 hook。→ 刪掉；內聯回去，直到真正的需求出現。
- **訊息鏈（Message Chains）**：呼叫者不應依賴的長串 `a.b().c().d()` 導航。→ 把這段走訪隱藏在第一個物件的一個方法後面。
- **中間人（Middle Man）**：一個大多只是往下委派的類別或函式。→ 砍掉它，直接呼叫真正的目標。
- **被拒絕的遺贈（Refused Bequest）**：一個忽略或覆寫大部分繼承內容的子類別或實作者。→ 放棄繼承，改用組合。

### 4. 平行產生兩個子代理

在前景同時發出兩個子代理呼叫，並彙整它們回傳的報告。

**規範子代理提示**應包含：

- 完整的 diff 指令與 commit 清單。
- 你在步驟 3 找到的規範來源檔清單，**加上步驟 3 的異味基準**全文貼上（子代理沒有其他管道取得它）。
- 任務說明：「回報（適用時依檔案/區塊）：(a) diff 違反文件化標準的每一處：引用該標準（檔案＋規則）；以及 (b) 你發現的任何基準異味：說出名稱並引用該區塊。區分硬性違規與判斷題：違反文件化標準可以是硬性的，但基準異味永遠是判斷題，且文件化的 repo 標準優先於基準。略過工具已強制執行的部分。400 字以內。」

**規格子代理提示**應包含：

- diff 指令與 commit 清單。
- 規格的路徑或已抓取的內容。
- 任務說明：「回報：(a) 規格要求但缺少或只做了一部分的需求；(b) diff 中沒有被要求的行為（範圍蔓延）；(c) 看起來已實作但實作似乎有誤的需求。每項發現都引用規格中的對應行。400 字以內。」

如果沒有規格，就略過規格子代理，並在最終報告中註明。

### 5. 彙整

把兩份報告分別放在 `## Standards` 與 `## Spec` 標題下，逐字或稍加整理。**不要**合併或重新排序發現，因為兩個軸是刻意分開的（見「為什麼要兩個軸」）。

以一行摘要作結：每個軸的發現總數，以及*各軸之內*最嚴重的問題（如果有）。不要跨軸選出單一贏家：那正是分軸要避免的重新排序。

## 為什麼要兩個軸

一個變更可能通過一個軸卻沒通過另一個：

- 遵循每一條標準、卻實作了錯誤東西的程式碼 → **規範通過，規格失敗。**
- 完全做到 issue 要求、卻破壞了專案慣例的程式碼 → **規格通過，規範失敗。**

分開回報可以避免一個軸掩蓋另一個軸。
