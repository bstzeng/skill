本技能取用目前的對話脈絡與對程式碼庫的理解，產出一份規格書。**不要**訪談使用者；只要綜合整理你已經知道的事。

issue 追蹤系統與分類標籤用語應該已經提供給你了。如果沒有，請使用者執行 `/setup-matt-pocock-skills`。

## 流程

1. 如果還沒探索過，先探索 repo 以了解程式碼庫的現況。在整份規格中使用專案領域詞彙表的用語，並尊重你所修改區域的任何 ADR。

2. 草擬你要在哪些接縫上測試這個功能。優先使用既有的接縫而非新的。使用盡可能高層的接縫。如果需要新接縫，就在你能找到的最高點提出。整個程式碼庫的接縫越少越好——理想數量是一個。

與使用者確認這些接縫符合他們的預期。

3. 使用下方模板撰寫規格書，然後發布到專案的 issue 追蹤系統。套用 `ready-for-agent` 分類標籤——不需要額外分類。

<spec-template>

## 問題陳述

使用者面對的問題，從使用者的角度描述。

## 解決方案

問題的解決方案，從使用者的角度描述。

## 使用者故事

一份很「長」的編號使用者故事清單。每則使用者故事的格式應為：

1. 身為一個 <角色>，我想要 <功能>，以便 <好處>

<user-story-example>
1. 身為一個行動銀行客戶，我想要看到各帳戶的餘額，以便對我的花費做出更有根據的決定
</user-story-example>

這份使用者故事清單應該極為詳盡，涵蓋功能的所有面向。

## 實作決策

已做出的實作決策清單，可以包括：

- 將要建立/修改的模組
- 這些模組將被修改的介面
- 開發者提供的技術說明
- 架構決策
- Schema 變更
- API 契約
- 具體的互動方式

**不要**包含具體的檔案路徑或程式碼片段。它們可能很快就會過時。

例外：如果原型產出了某段程式碼，比文字更精確地表達了一個決策（狀態機、reducer、schema、型別形狀），就把它內嵌在相關決策中，並簡短註明它來自原型。只修剪出富含決策的部分，不是可運作的示範，只要重要的片段。

## 測試決策

已做出的測試決策清單。包括：

- 說明什麼是好測試（只測試外部行為，不測實作細節）
- 哪些模組會被測試
- 測試的前例（也就是程式碼庫中類似類型的測試）

## 範圍外

說明哪些事情不在本規格的範圍內。

## 其他備註

關於此功能的任何其他備註。
