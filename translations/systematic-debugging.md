# 系統化除錯

## 概述

**核心原則：** 在嘗試修正之前，「永遠」先找出根本原因。只修症狀就是失敗。

**違反這個流程的字面，就是違反除錯的精神。**

## 鐵律

{{CODE:1}}

如果你還沒完成第一階段，就不能提出修正。

## 何時使用

用於「任何」技術問題：
- 測試失敗
- 正式環境的 bug
- 非預期行為
- 效能問題
- 建置失敗
- 整合問題

**「特別」在以下情況使用：**
- 有時間壓力時（緊急狀況讓猜測變得誘人）
- 「就一個快速修正」看起來很明顯時
- 你已經試過多個修正時
- 上一個修正沒用時
- 你沒有完全理解問題時

**以下情況也不要略過：**
- 問題看起來很簡單（簡單的 bug 也有根本原因）
- 你很趕（趕工保證要重做）
- 主管要你「現在」就修好（系統化比亂試更快）

## 四個階段

你「必須」完成每個階段才能進入下一個。

### 第一階段：根本原因調查

**在嘗試「任何」修正之前：**

1. **仔細閱讀錯誤訊息**
   - 不要跳過錯誤或警告
   - 它們常常包含確切的解法
   - 完整閱讀堆疊追蹤
   - 記下行號、檔案路徑、錯誤代碼

2. **穩定重現**
   - 你能可靠地觸發它嗎？
   - 確切的步驟是什麼？
   - 每次都會發生嗎？
   - 如果無法重現 → 蒐集更多資料，不要猜

3. **檢查近期變更**
   - 改了什麼可能造成這個問題？
   - Git diff、近期的 commit
   - 新的相依套件、設定變更
   - 環境差異

4. **在多元件系統中蒐集證據**

   **當系統有多個元件時（CI → 建置 → 簽署、API → 服務 → 資料庫）：**

   **在提出修正「之前」，加入診斷插樁：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```
   （對「每一個」元件邊界：記錄進入元件的資料、記錄離開元件的資料、驗證環境/設定的傳遞、檢查每一層的狀態。執行一次以蒐集顯示「在哪裡」斷掉的證據，「然後」分析證據找出失敗的元件，「然後」調查那個特定元件。）

   **範例（多層系統）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo SET || echo UNSET)"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "IDENTITY in environment" || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **這會揭露：** 哪一層失敗（secrets → workflow ✓、workflow → build ✗）

5. **追蹤資料流**

   **當錯誤深藏在呼叫堆疊中時：**

   完整的反向追蹤技巧請見此目錄中的 `root-cause-tracing.md`。

   **簡易版：**
   - 錯誤的值從哪裡產生？
   - 是什麼帶著錯誤的值呼叫了它？
   - 持續往上追，直到找到源頭
   - 在源頭修正，而不是在症狀處

### 第二階段：模式分析

**修正之前先找出模式：**

1. **找到可運作的範例**
   - 在同一個程式碼庫中找到類似且可運作的程式碼
   - 有什麼可運作的東西和壞掉的很類似？

2. **與參考實作比較**
   - 如果是在實作某個模式，「完整」閱讀參考實作
   - 不要略讀——每一行都讀
   - 套用之前先完全理解該模式

3. **找出差異**
   - 可運作的和壞掉的有什麼不同？
   - 列出每一個差異，無論多小
   - 不要假設「那不可能有影響」

4. **了解相依關係**
   - 它還需要哪些其他元件？
   - 哪些設定、組態、環境？
   - 它做了哪些假設？

### 第三階段：假設與測試

**科學方法：**

1. **形成單一假設**
   - 清楚陳述：「我認為 X 是根本原因，因為 Y」
   - 寫下來
   - 要具體，不要含糊

2. **最小化測試**
   - 做「最小」可能的變更來測試假設
   - 一次一個變數
   - 不要一次修多個東西

3. **繼續之前先驗證**
   - 有效嗎？有 → 第四階段
   - 沒效？形成「新的」假設
   - 「不要」在上面再疊更多修正

4. **當你不知道時**
   - 說「我不理解 X」
   - 不要假裝知道
   - 尋求協助
   - 做更多研究

### 第四階段：實作

**修正根本原因，而不是症狀：**

1. **建立失敗的測試案例**
   - 最簡單的可能重現
   - 可能的話用自動化測試
   - 沒有框架就寫一次性的測試腳本
   - 修正之前「必須」有
   - 使用 `superpowers:test-driven-development` 技能撰寫正確的失敗測試

2. **實作單一修正**
   - 處理已找出的根本原因
   - 一次「一個」變更
   - 不做「既然都在這裡了」的改進
   - 不夾帶重構

3. **驗證修正**
   - 測試現在通過了嗎？
   - 沒有其他測試壞掉嗎？
   - 問題真的解決了嗎？
   - 宣稱成功之前使用 `superpowers:verification-before-completion` 技能

4. **如果修正沒用**
   - 停下來
   - 數一數：你已經試了幾個修正？
   - 如果 < 3：回到第一階段，用新資訊重新分析
   - **如果 ≥ 3：停下來並質疑架構（下方步驟 5）**
   - 沒有經過架構討論，「不要」嘗試第 4 個修正

5. **如果 3 個以上的修正都失敗：質疑架構**

   **顯示架構問題的模式：**
   - 每個修正都在不同地方揭露新的共享狀態/耦合/問題
   - 修正需要「大規模重構」才能實作
   - 每個修正都在別處產生新的症狀

   **停下來並質疑根本：**
   - 這個模式根本上是健全的嗎？
   - 我們是不是「純粹出於慣性而堅持」？
   - 我們應該重構架構，還是繼續修症狀？

   **在嘗試更多修正之前，先與你的人類夥伴討論**

   這「不是」失敗的假設——這是錯誤的架構。

## 危險訊號——停下來並遵循流程

如果你發現自己在想：
- 「先快速修一下，之後再調查」
- 「試著改 X 看看有沒有用」
- 「加多個變更，跑測試」
- 「略過測試，我手動驗證」
- 「大概是 X，讓我修它」
- 「我沒有完全理解，但這可能有用」
- 「模式說 X，但我會用不同方式改編」
- 「主要問題如下：[未經調查就列出修正]」
- 在追蹤資料流之前就提出解法
- **「再試一個修正」（已經試了 2 個以上時）**
- **每個修正都在不同地方揭露新問題**

**以上「全部」都代表：停下來。回到第一階段。**

**如果 3 個以上的修正都失敗：** 質疑架構（見第四階段步驟 5）

## 你的人類夥伴暗示你做錯了的訊號

**注意這些導正：**
- 「那個沒有發生嗎？」——你沒有驗證就假設了
- 「它會顯示給我們看……嗎？」——你應該加入證據蒐集
- 「別再猜了」——你在不理解的情況下提出修正
- 「好好深思這個」——質疑根本，而不只是症狀
- 「我們卡住了？」（沮喪地）——你的做法沒有用

**看到這些時：** 停下來。回到第一階段。

## 常見的合理化藉口

| 藉口 | 現實 |
|------|------|
| 「問題很簡單，不需要流程」 | 簡單的問題也有根本原因。對簡單的 bug，流程很快。 |
| 「緊急狀況，沒時間走流程」 | 系統化除錯比瞎猜亂試「更快」。 |
| 「先試試這個，再調查」 | 第一個修正會定下模式。從一開始就做對。 |
| 「確認修正有效後再寫測試」 | 沒測試的修正留不住。先寫測試才能證明。 |
| 「一次多個修正能省時間」 | 無法分辨是哪個有效。還會造成新的 bug。 |
| 「參考資料太長，我改編一下模式就好」 | 一知半解保證會有 bug。完整讀完。 |
| 「我看到問題了，讓我修它」 | 看到症狀 ≠ 理解根本原因。 |
| 「再試一個修正」（失敗 2 次以上後） | 失敗 3 次以上 = 架構問題。質疑模式，不要再修。 |

## 快速參考

| 階段 | 關鍵活動 | 成功標準 |
|------|----------|----------|
| **1. 根本原因** | 讀錯誤、重現、檢查變更、蒐集證據 | 理解「什麼」與「為什麼」 |
| **2. 模式** | 找可運作的範例、比較 | 找出差異 |
| **3. 假設** | 形成理論、最小化測試 | 已確認或提出新假設 |
| **4. 實作** | 建立測試、修正、驗證 | Bug 已解決、測試通過 |

## 當流程顯示「沒有根本原因」時

如果系統化調查顯示問題確實是環境性、時序相依或外部的：

1. 你已經完成了流程
2. 記錄你調查了什麼
3. 實作適當的處理（重試、逾時、錯誤訊息）
4. 加入監控/日誌以供未來調查

**但是：** 95% 的「沒有根本原因」案例都是調查不完整。
